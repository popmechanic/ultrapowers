# Run Room: a live, read-only page of every fleet run

**Grammar:** claims-v1

**Claim:** After this run, I open the Run Room page on my phone or my laptop and see every fleet run, the live ones first and then the finished ones newest first, and tapping a run shows me its Claim and Summary, each task's steps on one timeline, the run-wide checks and its pull request. (elicited)
**Summary:** This is the Run Room, a web page that shows every fleet run, live and past, in place of reading the board from a terminal on the laptop. It exists because following a run today means running a command and reading raw output, while everything a run did is already written to GitHub as it goes. With it you can glance at the fleet from your phone, open any run to read what it promised and watch each task's steps land, and nothing on the page can steer or change a run.

**Goal:** On the BASE scaffold, build the server half — a Durable Object that reads each watched target's run record from GitHub every 60 s and digests it into the `fleet` store — and the read-only client half: the run list with its filters, the run page (header, task timeline, step detail, checks strip), and the empty-fleet and legacy-run states.

**Tech Stack:** Bun + TypeScript 6 + TinyBase 10 (one `MergeableStore`, `WsSynchronizer` client, `WsServerDurableObject` with the Durable Object SQLite persister), React 19 + Vite 8 in `client/`, a Cloudflare Worker with Durable Objects through wrangler 4 in `server/`, the store schema in `shared/schema.ts`. Workspaces are isolated: `client/` and `server/` each have their own `node_modules`, so a probe that imports a package runs from inside the workspace that has it. The suite is `bun run test` from the root (`bun run typecheck` over both workspaces, then `bun test`).

**Publish:** bun install && bun run deploy
**Verify:** curl -fsS --max-time 20 "$ULTRA_PUBLISH_URL/health" | grep -q '"ok":true'

Spec: `docs/superpowers/specs/2026-09-26-run-room-design.md` (the operator's laptop only; every fact a task needs from it is in that task's Context).

### Task 1: The GitHub reader lists a target's runs and reads a file at a ref

**Type:** implementation

**Files:**
- Create: `server/src/github.ts`

**Claim:** The server can find every run a target has on GitHub, finished and in flight, and read a run's status, log and plan, with nothing but a fetch it is handed. (derived)
Machine: M1. `createGitHub(fetchFn, token).listRuns(repo)` lists the evidence tags and the in-flight evidence branches, returns one `RunRef` per run number — the tag when both exist — sorted by `n` descending, and its first request is to exactly `https://api.github.com/repos/<repo>/git/matching-refs/tags/ultra/evidence/` with the header `Authorization: Bearer <token>`. M2. `readText(repo, path, ref)` requests exactly `https://api.github.com/repos/<repo>/contents/<path>?ref=<ref>` with `Accept: application/vnd.github.raw`, resolves to the response body text, resolves to `null` on a 404 and rejects on any other non-2xx status. M3. `readPlan(repo, n)` reads `.ultrapowers/plan.md` at the tag `ultra/plan/run-<n>` and, when that is a 404, at the branch `ultra/plan-run-<n>`.

**Authorized-by:** spec §Where the data comes from (the table of refs and reads)

**Interfaces:**
- Produces: `createGitHub(fetchFn: typeof fetch, token: string): GitHub`
- Produces: `RunRef`

**Context:** A pure module: no global `fetch`, no `cloudflare:*` import, nothing but the `fetchFn` argument, so Bun can import it directly. The shapes, which the scan loop and the Durable Object wiring also use verbatim:

```ts
export type RunRef = {n: number; sha: string; ref: string; live: boolean};
export type GitHub = {
  listRuns(repo: string): Promise<RunRef[]>;
  readText(repo: string, path: string, ref: string): Promise<string | null>;
  readPlan(repo: string, n: number): Promise<string | null>;
};
```

The reads, per target `repo` (`<owner>/<repo>`):
- finished runs: `GET https://api.github.com/repos/<repo>/git/matching-refs/tags/ultra/evidence/` — a JSON array of `{ref: "refs/tags/ultra/evidence/run-<N>", object: {sha}}`; each becomes `{n: N, sha: object.sha, ref: "ultra/evidence/run-<N>", live: false}`.
- in-flight runs: `GET https://api.github.com/repos/<repo>/git/matching-refs/heads/ultra/evidence-run-` — `{ref: "refs/heads/ultra/evidence-run-<N>", object: {sha}}`; each becomes `{n: N, sha, ref: "ultra/evidence-run-<N>", live: true}`. A run number that has a tag is finished: drop its branch.
- a file: `GET https://api.github.com/repos/<repo>/contents/<path>?ref=<ref>` with `Accept: application/vnd.github.raw`, the path's slashes left as they are. The run's files are `.ultrapowers/runs/<N>/status.json` and `.ultrapowers/runs/<N>/events.jsonl` at the run's evidence ref, and `.ultrapowers/plan.md` at the tag `ultra/plan/run-<N>`, else the branch `ultra/plan-run-<N>`.

Every request carries `Authorization: Bearer <token>`, `User-Agent: runroom` and `X-GitHub-Api-Version: 2022-11-28`; the ref listings carry `Accept: application/vnd.github+json`. An empty target answers `409`, which `listRuns` treats as no runs.

### Task 2: The plan parser reads a run's title, Claim, Summary and task titles

**Type:** implementation

**Files:**
- Create: `server/src/plan.ts`

**Claim:** A run's page shows the plan's own title, its Claim and its Summary word for word, and each task by its plan title. (derived)
Machine: M1. `parsePlan(text)` returns `title` as the first line beginning `# ` with that prefix removed, and `claim` as the rest of the first line beginning `**Claim:** ` byte-for-byte, its closing tag included. M2. `summary` is the text after `**Summary:** ` on its line plus every following line up to the next blank line, each line trimmed and joined with one space. M3. `tasks` is one `{id, title}` per `### Task <id>: <title>` heading, in file order. M4. For text with none of these, `parsePlan` returns `''` for `title`, `claim` and `summary` and `[]` for `tasks`.

### Task 3: The event digester turns a run's log into steps, checks and task outcomes

**Type:** implementation

**Files:**
- Create: `server/src/digest.ts`

**Claim:** Each task's lane shows its dispatches, probe runs, referee calls, landings and folds as steps, the run shows its checks, and an older run is marked as one whose timeline is not available. (derived)
Machine: M1. `digestRun(input)` returns `runId` `<repo>#<n>` and a `run` row carrying `repo`, `n`, `state`, `phase`, `title`, `claim`, `summary`, `pr`, `merged`, `startedAt`, `updatedAt`, `era`, `taskCount`, `evidenceSha` and `error`; for run-244 `state` is `done`, `era` `factory`, `taskCount` 9, `evidenceSha` the input `sha`, `merged` `2b463ab401b2d744e89d11ded322f73fb92732d0` and `pr` `https://github.com/popmechanic/ultrapowers/pull/1309`. M2. Each event of a mapped kind is one `steps` row whose `kind` follows the map; run-244's log yields exactly `audit=1 dispatch=20 fold=10 fold-red=10 land=9 measure=53 merge=1 pr=1 referee=3`. M3. A step's `ok` follows the ok rules; exactly 12 of run-244's steps have `ok` false. M4. A step's id is `<runId>/<seq>` with `seq` the event's zero-based line index in `events.jsonl`, and a `measure` step's `label` is `exit <exit>` and its `detail` the event's `cmd`. M5. Each `check:line` event is one `checks` row; run-244 yields 22, of which 2 have `base` true and 1 a non-zero `exit`. M6. `tasks` has one row per task; run-244 yields 9, every `outcome` `folded`, task 5's `k` 2, task 9's `claim` 0.18 and task 2's `refereeBlocking` 1. M7. The in-flight snapshot of run-244 yields `state` `running`, 102 steps and every task's `outcome` `pending`. M8. A log with no `dispatch:start` event is a legacy run: `era` `legacy`, zero `steps`, `checks` and `tasks` rows, and `taskCount` the plan's task count — run-150 gives `taskCount` 5.

**Authorized-by:** spec §The digest: the store's shape; §What the operator sees (Older runs)

**Interfaces:**
- Produces: `digestRun(input: DigestInput): Digest`

**Context:** A pure module with no imports beyond types, so Bun and the Worker both load it. The shapes, used verbatim by the scan loop and the Durable Object wiring:

```ts
type Cell = string | number | boolean;
type Row = Record<string, Cell>;
export type DigestInput = {
  repo: string;             // '<owner>/<repo>'
  n: number;
  sha: string;              // the evidence ref's sha this digest was read at
  status: any;              // parsed status.json
  events: string;           // raw events.jsonl text
  plan: {title: string; claim: string; summary: string; tasks: {id: string; title: string}[]} | null;
};
export type Digest = {
  runId: string;                 // '<repo>#<n>'
  run: Row;                      // the one runs row
  tasks: Record<string, Row>;    // row id '<runId>/<task>'
  steps: Record<string, Row>;    // row id '<runId>/<seq>'
  checks: Record<string, Row>;   // row id '<runId>/<seq>'
};
```

Cells (the store's `TABLES_SCHEMA` in `shared/schema.ts`):
- `runs`: `repo`, `n`, `state` (status `state`), `phase`, `pr`, `merged`, `startedAt`, `updatedAt`, `error` (each from status, `''` when null or absent), `title`, `claim`, `summary` (from `plan`, `''` when null), `era` (`factory` | `legacy`), `taskCount` (plan task count, 0 when null), `evidenceSha` (input `sha`).
- `tasks`: `runId`, `task`, `title` (plan task title), `k` (from `dispatch:k`, default 1), `outcome` (`status.tasks[task].state` when it is `folded`, `parked` or `failed`, else `pending`), `claim` (the `claim` of the task's last `landing`, 0 when none), `refereeBlocking` (the `blocking` of the task's last `referee`, 0 when none). The task ids are the plan's task ids, plus any key of the `dispatch:k` map the plan lacks.
- `steps`: `runId`, `task` (the event's `task`, `''` for run-level), `at` (ms: `Date.parse(ts)` for a string `ts`, the number itself otherwise), `kind`, `ok`, `label`, `detail`.
- `checks`: `runId`, `cmd`, `base` (`true` only when the event's `base` is `true`), `exit`, `minor` (`true` only when `minor` is `true`).

Event kind to step kind: `dispatch:start` → `dispatch`; `run:line` → `measure`; `referee` → `referee`; `landing` → `land`; `fold:verify` → `fold`; `fold:red` → `fold-red`; `publish:pr` → `pr`; `merge` → `merge`; `run:audit` → `audit`; `check:line` → a `checks` row, not a step. `dispatch:k` fills `tasks.k` from its `k` map (`{"1": 1, "5": 2, …}`) and makes no step. Every other kind is ignored (`worker:tool`, `jev`, `pair`, `supervisor*`, `select*`, `floor`, `gate:*`, `board:*`, `dispatch:end`, `landing:facts`, `refold`, …).

Ok rules: `measure` ok when `exit === 0`; `referee` ok when `blocking === 0`; `merge` ok when `code === 200`; `fold` ok when every entry of the event's `ran` array has `exit === 0`; `fold-red` never ok; every other step ok.

Labels: `dispatch` `k=<the task's k>`; `measure` `exit <exit>`; `referee` `<blocking> blocking`; `land` `claim <claim>`; `fold` `<ran.length> ran`; `fold-red` `exit <exit>`; `pr` the event's `url`; `merge` `code <code>`; `audit` the event's `state`. `detail`: the event's `cmd` for `measure` and `fold-red` (`''` when null), `''` otherwise.

`seq` counts every line of `events.jsonl` from 0 — blank and ignored lines included — so the ids are stable as the log grows. Skip a line that is not JSON. Era: a log with no `dispatch:start` line is `legacy` and yields no `tasks`, `steps` or `checks` rows at all (its `run` row is still complete).

### Task 4: The scan loop re-reads only changed runs and backfills five finished runs a tick

**Type:** implementation

**Files:**
- Create: `server/src/scan.ts`

**Claim:** A run that has not changed is never read again, a live run is read as soon as it changes, and the backlog of old runs fills in a few at a time, newest first. (derived)
Machine: M1. `scanTarget(opts)` calls `load` for a ref only when the store's `runs` row `<repo>#<n>` has an `evidenceSha` different from the ref's `sha` (or no row); it loads every changed live ref, then at most `budget` changed finished refs in descending `n`, and returns `{loaded, finishedLoaded}`. M2. With eight unseen finished refs 1–8 and one live ref 9 and a budget of 5, the first scan loads 9, 8, 7, 6, 5, 4 in that order, the second 3, 2, 1, and the third nothing. M3. `writeDigest(store, digest)` sets the digest's `runs` row and replaces every `tasks`, `steps` and `checks` row whose `runId` is the digest's, so a step absent from the new digest is gone from the store. M4. A `load` that rejects does not reject `scanTarget`: the run's row gets the error's message in `error` and its `evidenceSha` is not advanced. M5. `scanTarget` sets the `targets` row `<repo>` cell `lastScanAt` to `opts.now`.

**Authorized-by:** spec §Server (Refresh, Backfill), §Where the data comes from (Change detection)

**Interfaces:**
- Produces: `scanTarget(opts: ScanOpts): Promise<{loaded: number; finishedLoaded: number}>`
- Produces: `writeDigest(store: MergeableStore, digest: Digest): void`
