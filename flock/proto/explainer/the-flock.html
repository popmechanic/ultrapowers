Part one

Today's factory

A run takes a signed plan and turns it into one pull request. Five things happen, in this order.

Today · 1 of 5

One starting point, many isolated clones

The launcher commits the plan on top of main. That commit is BASE. Every task that is ready at the start is cloned from it; a task that starts later is cloned from the combined code as it stands at that moment. While they work, nobody can see anybody else's changes.

Today · 2 of 5

Race, measure, keep one

When a task has more than one implementer, the engine measures each version with the plan's own probes and the existing tests that touch it, then keeps one. The facts decide first; Jev's reading only breaks ties.

Today · 3 of 5

Landings, one at a time, through one writer

Tasks finish whenever they finish, and each one lands the moment it is ready. The engine is the only thing that writes the combined code, so every landing waits its turn through the same checks.

Today · 4 of 5

Inside a fold: a weave built for one use

Manyana merges by knowing which lines are the same line. The kernel does not keep that knowledge between landings. It rebuilds it each time by comparing text against the task's starting point (BASE, for this task), merges once, and throws it away.

Today · 5 of 5

One pull request per run

At the end the sandbox opens its own pull request, and merges it if the run ended green. Runs launch in parallel, so main may have moved by then. The sandbox folds its whole run onto the new main and tries again.

Part two · map #1292

The Flock

The map keeps the one thing that must never move, the mechanical facts, and puts them at a single edge in front of main. Everything behind that edge becomes a flock: agents that keep their own copies, share them freely, and post what they believe.

Flock · 1 of 6

Every agent keeps its own copy

Each agent edits its own copy of the file, kept as a weave. Copies travel between agents in any order. Because Manyana's merge gives the same result whatever the order, every copy ends up identical without anyone coordinating.

Flock · 2 of 6

Record the edit; don't guess it

This is the one wrong merge from the stress test. Task A deletes an if block; task B deletes the closing brace just above it. Two of the lines read exactly }.

Edits made by rewriting a whole file or by a shell command such as sed are not single edit calls, so those would still fall back to comparing text. How often that happens was measured on 2026-09-25: about 5% of landed file changes. Built from edit calls, the stray-brace case merges correctly, and 2,400 simulated edit pairs merged with no silent wrongs.

Flock · 3 of 6

The board holds beliefs; the facts stand apart

Agents post what they believe about the work, how sure they are, and which version of the code they looked at. Jev reads the board continuously and adjusts confidence. Nothing on the board blocks anyone. Facts are kept separate: an exit code on an exact snapshot.

Flock · 4 of 6

Nobody dispatches

Kata already lists which tasks are ready, and lets an agent claim one only if nobody owns it. In the Flock, agents pull their own work, let go of it when they are blocked, and can propose work the plan missed.

Flock · 5 of 6

Candidates live in the file, hidden

Today each racing implementer needs its own clone, and the losing clone is deleted. With lines that keep their identity, candidates can sit in the same weave as hidden lines, and choosing a winner makes its lines visible. Tested on 2026-09-25: this works for whole candidates. Keeping a single line from the loser also works, but the weave, not us, decides where that line goes.

Flock · 6 of 6

Facts at the edge

The swarm keeps producing snapshots of its merged code. Each is tested against the plan's facts. Main only takes a snapshot that is green and comes from a swarm that has gone quiet.

What could go wrong

  • Text that merges cleanly can still be broken code. The facts at the edge catch that, but nothing guarantees the swarm ever reaches green.
  • The swarm could oscillate, changing the same lines back and forth. Deciding when a run is settled is the riskiest part, and it is ticket 5.
  • Agents would see each other's half-finished work. An edit can fail because the file moved underneath it. The agent re-reads, which costs tokens.
  • Manyana's limits become ours. It is one file of Python, text only, with no line identity yet, and its history grows without bound. We never patch it; everything goes in our wrapper.
  • Keeping one line from a losing candidate can't choose where it lands. The weave orders lines added at the same spot by itself; in the test, an adopted guard landed after a return, with no flag.
  • Two agents inserting at exactly the same line are merged in a fixed order with no conflict flag, where git would flag it.
  • Some edits aren't edit calls. Whole-file rewrites and shell edits still need the text-comparison fallback.
  • It retires standing doctrine: "one merge, one writer", the Blackboard's strict "facts, never commands", and "fold on every landing". That is the operator's call, made on the prototype's numbers.
