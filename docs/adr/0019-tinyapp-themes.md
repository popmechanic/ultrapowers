# 0019. TinyApp themes

Status: accepted (2026-11-25)  
Governs: `skills/ultrawrite/themes/contract.json`, `skills/ultrawrite/themes/README.md`, `skills/ultrawrite/themes/structure.css`, `skills/ultrawrite/themes/sample.ts`, `skills/ultrawrite/themes/check.ts`, `skills/ultrawrite/themes/place.ts`, `skills/ultrawrite/themes/pouf/`, `skills/ultrawrite/stories/policy.json` (`ui`), `skills/ultrawrite/references/first-build.md`

## Handing a first build UI SDK and a theme

- **Why** — A new TinyApp's author writes a better page when handed tested behaviour and a look. On 2026-11-25 a spike built one page three ways, bare, on stock UI SDK and on Pouf-themed UI SDK (n=1 run per arm); blind, the operator ranked the Pouf-themed page first, the stock one second and the bare one third. So every first build is handed `@ui-sdk/react` and `@ui-sdk/core` and a theme in its first commit. The task's Context says both packages must be declared in `dependencies` at exactly the pinned version, which a probe checks, and that using the components and the theme, restyling them, adding to them or not using them is the author's call: the page is theirs.
- **An experiment** — The reading is n=1 run per arm, under the n=5 runs floor. Its rollback is the `ui` cell's: handed nothing, meaning first-build.md's Context without the UI paragraph and no place step. The rollback is words, not a code path, so nothing exercises it.
- **Nothing checks use** — The anti-goal is a catalog. No probe, check or gate reads whether a page uses the library or the theme, and the theme's layout pieces (`kit.tsx`) are conveniences, never the only parts allowed. The one probe added to a first build proves the plan's one clause about the pin (such as "The app declares UI SDK at exactly the pinned version"): it reads `dependencies` in `package.json` and nothing else. The walk reports the slots on the live page and the ones the theme has no rule for; it never gates.
- **The pin is one cell** — UI SDK is beta (`0.1.0-beta.17`, first published 2026-11-12), so it is pinned exactly, in the `ui` cell of skills/ultrawrite/stories/policy.json with its `n`, `window` and rollback. `place.ts` reads it into the app's `theme.json`; `contract.json`, the themes tools' `package.json` and first-build.md's version probe carry the same version, and the tests hold each to the cell. Moving the pin is changing the cell, running the check and looking at the sample page; `structure.css` is tied to the pinned version.
- **The theme is a choice in enrichment** — "How it looks" is which theme. The default is the cell's `theme`; the operator is asked only when more than one theme folder exists or they bring their own, and product.json carries the choice as the optional `intent.theme`, a theme's name or a path. A path is resolved against the directory `place.ts` is run from. How the page reads is still judged at the walk and the smoke.

## A theme travels as files

- **skills/ultrawrite/themes/place.ts** — A theme reaches an app by being copied into its first commit (operator's pick over a starter repository, which would restore the template retired by 0018, and over npm packages, which would need a release per theme change and make bringing your own mean publishing). A first build's builder reads only that commit and `node_modules`, and a built app keeps its look until a plan changes it. `place.ts` runs the check, refuses a theme with a finding and writes nothing then, refuses an app that already has `client/src/theme/`, and otherwise writes `client/src/theme/structure.css`, the theme's top-level files whose names do not begin with a dot at `client/src/theme/<name>/` and `client/src/theme/theme.json` (the theme's name, the plugin commit or else `plugin.json`'s version, the UI SDK version). It writes into a sibling folder and renames it into place, so a write that fails midway leaves no partial `client/src/theme/`. A name is a folder under `themes/`; a path is someone's own theme.
- **The Files lines** — `place.ts` prints the placed files as ``- Modify: `<path>` `` lines, because they exist at the base, for the task's Files; the path is in backticks because `plan_parse.py` reads a Files path only there. It leaves out `font.css`, so the gate's reader is not handed about 52 KB of font.
- **A theme has no behaviour and no build step** — A theme is plain CSS and, optionally, a few layout components. The first build has no CSS pipeline: the page is one HTML document and one script, so stylesheets are imported as text and inlined in `<style>` elements in the server render. A theme may therefore hold no `@import` and no `url()` but a `data:` URL, and the check refuses either. An app that imports the stylesheets with `with { type: 'text' }` needs an ambient `declare module '*.css'` for `bunx tsc --noEmit`; Pouf's README shows it.
- **Layers** — `structure.css` begins `@layer ui-sdk, structure;` and a theme's `theme.css` begins `@layer ui-sdk, structure, <name>;`, so the order holds whichever file is inlined first. UI SDK injects its behaviour CSS into the `ui-sdk` layer at runtime, so it stays underneath, and any unlayered rule the author writes beats all three. A theme replaces UI SDK's stock `web.css`, which is never also loaded.

## The structure sheet

- **skills/ultrawrite/themes/structure.css** — A structure sheet we own sits under every theme, in its own `structure` layer. The spike's theme had to supply dialog centring, backdrop sizing and a reset of the browser's popover chrome itself, some of it resting on a style UI SDK injects at runtime and does not document. Writing it once spares every theme author re-deriving it. Layering themes over stock `web.css` instead carried about 200 KB of rules into the page and had the theme fighting a second cascade (spike arm B).
- **What it holds** — Box sizing, dialog and alert-dialog content and backdrop positioning, the popover reset and popup sizing from UI SDK's variables for select, menu and combobox content only (UI SDK resets popover and tooltip content itself, measured on the pinned version), the zeroed margins of titles and descriptions, field and checkable-label layout, the segmented-control and tabs indicators' position, the meter and progress fills' position, separator thickness, and the toast stack and its order. Every rule sits in `:where()`, so a theme's rule wins at any specificity.
- **The line between structure and look** — Structure is what makes a part work at all; it sets no colour, radius, shadow or font, and `check.ts --structure` fails if it does. A theme's layer is above it, so a theme may override any of it (Pouf's phone sheet does). Icons are the theme's to draw, because UI SDK's icon tokens mean nothing without its `web.css`.

## The contract

- **skills/ultrawrite/themes/contract.json** — The contract is a machine-readable list, a sample page and a check, so someone else can write a theme and learn mechanically what it missed without reading our code; a document alone tells a theme author nothing. It also states the facts no slot list carries: the layer order, that popup placement is UI SDK's inline style and not a theme's to move, that variants are attributes the author sets (`data-variant`, `data-size`), that a theme draws every icon itself, and the folder's rules (its name is the layer name, a plain identifier other than `ui-sdk` or `structure`; `theme.css`, `README.md` and `LICENSE` are required, `font.css` and `kit.tsx` optional; only top-level files not beginning with a dot are placed; `theme.css` opens with the layer line, before any comment). `variables` lists every `--theme-*` custom property `structure.css` reads, with its default and purpose, and a test holds the list to the sheet. `themes/README.md` is the theme author's page: the files, the layer line, the variables, the sample and the check, with Pouf as the worked example.
- **The core set** — 21 components: Button, Field with Label, Input, Textarea, Number Input, Select, Dialog, Alert Dialog, Checkbox, Switch, Segmented Control, Radio, Tabs, Menu, Popover, Tooltip, Toast, Combobox, Meter, Progress, Separator. They are what the spike's authors reached for plus what a small app commonly needs, not all 54 of UI SDK's. An author who needs another styles it from the theme's tokens, and the walk lists its slots.
- **Slots** — Each slot says where it appears (`in`: `markup`, in a server render, or `live`, only in a running page), and, where it has duties, who does them: `structure` says what `structure.css` does for it and `theme` what the theme must (a size, an icon to draw, a row to lay out), so an author need not read our CSS. A slot marked `hidden` or `optional` is not required of a theme and is not reported by the walk's slot check.
- **States come in two kinds** — `markup` states appear in a server render (`data-disabled`, `data-checked`, `data-invalid` and the like); `css` states exist only in a live page or only in CSS (`data-open`, `data-starting-style`, `data-ending-style`, `:hover`, `:active`, `:focus-visible`). The check requires a rule for both kinds, and only `markup` slots and states from the sample's server render tell it the contract has gone stale against the pinned UI SDK.

## The sample and the check

- **skills/ultrawrite/themes/sample.ts** — The sample serves one page showing every contract component in every required state, under the structure sheet and a given theme. It is how a person looks at a theme, and `--slots` prints the slots its server render shows, which the check compares with the contract.
- **skills/ultrawrite/themes/check.ts** — The check reports, one per line, a required slot or state no rule in `theme.css` selects, a rendered slot the contract does not list, a folder name that cannot be a layer name, a missing `theme.css` or a wrong first layer statement (said as such when a comment comes first), an `@import` or a non-`data:` `url()`, and a missing `README.md` or `LICENSE`. It flattens nesting with Bun's own CSS transform and walks the rules: a slot is styled when any subject compound of a selector contains `[data-slot="X"]`, directly or inside `:is()`, and a state when that same compound carries the state. An ancestor or a `:has()` does not count.
- **Lowered logical properties** — Bun's CSS transform lowers logical properties into `:lang()` selector fragments; the check ignores those fragments, so a theme that writes `margin-inline` is read as written.
- **The check measures no colour** — Contrast is looked at on the sample page by a person, not computed, and a theme's README says where it falls short (Pouf's does).
- **The walk's slots** — `check.ts <theme> --slots <walk.json>` lists the slots on a built page the theme has no rule for. It exits 0 whatever it lists, because the walk is a report.

## Pouf

- **skills/ultrawrite/themes/pouf/** — Pouf is the first theme and the default we develop against, never one forced on everyone. It started from the spike's theme, with its structural rules moved to `structure.css`; Checkbox and Number Input were re-derived from the original 1st-Pouf sources at `dd53be04`, and the eleven components the spike did not cover were read from the same sources. It is light only and was looked at in Chromium only, at 1100 px and 375 px.
- **Meter and progress bars read against a deep well** — A dry build's author reported a full mint bar that looked empty: the pastel fills sat on the lavender page colour at 1.11:1 to 1.69:1. The well is now a deep purple (`--pouf-well-deep`, `#5b4499`) under an ink rim, and every tone's glossy pastel bar is 3.85:1 (purple) to 6.16:1 (yellow) against it by the WCAG formula, computed on the sample page.
- **Solid buttons stay under 3:1 on purpose** — The purple fill is 1.69:1 and the orange destructive fill 1.48:1 against the page, below the 3:1 UI SDK's guide asks for on control edges. An edge would remove the cushion look the operator preferred; the lip and drop shadow mark the edge, the ink label is well above 4.5:1, and the README says so. The combobox trigger shares the solid button's purple, under the same reasoning.
- **No second contrast exception** — A checked radio is marked with an ink dot rather than a pastel fill, so the buttons' fills stay the only controls whose state rests on a colour under 3:1.
- **Nunito is embedded** — `font.css` holds Nunito's Latin subset (39 KB, about 52 KB embedded) as a `data:` URL, so no font host is dialled and the theme has no relative URL. Its OFL-1.1 text ships beside it as `OFL.txt`; Pouf's own `LICENSE` is MIT (Mojtaba Beheshti).
- **kit.tsx** — The layout pieces (Stack, Row, Card, Heading, Text, Badge, Separator) each take `className` and `style` and typecheck under a strict `tsconfig`, since the app's check covers them. `@types/react` is a devDependency of the themes tools, so the kit can be typechecked in the plugin as well as in an app.
