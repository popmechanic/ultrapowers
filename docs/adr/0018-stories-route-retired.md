# 0018. The stories route is retired

Status: accepted (2026-11-25)  
Governs: `skills/ultrapowers/scripts/plan_parse.py`, `skills/ultrawrite/stories/ask.ts`, `skills/ultrawrite/stories/gate_jev.ts`, `skills/ultrawrite/stories/jev_checks.ts`, `skills/ultrawrite/stories/product.ts`, `skills/ultrawrite/stories/walk.ts`

Supersedes 0006 (the TinyApp checker), 0014 (the TinyApp template) and 0015 (story planning
for TinyApps). The decisions of 0015 that still describe a surviving file are restated below,
without the pieces that went, so nothing that remains is governed only by a superseded record.

## The retirement

- **What went** — On 2026-11-25 every TinyApp plan became a claims-v1 plan, and the route that wrote TinyApp plans as stories-v1 was removed in one branch. Authoring lost skills/ultrawrite/stories/ arrange.ts (Jev arranging the page into versions), scaffold.ts, storyui.ts, compile.ts, preview.ts and preview/, parts.ts, notebook.ts, bundle.ts, checks.ts, the TinyApp template (tinyapp-template/, with 1st-Pouf vendored inside it) and the vendored json-render composer; skills/ultrawrite/catalog/; skills/ultrawrite/references/stories.md; the `authoring_arrange` question set and the bundle stage of jev_checks.ts. The checker went whole: factory/stack/tinyapp/ (check.ts, screens.ts, browser.ts, celld.ts, diff.ts, probe.ts) and evals/readings/checker_kit.py. The grammar went everywhere it was read: stories_parse.py, stories_check.py and probe_block.py, the stories workload, checker pre-flight and screens check in the Flock engine, factory/flock/new_parts.mjs and the story-checker, screens and "New screen parts" rows of the run record, and the launcher's stories sizing, Numbers refusal and stories fetch. The intent tray lost its show_screen tool, its screen state and its version-pick and Open screen buttons; /tray, /note and the .ultrapowers/feedback.jsonl reader stay. The `first_build` cell of skills/ultrawrite/stories/policy.json went with the route it chose between.
- **Why** — The agents that build a TinyApp's front end did better work when less constrained. On 2026-11-24 the operator judged, in a blind smoke test, a one-author Potluck entirely superior to a three-builder one, and both better than the stories-route Potluck of 2026-11-20 (n=1 run per arm, popmechanic-potluck-3 run-1 and run-2, #1606). The stories route constrained the page three ways: Jev arranged it, a JSON screen format reached 15 parts of 1st-Pouf's 60 or so, and a checker refused anything else. Since #1606 a new app already went to one author and the stories route was reached only through the `first_build.route` rollback cell. The operator picked retiring the whole route over keeping stories with a freed page, or keeping the browser checker unexercised (2026-11-25).
- **An experiment** — The flip rests on n=1 run per arm, under the n=5 runs floor, so it is an `experiment`. Its rollback is a launch and an authoring session from a checkout of `dd53be04`, the base before the first deletion, as with the factory the Flock replaced.
- **What replaced it** — A new app's first plan follows skills/ultrawrite/references/first-build.md: one claims-v1 task from the ask and the app's rules, written by one author on an empty repository. Every later plan on a TinyApp is an ordinary claims-v1 plan. Both start with the enrichment in skills/ultrawrite/references/enrich.md, which now ends at the build order. Apps already built on stories (potluck-2, the old todo fixtures) are not migrated: their next plan is an ordinary claims-v1 plan, like any other built app.
- **How it looks** — "How it looks" is no longer asked while planning, because the arranged versions were the only thing shown. Until a theme exists it is judged on the real app, at the walk before the operator's smoke and at the smoke itself.
- **The installed plugin** — A session loads the plugin's last release, so sessions keep the old ultrawrite text until the next 0.3.x release; no release is part of this retirement.

## The retired grammar

- **skills/ultrapowers/scripts/plan_parse.py RETIRED_GRAMMARS** — A plan whose **Grammar:** header names stories-v1 is refused by name, `grammar: stories-v1 was retired on 2026-11-25; write the plan as claims-v1`, rather than read as an unknown grammar, so an author holding an old plan learns what to write instead. plan_parse.py and plan_check.py exit 2 on it, and skills/ultrawrite/scripts/check_provenance.py and extract_gate_input.py catch the refusal.

## Product route

- **routeOf** — `routeOf` in skills/ultrawrite/stories/product.ts reads a product record with no built subproject as a first build and prints `ROUTE fact: first build, one author`; a record with any built subproject prints `ROUTE fact: later plan, claims`. No policy cell chooses between routes. The `by` field of a subproject stays readable, so a record from an app once built by stories still loads, and it no longer changes the route.

## Carried from 0015

- **skills/ultrawrite/stories/walk.ts** — A run's probes show that an app works, not that it is good to use: on 2026-11-24 the Potluck app the operator judged far worse passed six of six probes and the better one five (n=1 run per arm), and on 2026-11-20 a page they called nonsensical passed seventeen of seventeen (#1609). So the session that serves a built app for the operator's smoke walks it first as a first-time user and answers the six `smoke_walk` questions of skills/ultrawrite/stories/questions.json, each yes, partly or no with one sentence of evidence. walk.ts makes no model or network call: it lists the questions, refuses an incomplete walk, renders the answers for a pull request comment, records the operator's own verdict beside the walk and counts agreement over `*.walk.json`. The walk reports and never gates. It is an experiment kept on the laptop until the walk and the operator have agreed on n=5 runs; moving it into the sandbox is a separate decision, and its rollback is removing the step.
- **skills/ultrawrite/stories/jev_checks.ts** — skills/ultrawrite/stories/jev_checks.ts asks Jev at each enrichment stage (understanding, map, decompose, named by a required --stage) after the code checks run; Jev judges and never generates or decides, and its flags are for the author to act on. Only three kinds of flag may become operator doubts (DOUBT:), each a product choice in plain words: an ask sentence with two readings, an assumption about what the app does, and a link the audience might not expect.
- **reader (skills/ultrawrite/stories/jev_checks.ts)** — In jev_checks.ts, reader's `one` sends each Jev request immediately so a stage's calls run concurrently, and returns a thunk the stage awaits in its own order, so flags and product.json reading rows keep a deterministic order.
- **understanding (skills/ultrawrite/stories/jev_checks.ts)** — The understanding stage in jev_checks.ts sends only assumptions the author made alone (by: author) to the surprise question; a choice the operator already made is never re-asked.
- **understanding (skills/ultrawrite/stories/jev_checks.ts)** — An assumption labelled technical skips the surprise question, so jev_checks.ts asks Jev whether it is really about the product; a high reading is only a flag for the author, never an operator doubt.
- **skills/ultrawrite/stories/gate_jev.ts** — skills/ultrawrite/stories/gate_jev.ts asks Jev, in one request over the gate reader's diet, whether each Machine clause states a computable fact, whether a probe would catch it false, whether a leg contradicts its cited clause, and (when base is present) whether a base file pins the opposite. The pass/fail verdict is computed from policy.json thresholds, and it is recorded beside the agent reader's verdict: Jev judges alongside and decides nothing.
- **skills/ultrawrite/stories/gate_jev.ts READING** — Which reading gate_jev.ts asks is set by policy.json gate_reading: the caught question's key and whether Jev reads base entries marked own (the task's own Modify:/Delete: files). A missing cell means the 2026-09-29 reading, and each cell reverts independently; an unknown caught key falls back to caught with one stderr line, and each recorded round names the reading asked.
- **skills/ultrawrite/stories/gate_jev.ts record** — record in skills/ultrawrite/stories/gate_jev.ts is the one writer of a task's gate verdict in gate-verdicts.json: it sets {hash, verdict, reason}, the fields plan_check.py reads, and appends the round with Jev's reading beside it, leaving every other key as it was.
- **skills/ultrawrite/stories/gate_jev.ts readings** — The gate-Jev census in skills/ultrawrite/stories/gate_jev.ts (readings) counts each reading (caught question key / own-files setting) separately, because a reworded question is a different question whose agreement cannot be pooled; a round recorded without a reading counts as caught/read.
- **skills/ultrawrite/stories/product.ts** — The product record (product.json, product-v1) holds the app's intent, what the operator said and the author assumed, the concepts a successful version needs and the build order. It lives beside the plan while a plan is authored and in the target app at stories/product.json once a plan is marked built; product.md is rendered from it in the operator's words by skills/ultrawrite/stories/product.ts and is never written by hand.
- **skills/ultrawrite/stories/product.ts renderProduct** — skills/ultrawrite/stories/product.ts renderProduct writes product.md in the operator's words with no ids, statuses, kinds or scores, because the operator adjudicates in plain language and never reads technical fields.
- **skills/ultrawrite/stories/ask.ts** — skills/ultrawrite/stories/ask.ts asks one Jev question from questions.json over state on stdin and prints {"noul": <number|null>}. A failed Jev call prints null and exits 0, so callers read no answer as an absent reading rather than a crash; only bad input (usage, unknown set or question, non-JSON stdin) exits 2.
