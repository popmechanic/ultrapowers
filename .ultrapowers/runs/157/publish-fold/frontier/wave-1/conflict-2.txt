# Ultrapowers — Report Format

The engine (`fleet/run-engine.mjs`) returns a single structured report object; `fleet/run-main.mjs` saves it bare to `<runDir>/workflow-result.json` and hands that path to `ultra_gate.py --result`, and the gate receipt is what the PR carries.

**Where the report lives:** the object below IS the file since 0.3.0. `ultra_gate.py` still accepts the pre-0.3.0 Workflow-tool envelope (`{..., result: <report>}`) for legacy bundles, so a reader of an old bundle looks under `result.*`; a reader of a live run reads the top level.

## Schema

```json
{ "type": "object",
  "required": ["integrationBranch", "waves", "tasks", "tests", "unfinished"],
  "properties": {
    "integrationBranch": { "type": "string" },
    "baseSha": { "type": "string" },
    "waves": { "type": "array", "items": { "type": "array", "items": { "type": "string" } } },
    "dependencyEdges": { "type": "array", "items": { "type": "string" } },
    "tasks": { "type": "array", "items": { "type": "object",
      "required": ["task", "status"],
      "properties": { "task": {"type":"string"}, "status": {"type":"string"}, "branch": {"type":"string"}, "headSha": {"type":"string"},
        "commit": {"type":"string"}, "reviewVerdict": {"type":"string"}, "notes": {"type":"string"},
        "actor": {"type":"string"},
        "tier": {"type":"string"}, "review": {"type":"string"}, "fixIterations": {"type":"integer"},
        "exam": {"type":["string","null"]}, "proposedPatches": {"type":"integer"},
        "proofFixes": {"type":"integer"}, "examRounds": {"type":"integer"},
        "stateExams": { "type": "array", "items": { "type": "object",
          "properties": { "exam": {"type":"string"}, "store_ms": {"type":["integer","null"]},
            "render_ms": {"type":["integer","null"]},
            "render": {"type":["string","null"], "enum":["ran","skipped",null]},
            "action_ms": {"type":["integer","null"]},
            "browser": {"type":["string","null"], "enum":["ran","skipped",null]},
            "mutant_killed": {"type":["boolean","null"]},
            "contract": {"type":["string","null"]} } } },
        "baseCorrected": { "oneOf": [{"type":"null"}, {"type":"object", "required":["from","to"], "properties": {"from":{"type":"string"}, "to":{"type":"string"}}}] } } } },
    "tests": { "type": "object", "properties": { "command": {"type":"string"}, "passed": {"type":"boolean"}, "output": {"type":"string"},
      "unattributed": { "type": "array", "items": { "type": "string" } } } },
    "integratedChecks": { "type": "array", "items": { "type": "object",
      "properties": { "cmd": {"type":"string"}, "exit": {"type":"integer"},
        "stdout": {"type":"string"}, "minor": {"type":"boolean"} } } },
    "reviewEconomy": { "type": "object", "properties": {
      "reviewerMs": {"type":"integer"}, "blockingFindings": {"type":"integer"},
      "blockingPerReviewerMinute": {"type":"number"} } },
    "baseline": { "oneOf": [{"type":"null"}, {"type":"object", "properties":
      { "passed": {"type":"boolean"}, "output": {"type":"string"} }}] },
    "waveMerges": { "type": "array", "items": { "type": "object",
      "properties": { "wave": {"type":"integer"}, "status": {"type":"string"}, "headSha": {"type":"string"},
        "detail": {"type":"string"}, "branches": {"type":"array","items":{"type":"string"}},
        "joined": {"type":"array","items":{"type":"string"}},
        "suite": {"type":"object"} } } },
    "frontier": { "type": "array", "items": { "type": "object",
      "properties": { "wave": {"type":"integer"}, "foldLogPath": {"type":"string"},
        "conflictsIndex": {"type":"string"}, "selfChecks": {"type":"string"},
        "foldCliCalls": {"type":"integer"},
        "foldCliWallTimeSec": {"type":["number","null"]},
        "resolverTranscripts": { "type": "array", "items": { "type": "object" } } } } },
    "blockedWaves": { "type": "array", "items": { "type": "object",
      "properties": { "wave": {"type":"integer"}, "detail": {"type":"string"} } } },
    "coverage": { "type": "object", "properties": {
      "tasks_merged": {"type":"integer"}, "tasks_planned": {"type":"integer"}, "complete": {"type":"boolean"} } },
    "missingDeliverables": { "type": "array", "items": { "type": "object",
      "properties": { "task": {"type":"string"}, "files": {"type":"array","items":{"type":"string"}} } } },
    "gitVerified": { "type": "boolean" },
    "deferredVerification": { "type": "array", "items": { "type": "object",
      "required": ["deliverable", "reason"],
      "properties": {
        "deliverable": { "type": "string" },
        "reason": { "type": "string", "enum": ["browser", "runtime", "external", "manual", "plan-defect"] },
        "why":  { "type": "string" } } } },
    "judgmentCalls": { "type": "array", "items": { "type": "string" } },
    "amendments": { "type": "array", "items": { "type": "object",
      "required": ["task", "amends", "what", "why"],
      "properties": {
        "task": { "type": "string" },
        "amends": { "type": "string", "enum": ["clause", "files", "sim"] },
        "what": { "type": "string" },
        "why": { "type": "string" } } } },
    "unfinished": { "type": "array", "items": { "type": "string" } },
    "completenessFindings": { "type": "array", "items": { "type": "object",
      "required": ["severity", "detail"],
      "properties": {
        "severity": { "type": "string", "enum": ["blocking", "minor"] },
        "detail": { "type": "string" } } } } } }
```

### Field reference

| Field | Required | Description |
|---|---|---|
| `integrationBranch` | yes | Branch where all task branches were merged |
| `baseSha` | no | The run base — the setup reply's head sha (agent-reported context, not authority). `finalize_report.py` reads it to refuse a merged claim whose branch carries no commits beyond the run base (#275); the git-derived ancestry checks remain the authority. Absent or unresolvable → that guard is skipped with a named warning |
| `waves` | yes | The plan's compiled layering, verbatim: an ordered list, each entry a list of task IDs. It is what the plan asked for, not the order the run took — this engine dispatches from the ready set, and what one fold adopts is an epoch numbered in fold order, so a `waveMerges[].wave` is an epoch and never an index into this array |
| `dependencyEdges` | no | Human-readable edges that shaped wave order, e.g. `"task-2 → task-4"` |
| `tasks` | yes | One entry per task; `status` is `done` or `failed`; a task that never became ready is reported as a string in `unfinished`, not as a `tasks[]` entry |
| `tasks[].branch` | no | Worktree branch used for the task |
| `tasks[].headSha` | no | The implementer's final worktree HEAD (what the merge agent merges); distinct from `commit` below |
| `tasks[].commit` | no | The implementer's final commit on the task's worktree branch (self-reported); the integration merge SHA lives in `waveMerges[].headSha` |
| `headSha` provenance | — | headSha values are derived at finalization from git ancestry by `finalize_report.py --report <file> --repo <path> --branch <integrationBranch>` (#259; `docs/superpowers/specs/2026-08-26-fold-over-git-heads.md` §3): each merged task's `headSha` is its branch tip (`git rev-parse <branch>`), asserted to be an ancestor of the integration branch tip; the final MERGED `waveMerges` entry's `headSha` is the integration branch tip itself. finalize_report.py rewrites the saved result envelope's `result.*` headSha fields in place before ultra_gate.py runs. Intermediate (non-final) `waveMerges[].headSha` values are left as model-recorded — context, not authority; no mechanical consumer reads them. The `<runDir>/heads/` sidecars no longer exist. |

| `tasks[].actor` | no | Who a failed row's question belongs to. Present only on a row the driver parked for the **plan** (#722), where it reads `plan`: the implementer reported a leg-labelled cannot-pass `plan-defect:` concern against a Proof leg whose exam the pre-review pass found red twice (pass + re-run, #944), so the driver spent no `fix:<id>:0` round and dispatched no reviewer (`reviewVerdict: 'plan-defect'`, `fixIterations: 0`, `proofFixes: 0`, `notes` = the matching concerns joined by `; `). Absent from every other row — a row without the key is a row whose findings the implementer owned. Not the same field as a reviewer issue's `actor`, which routes a finding inside a review round rather than ending the task |
| `tasks[].notes` | no | Free-form notes from the implementing or reviewing subagent (minor review findings and implementer concerns) |
| `tasks[].tier` | no | Resolved model alias the implementer ran at (`haiku`/`sonnet`/`opus`) |
| `tasks[].review` | no | Review depth applied: `lean` (one pass) or `peer` (two) — the plan's own ask, kept on the row as the run's record of it. Since #964 Task 2 the engine reads both the same way, one reviewer and one round, so `peer` (two) says what the plan asked for rather than how many referees ran |
| `tasks[].fixIterations` | no | Fix rounds a REVIEWER's findings drove. `0` on every row this engine writes: the one review round dispatches no fix worker, so a reviewer's blocking issue ends the task instead of buying a round (#964 Task 2). The key stays, and an older run's report may carry `1`. The driver's own pre-review repair round is counted by `proofFixes` below, never here |
| `tasks[].proposedPatches` | no | The number of blocking issues in the review round that carried a non-empty `proposedPatch`; `0` when none, on a clean review, and on a task that failed before any review. Since #964 Task 2 no fix worker reads those patches — they are a count of what the referee offered, and a person reads the referee's own reply for the patch itself |
| `tasks[].proofFixes` | no | Pre-review repair rounds this task consumed: `0` when the driver's own `Run:`/`Check:` pass was green the first time it ran (and on every task the run declared no commands for), `1` when a red command bought one `fix:<id>:0` round before any reviewer was dispatched. Never more than 1 — a second red pass ends the task at `proof-red`, with one exception (#908): a still-red exam beside an `exam:` concern on the `fix:<id>:0` reply goes to review round 1 with an `EXAM CONCERN:` line instead of parking, so the row keeps `proofFixes: 1` and carries a reviewed verdict (`fixIterations` is `0`, as it is on every row since #964 Task 2). Read it beside `fixIterations`, which counts only the rounds a REVIEWER's findings drove: a task can be `proofFixes: 1, fixIterations: 0` — the driver caught it, and the reviewers then found nothing |

| `tasks[].examEdited` | no | Present on every row returned after the implementer when the wave-0 examiner recorded an exam (#553): the `proofTests` paths whose blob no longer matches what the examiner left — edited by the pre-review repair round (since #653 the implementer never holds the exam while it works, and since #964 Task 2 that round is the only fix round there is) — `[]` when none moved. | `tasks[].examRounds` | no | How many exam rounds the task's examiner ran (#1037). `1` on every row of a task whose wave-0 examiner recorded an exam — `examEdited`'s presence rule, so the key is absent from a task with no examiner, one whose examiner was BLOCKED or died, and every `Run:`-only proof — and `2` when a review round's blocking finding named one of the Proof `Test:` landing paths in backticks (the token equal to the path, or the path followed by `:<digits>` or `:<digits>-<digits>`) and bought the peer who wrote the exam one round to rewrite the leg. | `tasks[].baseCorrected` | no | The #314 provisioning-drift record. `null` when the implementer's reported `startHead` (its pre-work `git rev-parse HEAD`, a required implementer-schema field) equalled the dispatched `BASE`; `{ from, to }` when it differed and the implementer reset to `BASE` (`from` = the sha the worktree was provisioned at, `to` = `BASE`); absent when no implementer reply was received (`agent-error`, infra-park). Engine-derived, never model-typed; the predicate is exact equality, not ancestry. Every correction also pushes an `autonomy` judgment call naming both shas; a reply with no `startHead` (engine-bypass class — the schema requires it) pushes a `degradation` call `BASE anchoring unverified` instead. Fix-round replies are not compared: their `BASE` is the prior implementation HEAD by design. |
| `tests` | yes | Result of the suite run on the integration branch: `{ command, passed, output, unattributed }`. `unattributed` is the run's **unattributed reds** (#871) — every test path a wave adopted red because no task of that wave named it, in wave order and once each; `[]` when there was none, on a green run, and on a run that merged nothing (the key is always present). A path is attributed when it equals an entry of some wave task's `files` or `proofTests` — string equality on the path the plan spelled, no globbing and no resolving — and a candidate takes the unattributed route only when its failing paths are non-empty and every one of them is unattributed: one attributed path, or an output that named no path at all, sends the candidate down the `reconcile:` route and on to `TEST_FAILED` as before. An unattributed candidate is adopted exactly as a green one is (same `MERGED` `waveMerges` row, whose `suite` reads `{ passed: false, unattributed, output }`), no `reconcile:` agent is dispatched at it, and each path draws one `judgmentCalls` line `unattributed red: <path> went red on wave <n>'s fold; no task names it`. The gate reads this field: a `passed: false` with a non-empty `unattributed` passes rather than blocks, and the gate receipt's `suite` carries the list |
| `integratedRuns` | no | The driver's own execution of the Proof `Run:` commands of every merged task the fold JOINED (#887), re-run on the adopted integration tree. A task is joined when its touch set (declared `files` ∪ the paths its captured patch changed) meets another merged task's, which is the only case where the fold can break a proof its own clone already passed; a single-task wave and a wave of pairwise-disjoint tasks re-run nothing. One item per executed command, `{ task, cmd, exit, stdout, joined, with }`: the task id, the command verbatim, its exit code, its combined stdout/stderr tail, the joined paths this task shares (`waveMerges[w].joined` ∩ its touch set) and the ids of the tasks it shares them with, in plan order. `[]` when no joined task declared a `Run:` proof, when the wave joined nothing and when no tree was adopted — the cases are indistinguishable here, so read it beside `waveMerges` and its `joined`. A non-zero `exit` is **reported, not gated** (#871 decision 1): the run carries one `judgmentCalls` line naming the command, the joined path and the pair it went red on, and nothing blocks — a red on the fold of two tasks is a finding about the join, not a finding against either task, so it is not a blocking one. Because the driver ran these itself, they are settled — a cannot-verify item asking for their re-execution is answered by this field, not deferred |
| `integratedChecks` | no | The driver's own execution of every Global Constraints `Check:` command on the adopted integration tree. One item per command, `{ cmd, exit, stdout, minor }`: the command verbatim, its exit code, its combined stdout/stderr tail, and whether the run declared it minor. `[]` when the run declared no checks and when no tree was adopted — the two cases are indistinguishable here, so read it beside `waveMerges`. A non-zero `exit` on a non-minor check is a blocking completeness finding (`integrated Check: <cmd> exited <n> on the adopted tree`): the constraint held in every task's own clone, where each reviewer was right about the tree it read, and the fold broke it — which is precisely what no per-task review can see. A non-zero minor check is a judgment call and nothing more |
| `reviewEconomy` | no | What a reviewer-minute bought. `reviewerMs` — the summed wall clock of every `review:` agent call. `blockingFindings` — how many blocking issues the REVIEWERS returned, de-duplicated by `severity|detail` across the run; the driver's own `Run:`/`Check:` reds are excluded, because charging the driver's findings to the reviewers flatters the ratio. `blockingPerReviewerMinute` — `blockingFindings / (reviewerMs / 60000)`, and `0` when no reviewer ran. Three keys and no others: `pairRounds` and `r2MarginalBlocking` — how many rounds dispatched a pair, and what the second reviewer returned that the first did not — were the measurement that retired the pair itself (#964 Task 2: eight marginal findings across 71 runs, n=71 runs through 2026-09-13, none of them one of the five real defects), and went with it |
| `baseline` | no | Result of the suite run on BASE's tree in a clone of its own, `<runDir>/clones/baseline` — started during **Setup**, concurrently with wave 1 but with a deliberate head start on its dispatch: the engine's `BASELINE_HEAD_START_MS` (500 ms in `fleet/run-engine.mjs`) is a bounded race, not a wait — a suite that answers red inside that window parks the run before any worker is dispatched, and one that does not is left running while wave 1 goes out and is read at the barrier. Run **exactly once per run** whatever the waves do. `{ passed, output }` on every run that completed Setup — never `null` there; `null` only on a run that never got that far. `passed: false` means BASE itself was red, and the run PARKS on it: the epoch is pushed as one `TEST_FAILED` row with a `detail` beginning `baseline: the suite is RED on BASE`, every task the red held up is named in `unfinished` as `never dispatched`, no `reconcile:` agent is ever dispatched (there is no red for one to repair that the run did not inherit), and the integration branch is left where the run found it. A red baseline also draws a `baseline:` judgment call. A green one is what makes every later candidate red attributable to the epoch that adopted it |
| `waveMerges` | no | The engine writes one row per epoch — an epoch being the set of results one fold adopts, numbered 1, 2, … in fold order — and a row's `wave` is that number, the epoch, never an index into `waves`. A fold's row carries `wave`, `status`, `headSha`, `detail`, `branches` (the task IDs submitted to that fold, listed even when it failed), `joined` (the paths this epoch's tasks met on, `[]` when they met on none) and, when the suite reported unattributed reds, `suite`. Surfaces *how* integration went, not just whether it failed; status semantics are enumerated once under **`waveMerges[].status` values** below. A red baseline on BASE is itself one row: the `TEST_FAILED` row the `baseline` field describes, carrying `wave`, `status`, `detail` and `branches` and no `headSha` (nor `joined`, nor `suite` — those three come from the fold push alone), so a run that parked on a red BASE has a row here, not nothing. The array is empty only when no fold ever ran — a run interrupted before any fold, a run whose every task failed so nothing mergeable was ever captured, or a plan whose dependency cycle let no task be dispatched — and it is never absent. Consumers — the Step-5 gate and display code — MUST degrade gracefully: check that `waveMerges` is present and non-empty and that `waveMerges[last].headSha` exists before indexing it; an empty `waveMerges`, or a last row carrying no `headSha`, is `BLOCKED` at the Step-5 gate as "merge-sha guard unavailable", never a crash. |
| `frontier` | no | One entry per epoch fold that took the **contended** merge path (frontier mode) — recorded whether the epoch adopted its folded candidate or fell back: whenever the fold CLI ran, the on-disk `frontier/wave-<n>/` directory is the durable record the production canary harvests. Absent or empty on every run whose every fold ran uncontended: `overlap=fold` has been `compile_plan.py`'s shipped default since the 2026-08-14 A/B (CLAUDE.md, "One merge, one writer"), so an empty `frontier` reads as epochs that held no intersecting `files`, not as a compile that opted out of folding. Fields, all sourced from the contended dispatches' reply scalars — no payload is relayed through an agent (#36): `wave` (the epoch number, in fold order — the same number `waveMerges[].wave` carries, never an index into `waves`); `foldLogPath` (the wave's `fold_log.jsonl`, the self-sufficient event record documented in `kernel/FOLD_LOG.md`); `conflictsIndex` (the `conflicts.json` beside it — the single record of every conflict and every park, with its `dispatchable()` verdict and reason); `selfChecks` (the fold CLI's two live self-checks, **sourced from the completing CLI reply** — the CLI runs them inside whichever call completes the wave, so a stop reply carries none; `ok`, or a named failure that routed the wave to fallback, or the empty string when no reply ever attested; the engine never claims a fold succeeded without them); `foldCliCalls` (how many fold-CLI invocations this wave drove — 1 fold + N resolves + 1 materialize on a clean run, fewer when it fell back. The incremental protocol makes N unbounded by the conflict total, because a drained stop folds on inside the same `resolve` call, so this is the wave's real CLI cost rather than a number derivable from the conflict count); `foldCliWallTimeSec` (the **sum** of the wall clocks the STEP replies reported across every leg — fold, each resolve, and materialize — reported on its own line so the first real-repo reading is not buried inside a passing test result; `null` when no reply timed its invocation); `autoResolved` (how many conflicts the kernel resolved **in process** against the wave's `Commutes:` contract — every writer declared the path and every hunk segment was an addition, so the fold never stopped on it and no resolver was dispatched. **Summed** across the fold and resolve legs, since the kernel folds on past a contract-resolved conflict inside any call; `0` when the wave declared no `Commutes:`, when no declared path conflicted, or when no reply carried the count. Read it beside `resolverTranscripts`: it is the resolver dispatches the contract *bought*); `resolverTranscripts` (one entry per resolver dispatch — `conflict` (the conflicts-index `i`), `attempt`, `path`, `epoch`, `hunksFile`, `replyDir`, `status`, `notes` — recorded verbatim as the A/B grading surface). `foldLogPath` and `conflictsIndex` are empty strings when the fold dispatch threw, returned no reply at all, or returned a reply that carried no paths — in the first two cases the directory the paths would name may never have been written, since the CLI itself may never have run. Fallback **reasons** are **not** recorded here: each one is a `judgmentCalls` entry naming its reason plus the wave's `waveMerges` result — one fact, one record |
| `blockedWaves` | no | One `{ wave, detail }` per red epoch — a fold that could not be made green, and the red-baseline park. Nothing propagates to "later waves": a red epoch marks exactly its own tasks blocked, which makes the consumers of those tasks unready (they land in `unfinished`), and every other ready task is dispatched as before |
| `coverage` | no | Structural completeness signal: `{ tasks_merged, tasks_planned, complete }`. `tasks_planned` = total tasks across all waves; `tasks_merged` = count of distinct task branches that landed via a `MERGED` wave; `complete` = `tasks_merged >= tasks_planned`. A `complete: false` with a green `tests.passed` is the false-green the gate must catch — only existing tests can fail, so a dropped/never-merged task leaves the suite green. The engine reports the *count* it can observe, and since #964 Task 2 that count is the whole signal: no agent reads the finished run, so a per-file presence check on the integrated tree is the human reader's, or a Global Constraint `Check:` the driver runs itself |
| `engineCoverage` | no | The engine's own coverage reading (#992), taken after the last fold by `fleet/engine-coverage.mjs` on a run whose adopted tree changed `fleet/run-engine.mjs` and holds at least one `fleet/tests/test_run_engine_*.mjs`; `null` on every other run, and `null` too when the diff added or modified no line (a head equal to base, a head that only deletes). Otherwise `{ file, base, head, changed, reached, unreached, sims }`: `changed` the ascending new-side line numbers of every added or modified line of `git diff -U0 <base> <head> -- <file>`; `reached` the ascending subset of them whose V8 count is above zero in at least one sim; `unreached` the rest, ascending; and `sims` one `{ sim, exit, ms, reached }` per engine sim, sorted by path, each run as `node <tree>/<sim>` with cwd the tree and a `NODE_V8_COVERAGE` directory of its own, at most the run's width at once, a non-zero `exit` recorded and its coverage read all the same. A reading beside the receipt and **never gated**: a run whose changed engine lines no sim reached ends with the `tests.passed`, `coverage.complete`, gate receipt and merge decision it would have had without it |
| `missingDeliverables` | no | One entry per `failed` task, and per task that never became ready, whose plan-declared `files` did not reach the integration branch: `{ task, files }`. Tasks with no declared file scope are omitted. The gate renders it under unfinished |
| `gitVerified` | no | Boolean: are the integration receipts intact — the integration branch tip equals the last adopt receipt's sha, and every task reported merged has a fold event in its wave's fold log (the receipt-based #70 check, surfaced as `ancestryMisses`) — on a run where at least one wave merged? Derived by the DRIVER from the repo and the fold logs (#259; `docs/superpowers/specs/2026-08-26-fold-over-git-heads.md` §2), which is the whole of it since #964 Task 2: the old meaning (a completeness critic's own `onIntegrationHead` attestation after a `git checkout --detach` and re-confirm) cannot exist when no agent reads the finished run. The model-recorded merge sha (`waveMerges[last].headSha`) is one half of the tip comparison, not authority on its own — a mismatch against the derived tip withholds the flag and pushes a checkout-drift judgment call. **Step-5 gating:** `gitVerified` MUST be true to Approve — a false value means the receipts do not line up and is treated as `BLOCKED` pending a manual integration-tree check. This is the report-driven hardening of the gate's `git rev-parse <integrationBranch>` == `waveMerges[last].headSha` check |
| `deferredVerification` | no | Deliverables present and structurally complete but whose behavior the sandbox could not execute, each tagged with a `reason` — `browser` (live UI), `runtime` (target runtime the sandbox can't run: boot, device, deploy target), `external` (unreachable service/credential/network), `manual` (human judgment: aesthetic, product-fit — a command the driver executed is never `manual` on its own, because the integrated run evidence already carries its result, and a recorded exit code is not a judgment call. When that evidence settles the deliverable's presence and only the judgment remains, the `why` quotes the settling command verbatim from the `$ <cmd>` line of the integrated run evidence, and `ackDecision` pre-authorizes the resulting `deferred:manual` ack when the quoted command is an integrated `Run:` the driver executed that exited 0; a `deferred:manual` ack whose detail quotes no green run verbatim — or quotes a red one as well — is not pre-authorized and parks for an operator, which is the safe failure for a paraphrase (#753)), `plan-defect` (a per-task reviewer returned a blocking issue whose actor is the **plan**, not the implementer: a machine clause that cannot hold, an interface the task was never given. No fix round can close it and no reviewer can wave it through, so the task merges as reviewed and the defect travels here — one item per distinct detail, on tasks whose final `status` is `done`, plus one item for each task the driver parked for the plan before any fix round (#722): the row that carries `actor: plan`, whose `why` is the implementer's own leg-naming `plan-defect:` concern verbatim rather than a reviewer's detail. A parked task is the one `failed` row that still asks the plan a question, and its files are also listed under `missingDeliverables`; `deliverable` is the task id. `ackDecision` does not pre-authorize the resulting `deferred:plan-defect` ack: an operator reads it or the run does not merge). Gating rule: a non-empty `runtime` or `external` group is a structural false-green and routes into the **same** acknowledgement disposition as `coverage.complete: false`; `browser`/`manual` remain a verify-then-approve checklist. One exception, read by `gate_check.py` before it types the ack (#863): a `browser` or `external` item whose subject is the render (its `deliverable`/`why` says so) is checked against `tasks[].stateExams` — the named task's rows, or every task's rows when it names no task id — and when there is at least one row and every row reads `render: "ran"`, the run's own record contradicts the deferral (the driver ran those exams against the live renderer during the suite), so the item is not an ack at all: it lands in the gate output's `notes` as `{ type: "satisfied-by-record", downgraded: "deferred:<reason>", detail, rows }`, naming each row, and gates nothing. A `render: "skipped"` row, a task with no record, or a deferral whose subject is not the render parks exactly as before. Since #964 Task 2 the plan defects are the whole list — the `browser`/`runtime`/`external`/`manual` reasons above are the taxonomy a reader and `gate_check.py` still apply to items carried in from another producer, but this engine emits none of its own: the critic that used to find them is gone. Empty when no task disclosed a plan defect |
| `judgmentCalls` | no | Non-obvious autonomous decisions, each one of four kinds (the kind is carried in the entry's string prefix): **autonomy** — a defensible call, FYI, asks nothing (tier-escalation recovery, fell-back-to-default review depth/tier, convergent output, worktree provisioned off BASE and reset before work (#314), a task re-edged behind a sibling still in flight and re-dispatched once that sibling was adopted (#979)); **degradation** — verify the affected slice (integration-review-deferred, agent-error, startHead not reported so BASE anchoring unverified (#314)); **disagreement** — look before approving (reviewer verdict/severity mismatch, reviewer returned no verdict, lost-coordinates, merge reported MERGED without headSha, suite-acceptance failed, disclosed plan-defect divergence (a plan-defect:-prefixed concern)); **binding** — likely a plan typo, and exactly two of them, both written before any dispatch: an edge one of whose endpoints is not a task of this run (`endpoint not in this run — unbound for dependency blocking (check for a typo)`), and a set of edges forming a dependency `cycle`, where no task can ever become ready because every one waits on a task that waits on it, so none is dispatched. New cases slot into an existing kind rather than lengthening this reference. |
| `amendments` | no | What the workers asked the PLAN for, as against what they did (#990). One object per amendment, in the order the driver collected them: `{ task, amends, what, why }` — the id of the task the worker was dispatched at, which part of that task it would have the plan change (`amends` is one of `clause`, `files` and `sim`, and no other value), the change it asks for, and the reason for asking. Present on every report, `[]` when the run collected none. Each row is also one `driver:amendment` event on the run's `events.jsonl` and on that task's hub issue, and draws one `judgmentCalls` line `task <id>: amendment (<amends>): <what> — <why>`, so a reader of the calls alone still sees it; the PR card lists the rows under `Amendments: <n> from workers`, below the residual errands and above the folded record. A note to whoever writes the next plan, and **never gated**: an amendment changes no run's verdict — for the same tree, `tests.passed`, the gate receipt, the PR's draft/ready state and the merge decision are what they would have been without it |
| `unfinished` | yes | One string per task that never became ready, each naming its reason (empty array if none). Three shapes and no others: `"<id>: never dispatched — the suite was already RED on BASE"`, for every task a red baseline held up; `"<id>: blocked — depends on a failed task"`, for a task whose predecessor's epoch went red; and `"<id>: never became ready — a task an edge names as its predecessor never landed"` for the rest — the task an edge names as its predecessor never landed at all |
| `completenessFindings` | no | Gaps the DRIVER found on the adopted tree, `{severity, detail}` each (#474). Since #964 Task 2 no agent reads the finished run, so this list is the driver's own and is `[]` on every run whose integrated `Check:`s were green — which is every run that declares no Global Constraints. The one producer left is a Global Constraint `Check:` that came back red on the adopted tree: one **`blocking`** finding per red check, quoting it. **`minor`** stays in the vocabulary for entries carried in from elsewhere but the engine emits none. The consumer is `fleet/run-main.mjs`'s `criticDecision`, **not** `gate_check.py`, which still never reads this field: a run carrying any `blocking` finding is refused by the driver before `ultra_gate.py --approve` is ever invoked. So a refused run leaves a `PASS` or `NEEDS_ACK` gate receipt beside a `critic-block.json` — the gate is honest about what *it* checked, and the blocking finding is what it does not read; the two are not in contradiction. Elements from runs before #474 are bare strings: they carry no severity, and every consumer (`criticDecision`, the driver's PR body) reads them as `minor`. |

### `waveMerges[].status` values

Three values, and the engine writes no others.

- `MERGED` — the epoch's candidate was adopted; `headSha` carries the new integration-branch HEAD, and every task of the epoch counts as landed, which is what frees the tasks waiting on them.
- `CONFLICT` — the fold could not be made whole. The integration branch is restored to the head the epoch started on, the epoch is recorded in `blockedWaves`, and exactly its own tasks are marked blocked — their consumers then never become ready and are named in `unfinished`, while every other ready task is dispatched as before.
- `TEST_FAILED` — two meanings, told apart by `detail`: **(a)** the red baseline (#862) — BASE itself was red, so the run parked with **no merge attempt** (`detail` begins `baseline: the suite is RED on BASE`, no candidate was tested and no `reconcile:` agent was dispatched; this is the row the `baseline` field describes, and it carries `wave`, `status`, `detail` and `branches` and nothing more); **(b)** the fold's candidate stayed red through the `reconcile:` rounds (`detail` begins `candidate suite failed after reconcile attempts`). Either way the integration branch is restored to the head the epoch started on and the epoch is recorded in `blockedWaves`, with the same consequence for its own tasks as `CONFLICT`.

## Presentation

When the workflow completes, the main agent renders the report as a concise human-readable summary in this order:

1. **Integration branch** — name of the branch ready for review.
2. **Plan layering and epochs** — the compiled `waves` layering the plan asked for, and beside it one line per epoch in fold order naming the task results that fold adopted. They are two different readings: the run dispatches from the ready set, so an epoch is what one fold took, not a row of the plan.
3. **Baseline** — whether the suite is green on BASE itself, read once per run in `clones/baseline` during Setup and so present on every run that completed Setup (`null` only when the run never did — nothing to render, omit the line); a red baseline reframes every later test result and is why the run parked with nothing merged.
4. **Per-task status** — a compact table or bullet list: task name, status, review verdict, and any notes; include tier, review depth, and fix iterations so the human can judge cost vs. benefit per task.
5. **Epoch folds** — one line per `waveMerges` row: the epoch, its `status`, the task IDs it folded, and the integration `headSha` (or the conflict/failure detail). Lets the human see the integration sequence, not just the final state.
6. **Blocked epochs** — any epoch whose fold did not land, with its failure detail; its own tasks, and the consumers those tasks left unready, appear under unfinished. Omit the section only when the array is empty.
7. **Test result** — pass or fail, the command run, and any relevant output excerpt. When `coverage.complete` is false, show a ⚠ "green suite but `tasks_merged`/`tasks_planned` tasks merged" beside the result: a passing suite over an incomplete merge is a false-green (only existing tests can fail), and the unmerged tasks' deliverables are itemized in `missingDeliverables` under unfinished.
8. **Judgment calls** — render entries grouped by kind, leading with `disagreement` and `binding`, then `degradation`, folding `autonomy` last, so the human can prioritize high-signal items (likely issues) before low-signal FYIs; within disagreement, cluster plan-defect: entries together so all plan divergences read as one group.
9. **Unfinished / completeness findings** — every task that never became ready, each with the reason `unfinished` gives it, plus the driver's own completeness findings (a red integrated `Check:` on the adopted tree; empty on every run that declares no Global Constraints); empty means nothing was left behind. Surface `gitVerified` here: a false value means the integration receipts do not line up — the branch tip does not equal the last adopt receipt, or a task reported merged has no fold event (#29, #70) — and the gate must treat it as `BLOCKED`.
9a. **Deferred verification — confirm before trusting green** — render `deferredVerification` grouped by `reason`, applying the taxonomy and gating rule from the field reference above: `runtime`/`external` groups require the explicit operator acknowledgement; `browser`/`manual` remain a verify-then-approve checklist; a gate-output `notes` entry of type `satisfied-by-record` is rendered beside the item it downgraded, with its rows, and asks for nothing. Omit the section when the array is empty.
10. **Post-merge runbook** — the `release`/`manual` tasks excluded at compile time,
   rendered verbatim in document order. Sourced from the compiler's
   `post_merge_runbook` (`compile_plan.py` output), **not** from the engine's report —
   the schema above is unchanged. Empty runbook means the whole plan was waveable.
   Since 0.3.0 no engine surface renders it: the orchestrator's PR body carries the
   gate receipt only, so the operator reads any `release`/`manual` tasks from the
   compiled plan. The merge-method and deploy-target checks in
   `references/finishing-notes.md` are the operator's, at the PR.

This pre-merge review is the **second and final gate** (after plan approval; the wave plan
is rendered for transparency but does not pause for approval). After the summary the session
applies the two-move rule:

- **Approve** — the two-move rule (`fleet/run-engine.mjs`'s gate phase is the executable form since 0.3.0; the fleet's launch directive is the standing instruction). `PASS` → approve. `NEEDS_ACK` → approve iff every ack is a `deferredVerification` item with reason `runtime` or `external`, or a `deferred:manual` ack whose detail quotes verbatim the command of an integrated `Run:` the driver executed that exited 0, and quotes no red one (#753 — the driver executed it, so only the judgment was ever deferred); a `deferred:manual` ack that quotes no green integrated `Run:` verbatim is not pre-authorized, and neither is `deferred:plan-defect`. Approve only after writing `run-<stamp>/standing-approval.json` (`{grantedAt, instruction, ackList}`, the launch directive verbatim as `instruction`) FIRST — the rendered gate presentation lists the same ack list and instruction, so the transcript and the disk agree. Anything else (`BLOCKED`, any other ack type, a `coverage.complete: false`) → do not approve; the gate receipt is the terminal artifact. Approve runs `python3 ${CLAUDE_PLUGIN_ROOT}/skills/ultrapowers/scripts/ultra_gate.py --approve --stamp <stamp>` (checkout of the integration branch + re-verified tests) and saves its JSON output verbatim to `run-<stamp>/approve-receipt.json`; the fleet shim's `readGateGreen` greens the run only on that receipt with a matching stamp. The orchestrator publishes the branch and opens the PR — the session never pushes and never hands off to `superpowers:finishing-a-development-branch` (superpowers does not run in a sandbox); the post-merge runbook rides in the PR body.
