| `tasks[].stateExams` | no | The task's state-exam record, read back by the driver from `<runDir>/state-exams/task-<id>/` — one element per exam stem, `[]` when the task's exam wrote nothing there (which is every task whose exam is not a state exam, and every `failed` row that never got that far; the key is present on every row either way). A stem's directories are named `<stem>-<pass>`, split at the last `-`, and the element is read from that stem's highest-numbered pass, never `base` and never any other non-numeric suffix. The exam's own pass is `0` — the pre-review pass, and the repeat that follows the pre-review repair round — so the row carries the last record the task's own tree produced. (A `2` directory is the exam-rejected round's re-execution (#1037) — the only numbered pass above `0` this engine writes, and on a task that had one the highest-numbered rule finds it rather than `0`, which is right: it is the last record the task's own tree produced. #964 Task 2 retired the round-2 re-execution that followed a review-round fix, so a `2` directory is never that any more.)  `base` is the at-BASE probe's pass, taken on a tree that predates the patch, so a stem whose only directory is `-base` contributes no element at all. Each element is `{ exam, store_ms, render_ms, render, action_ms, browser, mutant_killed, contract }`: `exam` is the stem; `store_ms` and `render` (`ran`/`skipped`) are read from that directory's `walls.json`; `render_ms` is that file's reading when `render` is `ran` and `null` when the render was skipped; `action_ms` is that file's `action_ms` — how long the exam's interaction took — when it is a number and `null` otherwise, which is both a callback exam that had no interaction to time and a pre-#834 `walls.json` that wrote no such key; `browser` is that file's `browser` — whether the exam drove a live browser — when it reads `ran` or `skipped`, and `null` otherwise, again including the pre-#834 shape; `mutant_killed` is `killed` from `mutant.json` — the driver's own proof that the exam would have caught a wrong state; `contract` is `ok` when `contract.json`'s `breach` is `null` and the breach line verbatim otherwise. Unreadable or missing JSON leaves `null` in the fields it could not supply rather than dropping the element — evidence, not control flow. When every element's `mutant_killed` is `true`, the driver also tells that task's reviewer so, as a `STATE EXAM:` block naming each exam and its mutant path: duty 5 is settled for those exam files and for nothing else. That block reaches a reviewer only when a reviewer is dispatched — with `reviewOnStateExams` off (the default) the same condition skips the review round entirely and the row reads `reviewVerdict: 'skipped-mutant-killed'`, so the block is written into a prompt only on a run that set `reviewOnStateExams: true` |
