# The compiler split: a parser the sandbox runs, beside the old compiler the laptop keeps

**Grammar:** claims-v1

**Claim:** do: launch a plan on the factory with no verdict record beside it; see: the sandbox parses it and runs, because the sandbox now reads a parser of a few hundred lines that refuses only what it cannot parse, and every judgment the old compiler made stays on the laptop, where the launch line already proves it. (elicited)
**Summary:** This is the compiler split: a small parser the sandbox runs, beside the old compiler, which stays the laptop's check and the old engine's compiler. It exists because the factory's first run died in 139 milliseconds on a rule the laptop had already enforced before the launch, and the 3,643-line compiler is 96 functions of authoring judgment the sandbox has no use for. You get a factory that cannot die on a laptop rule, a parser you can read in one sitting, and the old compiler untouched as the rollback.

**Goal:** A new `skills/ultrapowers/scripts/plan_parse.py` that turns a claims-v1 plan into the nine fields `factory/engine.mjs` reads — per task `id`, `title`, `files`, `depends_on`, `proofTests`, `testCmd`, plus `dag_edges` and `launch_waves` — and refuses only what it cannot parse: no task heading, a duplicated id, a cycle. It reads no verdict record, evaluates no stale-if, pins no base fact, checks no provenance, runs no git. `factory/engine.mjs` points at it. `skills/ultrapowers/scripts/compile_plan.py` is untouched: it stays what `--check --base` runs on the laptop before every launch and what the old engine compiles with, which is the rollback. Read at authoring (2026-09-18): run-188 died at engine start on `gate verdicts missing`, a rule `--check` had already enforced on the laptop; the factory engine executes a task's exam command only, so this plan's `Run:` lines are the reviewer's reading and the exam file of Task 1 is the one executed proof. The spec's budget for the compiler is a design note (≤ 1,200 lines, "the grammar parse; semantic checks become authoring-time questions or go"); the parser's size is a number the pull request reports, not a clause.

**Tech Stack:** Python 3 standard library only for the parser (no import from `compile_plan.py`, so the two never share a line); pytest for its exam; one constant in Node for the engine.
Spec: `docs/superpowers/specs/2026-09-17-jev-factory.md` §Components (compiler row) — laptop only; what a worker needs is in its Context.

**Parallelization rationale:** two tasks, one chain. Task 2 re-points the engine at the parser and its proof runs the parser over the fixture plan, which needs the parser's runtime behaviour, not its shape — so the compiler derives the edge from Task 2's `Run:` naming Task 1's file, and Task 2 follows.

## Global Constraints

- The parser is self-contained: `plan_parse.py` imports nothing from `compile_plan.py` or any sibling script, spawns no process, opens no file but the plan it is given, and touches no network.
- Check: git diff --quiet $ULTRA_BASE -- fleet skills/ultrapowers/scripts/compile_plan.py factory/boot.sh factory/worker.mjs factory/judge.mjs factory/tools.mjs factory/roles factory/questions.json factory/policy.json
- The freeze above is the rollback: the old compiler and the old engine stay byte-identical, and the factory's other files are not this plan's.

Every entry of `tasks`, and every entry of every wave of `launch_waves`, is an object with keys exactly `id`, `title`, `files`, `depends_on`, `proofTests`, `testCmd`, `interfaces`: `id` is the `### Task <id>:` heading's id as a string and `title` the rest of that line; `files` is the sorted union of the task's Files `Create:`, `Modify:` and `Test:` paths; `depends_on` is `[]`; `proofTests` is the Proof slot's `Test:` paths in document order; `testCmd` is the plan header's `**Exam command:**` template with `{paths}` replaced by the space-joined `proofTests` when the header carries one, else the built-in derivation — one `node <path>` per path matching `fleet/tests/test_*.mjs` joined by ` && `, then `python3 -m pytest -q <paths>` for the paths matching `tests/**/*.py`, then `bun test <paths>` for the paths matching `tests/**/*.test.ts` — and `null` when `proofTests` is empty or any path matches none of the three; `interfaces` is `{"consumes": [...], "produces": [...]}` holding each Interfaces bullet's text after its label, verbatim, as the old compiler emits it; a task whose `**Type:**` is `gate`, `release` or `manual` appears in neither list. M3. For the edge rule, a token is read off an Interfaces bullet as: the backticked span's words with any leading `def`, `function`, `class`, `const`, `let`, `var`, `export`, `async` dropped, cut at the first `(`, space or `:`; a bullet with no backticks yields its first bare word only when nothing but that word follows; `none` and `nothing` yield no token. M4. `dag_edges` is a list of `{from, to, why}` over the implementation tasks where, for each ordered pair (A, B), `why` is `write-after-create` when a `Modify:` path of B is a `Create:` path of A, `interface` when a consumes token of B equals a produces token of A, `proof-run` when a `Run:` command of B contains, as a whole token, a path in A's `files` and not in B's; an edge is added once per pair with the first label that fires in that order; a `write-after-create` edge is always added, while an `interface` or `proof-run` edge whose reverse direction is already reachable through the edges so far is not added; no other rule adds an edge. M5. `launch_waves` is the Kahn layering of the implementation tasks over `dag_edges`, every wave in document order; a plan with no `### Task <id>:` heading, a plan with the same id on two headings, and a plan whose edges form a cycle each exit 2 with exactly one line on stderr, the cycle line naming every task in the cycle. M6. For each of the three fixture plans that carry a verdict record — `evals/fixtures/claims/plan.md`, `tests/fixtures/plans/2026-09-01-511-attempt-racing.md`, `tests/fixtures/plans/2026-09-02-papercut-drain-2.md` — the parser's answer and `python3 skills/ultrapowers/scripts/compile_plan.py <plan>`'s answer agree on: the list of `id`s in `tasks`, the `id`/`title`/`files`/`depends_on`/`proofTests`/`testCmd`/`interfaces` of each task, the set of `(from, to)` pairs of `dag_edges`, and the lists of ids of each wave of `launch_waves`; and for each of the six claims-v1 plans under `tests/fixtures/plans/` that carry no verdict record, the parser exits 0 with a non-empty `launch_waves` where `compile_plan.py` exits non-zero.

**Context:** Write it from the grammar, not from the old compiler: the shape of a claims-v1 plan is `# H1`, a header block with `**Grammar:** claims-v1`, `**Claim:**`, `**Summary:**`, `**Goal:**`, optional `**Closes:**`, `**Tech Stack:**`, optional `**Exam command:**` (the value is a template carrying exactly one `{paths}`), `## Global Constraints`, then tasks. A task is `### Task <id>: <title>`, a contiguous header run of `**Type:**` and `**Review:**` lines, a `**Files:**` block of `- Create:` / `- Modify:` / `- Delete:` / `- Test:` bullets each carrying one or more backticked paths, then six `**Slot:**` blocks in order — `Claim`, `Authorized-by`, `Interfaces` (`- Consumes:` / `- Produces:` bullets), `Context`, `Proof` (`- Test:` paths, `- Run:` commands, `- Guard:` paths, `- Legs:` prose), `Stale-if`. A slot runs to the next `**Slot:**` line or the next `### `/`## ` heading; fenced code inside Proof is text, not markdown. The id is `[A-Za-z0-9]+`; `TASK_HEAD` in the old compiler is `^### Task ([A-Za-z0-9]+):\s*(.*)$` and the heading regex here matches the same strings. A `Run:` value may be wrapped in one pair of backticks; strip that pair only. The path-token rule for `proof-run` is: split the command on whitespace and on `;`, `&&`, `||`, `|`, `(`, `)`, and compare each token, with a leading `./` removed, to the sibling's `files`. Implementation tasks are those whose `**Type:**` is `implementation` or absent. The three built-in test shapes are the old compiler's `MJS_PROOF_TEST_RE` `^fleet/tests/test_[^/]*\.mjs$`, `PY_PROOF_TEST_RE` `^tests/(?:[^/]+/)*[^/]+\.py$`, `BUN_PROOF_TEST_RE` `^tests/(?:[^/]+/)*[^/]+\.test\.ts$`. `factory/engine.mjs` reads the answer with `lastJson`, the last JSON object of stdout, and reads each task's body out of the plan text itself, so the parser emits no body. The old compiler, run as `python3 skills/ultrapowers/scripts/compile_plan.py <plan>` from the repository root, is the exam's oracle on the three fixtures that carry a record and refuses the six that do not; the exam runs both as subprocesses and never imports `compile_plan`. The exam belongs to the pytest suite (`python3 -m pytest` from the root; `pytest.ini` scopes it to `tests/`), imports nothing from `fleet/`, and writes its refusal fixtures — a plan with no heading, one with `### Task 1:` twice, one with two tasks whose Interfaces consume each other's produces — under `tmp_path`.
