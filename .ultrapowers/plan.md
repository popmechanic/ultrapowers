# The Jev factory's boot: a sandbox runs the factory engine when the launch names it, and the engine writes its own record

**Grammar:** claims-v1

**Claim:** do: launch a plan with an engine sha that carries the factory; see: the sandbox boots the factory engine instead of the old one, the run's record lands on its evidence branch as the engine goes, and the pull request opens from the sandbox, while a launch naming any older sha boots exactly as it did yesterday. (elicited)
**Summary:** This is the boot for the Jev factory: the three hundred lines that let a sandbox run the new engine when a launch names it, and nothing when it does not. It exists because the engine merged inert, and a one-year inference token that serves every model call still parks every run at the old boot's credential check. You get a way to drive a real plan on the new loop by sha alone, with the old boot untouched as the rollback and the run's record written by the engine itself.

**Goal:** Map #1131's boot step (spec §Components: boot ≤ 300 lines — install, auth probe, start the unit; the engine commits its own evidence). Three files: `factory/boot.sh` (new, ≤ 300 lines: the assignment, the clone, the credential probe, the engine under its unit, evidence commits while it runs, and the publish — the integration branch, the pull request over REST, the two record tags — in the old boot's own git and curl lines), a dispatch line in `fleet/fleet-bootstrap.sh` (the one `fleet/` file that moves: it execs `factory/boot.sh` when the engine sha carries one, else `fleet/sandbox-boot.sh` exactly as today), and one sentence in `factory/roles/exam.md` so the next examiner's node exam passes the hermetic sweep. `factory/engine.mjs` is frozen: the engine's contribution to the record is the `events.jsonl` it already writes, and publish is shell, not a seam. The factory path stays opt-in by `--engine <sha>` until five green runs (CLAUDE.md doctrine); this plan flips no default. Readings cited: run-185 (n=1 run, 2026-09-18) merged the engine with every fixture task adopted through the fold and one suite red from an unguarded exam; the three sandbox probes of 2026-09-17 are dated rows on `fleet/CONTRACT.md`.

**Tech Stack:** bash for the two boot scripts (the sandbox is exe.dev's Ubuntu image with `systemd --user`, `curl`, `git`, `npm`, `node` 24, `claude`); no Node change and no new dependency. Every exam puts stub binaries on `PATH` and reads their argv; no exam touches the network.
Spec: `docs/superpowers/specs/2026-09-17-jev-factory.md` (laptop only; nothing below asks a worker to open it — what a worker needs is in its Context).

**Exam command:** node {paths}

**Parallelization rationale:** one wave, three wide. The three tasks share no file: the boot script, the bootstrap and the role file each carry their own contract. No chain: nothing here needs a sibling's runtime behaviour, and the first end-to-end drive of boot → engine → pull request is the next live launch with `--engine` at this merge, which no sandbox exam can stand in for.

## Global Constraints

- No direct Anthropic API call and no `anthropic` SDK anywhere under `factory/`: every model call is one `query()` of `@anthropic-ai/claude-agent-sdk`, which rides the edge-injected bearer. A file under `factory/` that imports `@anthropic-ai/sdk` or sets `x-api-key` is a blocking finding.
- Models never run git. Every `git`, every `curl` and every kernel invocation is the boot's or the engine's own process; no worker prompt asks for one.
- No credential is written to any file or any argv: the sandbox's bearer is injected at the edge, `CLAUDE_CODE_OAUTH_TOKEN` is the literal `placeholder`, and the boot passes no token to the engine.

### Task 1: The factory boot — three hundred lines that read the assignment, prove the credential, start the engine and publish what it left

**Type:** implementation
**Review:** peer

**Files:**
- Create: `factory/boot.sh`
- Test: `fleet/tests/test_factory_boot.mjs`

**Claim:** A sandbox handed a run reads what it was assigned, refuses a credential that is really dead without refusing one that is merely scoped for inference, starts the factory engine, keeps the run's record on its evidence branch while the engine works, and when the engine is done pushes the branch, opens the pull request and leaves the two tags that are the run's record. (derived)
Machine: M1. `factory/boot.sh boot` reads the assignment from `$FLEET_ASSIGNMENT` when set, else from the `comment` field of `GET $REFLECTION_URL/comment`, and accepts exactly the keys `run`, `plan`, `target`, `base`, `engine`, `tier`, `effort`, `hold`: any other key exits 1 with a line naming it, and a `plan`, `base` or `engine` that is not 40 lowercase hex, or a `target` that is not `owner/repo`, exits 1. M2. It clones `https://github.int.exe.xyz/<target>.git` into `$FLEET_HOME/target` and checks out `base`; it fetches `refs/heads/ultra/plan-run-<N>` and exits 1 when `FETCH_HEAD` is not `plan`; it writes the blob `<plan>:.ultrapowers/plan.md` to `$FLEET_HOME/plans/run-<N>.md`; it then runs `git -C $FLEET_HOME/target fetch origin refs/heads/ultra/evidence-run-<N>` and adds a detached worktree at `$FLEET_HOME/evidence` at `FETCH_HEAD` when that fetch succeeded, else at `plan`, writes `$FLEET_HOME/evidence/.ultrapowers/runs/<N>/status.json` with `state` `running`, commits it with subject `run-<N>: running` and pushes `HEAD:refs/heads/ultra/evidence-run-<N>`. M3. When `$FLEET_HOME/engines/<engine>/fleet/node_modules` is absent it runs `npm ci --no-audit --no-fund` in `$FLEET_HOME/engines/<engine>/fleet` when `package-lock.json` is present there, else `npm install --no-audit --no-fund`; when the directory is present it runs neither. M4. Before the engine starts, `claude auth status` (run with `ANTHROPIC_BASE_URL=$ANTHROPIC_PROXY_URL CLAUDE_CODE_OAUTH_TOKEN=placeholder`) must print `oauth_token` and must not print `api_key`, else exit 1; then exactly one `GET $ANTHROPIC_PROXY_URL/api/oauth/usage` with header `authorization: Bearer placeholder` is classified by status and body: `200` proceeds, logging `bearer probe: alive`; `401` or `403` whose body contains `oauth_scope_insufficient` proceeds, logging `bearer probe: inconclusive (scope)`; `401` or `403` whose body contains `"type":"error"` and not that token exits 1 with a line carrying the body's `message`; `403` whose body begins `integration not found` exits 1 with a line carrying the whole body; any other status or no answer proceeds, logging `bearer probe: inconclusive`. M5. It starts the engine as one `systemd-run --user --unit=fleet-engine-<N> --pipe --wait --collect -p MemoryMax=40G -p MemorySwapMax=0 -p LimitNOFILE=524288 -p WorkingDirectory=$FLEET_HOME/target -- env -u CLAUDE_CONFIG_DIR ANTHROPIC_BASE_URL=$ANTHROPIC_PROXY_URL TYPESAFE_BASE_URL=$TYPESAFE_PROXY_URL CLAUDE_CODE_OAUTH_TOKEN=placeholder ULTRAPOWERS_FLEET_RUN=run-<N> node $FLEET_HOME/engines/<engine>/factory/engine.mjs --plan $FLEET_HOME/plans/run-<N>.md --target $FLEET_HOME/target --base <base> --run-dir $FLEET_HOME/run`, appending its combined output to `$FLEET_HOME/engine.log` and writing its exit code to `$FLEET_HOME/.fleet-engine-done`; while it runs, every `$FLEET_COMMIT_SECONDS` seconds (default 60) the boot copies `$FLEET_HOME/run/events.jsonl`, when it exists and its bytes differ from the copy, to `$FLEET_HOME/evidence/.ultrapowers/runs/<N>/events.jsonl` by writing a temporary name in that directory and renaming, commits with subject `run-<N>: events` and pushes `HEAD:refs/heads/ultra/evidence-run-<N>`, and a tick with no new bytes makes no commit. M6. After the engine exits, the boot copies `events.jsonl` and `engine.log` beside `status.json` and stages exactly those three paths; then: when the exit code is not 0 and the last line of `engine.log` does not contain `"adopted"`, it writes `state` `failed` with `error` `engine exit <code>`, commits `run-<N>: failed`, pushes, and exits with that code; when `git -C $FLEET_HOME/target rev-parse HEAD` equals `base`, it writes `state` `parked` with `phase` `nothing ahead of base`, commits `run-<N>: parked`, pushes, and exits 0; otherwise it pushes `HEAD:refs/heads/ultra/integration-run-<N>` from the target, writes `state` `publishing`, commits `run-<N>: publishing` and pushes, then POSTs `https://github.int.exe.xyz/api/v3/repos/<target>/pulls` with a JSON body `{ title, head, base, body, draft }` where `title` is `fleet run-<N>: <the plan file's first line beginning "# ", without the "# ">`, `head` is `ultra/integration-run-<N>`, `base` is the name after `refs/remotes/origin/` in `git -C $FLEET_HOME/target symbolic-ref refs/remotes/origin/HEAD`, `draft` is `false` when the engine's exit code was 0 and `true` otherwise, and `body` begins with the plan's `**Summary:**` paragraph verbatim (the text after `**Summary:** ` to its blank line), then one markdown row per `landing` row of `events.jsonl` in order, `| <task> | <k> | <examExit> | <candidateSha> |`, then one `Closes #<n>` line per number on the plan's `**Closes:**` line in order; on a 2xx reply it appends `{"kind":"publish:pr","url":"<html_url>","number":<number>,"draft":<draft>}` to the evidence `events.jsonl`, writes `state` `done` (exit 0) or `parked` (otherwise) with `pr` the reply's top-level `html_url` and `prAuthor` its top-level `user.login`, commits `run-<N>: <state>`, pushes, and the boot's exit code is 0 for `done` and 0 for `parked`; on a non-2xx reply it writes `state` `failed` with `error` the first 2000 characters of the reply body, commits, pushes, and exits 1. M7. `status.json` is a JSON object whose top-level keys are exactly `run`, `state`, `phase`, `pr`, `prAuthor`, `merged`, `disclosures`, `branch`, `vm`, `startedAt`, `updatedAt`, `error`, `tasks`, with `run` the string `<N>`, `branch` `ultra/integration-run-<N>`, `vm` the `name` field of `GET $REFLECTION_URL/` or `null`, `merged` and `disclosures` `null`, `startedAt` the boot's first write in ISO 8601 UTC and `updatedAt` every write's, and `tasks` an object with one key per distinct `task` of the `landing` and `parked` rows of `events.jsonl` whose value is `{"wave":null,"state":"folded","role":null,"lastProof":null,"park":null,"attention":null,"blockedBy":null}` for a landing and the same with `state` `failed` and `park` the row's `reason` for a park. M8. After the final `status.json` commit and push of a `done` or `parked` run, the boot pushes `<plan>:refs/tags/ultra/plan/run-<N>` from the target and `HEAD:refs/tags/ultra/evidence/run-<N>` from the evidence worktree, reads `git -C $FLEET_HOME/target ls-remote --tags origin refs/tags/ultra/plan/run-<N> refs/tags/ultra/evidence/run-<N>`, and only when that listing shows both refs at those two shas runs `git -C $FLEET_HOME/target push origin --delete refs/heads/ultra/plan-run-<N> refs/heads/ultra/evidence-run-<N>`; otherwise it logs a line beginning `record:` and issues no delete; a `failed` run pushes no tag. M9. `factory/boot.sh` is 300 lines or fewer, and no line of it contains the string `/usr/bin/` or the string `/usr/local/bin/`, so every `curl`, `git`, `npm`, `claude` and `systemd-run` it runs is resolved through `PATH`.
