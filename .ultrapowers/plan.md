# Kata on the fleet hub — the compiler creates the run's tasks with their fact sheets, the engine reads them there, and the record rides the tag (#913)

**Grammar:** claims-v1

**Claim:** do: build the hub once, then launch a plan as before. see: the compiler creates the run's tasks with their fact sheets, the engine reads them there, and the record is exported to the tag. (elicited)

**Summary:** This puts a small issue tracker on a long-lived exe.dev machine and makes every fleet run write its work there. Today each task's facts — which files it owns, where its exam lands, who its neighbours are — are computed again by every piece of the engine that needs them, and two of those copies disagreeing is what parked runs 74, 77 and 101 on defects that were not defects. After this run the compiler computes each task's fact sheet once, the launcher files it on the hub as one issue per task, the engine reads it there and never recomputes it, and the operator can watch a run turn from the laptop within seconds instead of a wave behind. The janitor learns to leave the hub alone, and the doctor learns to check that it is there.

**Goal:** #913 (map #810 ticket 5, re-chartered 2026-09-11: kata is the substrate, not a build of our own), in the exe.dev shape Shelley gave on 2026-09-11 — a peer `http-proxy` integration named `kata` attached to `tag:fleet`, the sandbox URL `http://kata.int.exe.xyz`, a hub VM `kata-hub` created by plain `new` with a setup script and NO `--tag fleet`, its comment `kata hub — persistent service, do not reap`, the unit `enable --now`, kata's bearer in a root-owned EnvironmentFile, writes as plain POSTs — amended by Shelley's review of this plan (2026-09-11): `--policy 'tag:fleet'` (never `--attach`; `integrations attach` is refused), `share port kata-hub 8000`, the hub's `https_url` read from `ls --json` and never guessed, a readiness wait, 1 vCPU / 2 GB / 20 GB, an 8192-byte script ceiling, the bearer delivered over ssh after first boot so the setup script carries no secret, and no laptop token at all — the laptop reaches the daemon with `ssh <hub> curl … localhost:8000/api/v1/…`. The pre-registered readings, taken on the first run after this merges and never on this plan's own run: (1) the engine's exam handoff and fold ownership read landing and files from the sheet, never recomputed — the engine's record shows one `getIssue` per task and no `reservedExamPath` call on a task with a sheet; (2) lag — the timestamp of each `driver:*` event on the sandbox against its visibility on the laptop via `GET /api/v1/projects/<id>/events`, compared to the evidence branch's commit time, bar: median under 5 s; (3) cost — sandbox-side time spent in kata calls per task (≤ 1 % of task wall) and the hub's memory at 8 concurrent runs. What it retires if adopted (map #810 rule 5): the TinyBase tuple-space build, #879's push-to-DO shape, the janitor's git polling, #601 as its own prototype. The mechanical referee is being deleted whole by a sibling plan (operator, 2026-09-11) and nothing here touches `fleet/referee.mjs` or any referee symbol.
