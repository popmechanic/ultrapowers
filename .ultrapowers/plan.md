# A factory run finishes its own work: it merges its own green pull request, folds again when main has moved, and runs the commands a plan names as proof

**Grammar:** claims-v1

**Claim:** do: launch a plan on the factory and walk away; see: when every task was adopted and every exam ran green on the folded tree, the run merges its own pull request — folding its work onto main again first if main moved while it ran, and running its exams again there — while a run that is not green, or one I launched with --hold, leaves its pull request open for me; the commands a plan names as proof are actually run, so a clause a command decides is proven by that command and not guessed from the diff; and it works on a target that has dependencies to install. (elicited)
**Summary:** This lets a factory run finish its own work. It exists because every factory run so far was merged by hand, and branch-updated by hand whenever main had moved (runs 189 to 195, n=7 runs), and because the factory judged command-proven clauses from the diff, where true ones read 0.19 to 0.40 (runs 192 to 193, n=3 clauses). You get runs you can launch and leave, concurrent runs that do not queue behind you, and proofs that are run rather than read.

**Goal:** Step 4 of the mow sequence on map #1131 (the operator's decision of 2026-09-18): close the three measured gaps between the factory and the old engine, so cut two can follow one TinyApp run. Gap 1 — the factory opens a pull request and stops: every factory run (189–195, n=7 runs) was merged by hand, and `gh pr update-branch` was run by hand whenever main had moved. Gap 3 — the factory executes a task's exam file and nothing else: a plan's `Run:` and `Check:` lines are never run, so command-proven clauses were judged from the diff (0.19, 0.40 and 0.24 on clauses that were true, runs 192–193). Gap 2, read off the code on 2026-09-18 rather than off a run — the engine makes a fresh clone per examiner, implementer, anchor check and fold check and installs nothing in it, so a target with dependencies cannot run its exams, and a worker that installs them in its own clone would pass where the fold check's fresh clone goes red. And #1163, found on run-195: a test command joined with `&&` has only its first program run, so a run that merges itself could not trust that every exam ran. Publish stays shell (run-186 was killed on a publish stage inside the engine behind fakes): the fetch, the mergeability wait, the squash and the retry live in `factory/boot.sh`; only the re-fold is the engine's, because it is the kernel's fold and the fold check, which already live there. One switch, `policy.publish.self_merge.enabled`, is the rollback of the merge: off is today's boot; `policy.proofs.run_lines` is the rollback of the proof lines. Both are `experiment`s under the n = 5 floor. Every defect of 2026-09-18 crossed a task boundary, so each engine task's Context says what its siblings assume of the code it touches. Nothing under the old engine moves.
**Closes:** #1163

**Tech Stack:** bash for the boot, with `curl` through the GitHub edge host as `publish` already uses it; Node 24 ESM for the engine, with no new npm dependency; Python 3 standard library for the parser; the sha-pinned kernel through the engine's existing `kernel(...)` door, not edited.
Spec: `docs/superpowers/specs/2026-09-17-jev-factory.md` §The loop, and map #1131 on the target — laptop only; what a worker needs is in its Context.

## Global Constraints

- A run merges only on mechanical facts: the engine ended `done`, every exam ran green on the tree that is merged, the launch carried no hold, and the switch is on. No judgment of Jev's and no sentence of a worker's is part of that gate.
- Publish is shell: nothing in `factory/engine.mjs` talks to GitHub, pushes a branch or opens a socket to merge.
- Models never run git; the engine's own `child_process` runs every command a plan names, and a plan's `Run:` or `Check:` line runs under `timeout`.
- A failed merge, a refused re-fold and a red proof line are rows and a pull request left open — never a lost run: whatever was adopted is always pushed.

### Task 4: The engine can fold a finished run onto a main that moved, and check it there

**Type:** implementation
**Review:** peer

**Files:**
- Modify: `factory/engine.mjs`
- Test: `fleet/tests/test_factory_refold.mjs`

**Claim:** When main has moved under a finished run, the engine can be asked to put the run's whole work onto the new main through the same fold it uses for every task, run every task's exam on the result, and say plainly whether it held — so what gets merged has been checked where it will live. (derived)
Machine: M1. `node factory/engine.mjs --refold --plan <plan.md> --target <dir> --base <run base sha> --onto <tip sha> --run-dir <dir> [--exams-dir <dir>]` captures the run's whole patch as the target's `HEAD` against `--base`, folds it onto `--onto` through the kernel's `fold` and `materialize` exactly as a task's landing is folded — the union and the resolver included — resets the target to the resulting commit, and prints one JSON line `{ "refolded": true, "head": <that commit>, "onto": <tip> }` with exit 0. M2. Before it answers, it clones the new head, copies every file under `--exams-dir` into that clone at its relative path when the clone lacks it, and runs every task's exam there; a non-zero exam appends `{ kind: 'refold:red', exam, exit }`, resets the target back to the head it had, prints `{ "refolded": false, "reason": "red", … }` and exits 3. M3. A fold that does not complete after the union and one resolver pass appends `{ kind: 'refold:conflict', path }`, leaves the target at the head it had, prints `{ "refolded": false, "reason": "conflict", … }` and exits 4. M4. Without `--refold` the entry is what it was, and `--refold` dispatches no examiner and no implementer.

**Authorized-by:** the operator's signed Claim of 2026-09-18 ("folding its work onto main again first if main moved while it ran, and running its exams again there"); CLAUDE.md "One merge, one writer" (Manyana's fold is the only merge in the system)

**Interfaces:**
- Consumes: none
- Produces: `factory/engine.mjs --refold`

**Context:** `factory/engine.mjs`'s entry is `main(argv)`: it parses the arguments with `parseArgv`, requires `plan`, `target` and `runDir`, runs `runEngine(args, buildDeps(args))`, prints its answer as one JSON line and exits 0 when `done`, else 1. Inside `runEngine`, a task's landing is folded by `foldIn(landing)`, which takes `{ task, best: { patch }, anchor }`: it asks the kernel `fold` with `--base <the moving head> --patch <id>=<patch file>@<anchor>`, on an incomplete fold tries the union (`factory/union.mjs`'s `unionReply`, gated by `readUnion`) and then one resolver pass (`resolve`), asks `materialize` for the commit, and `git reset --hard`s the target onto it; `reverifyAfterFold` then runs exams in a clone of the new head. A re-fold is that same path with one landing: the patch is `git diff --binary --full-index --no-renames <base> HEAD` of the target written to a file, the anchor is `--base`, and the moving head is `--onto` — so build a second entry, `runRefold(args, deps)`, beside `runEngine`, sharing `foldIn` and the exam runner rather than copying them; the boot (a sibling task) calls it as a plain `node` process after `git fetch`ing the tip into the target, and reads its last stdout line and its exit code — exactly the three outcomes above, which it turns into a push, a pull request left open, or a retry.
