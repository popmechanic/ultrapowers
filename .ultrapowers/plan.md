# The record is the scheduler — a task starts when what it depends on is folded in, and a stuck worker re-edges instead of failing

**Grammar:** claims-v1

**Claim:** When I run a plan, a task starts the moment everything it depends on has been folded in, and never waits for the rest of its wave. (elicited)
**Summary:** This replaces the engine's wave barrier with a ready set: the driver keeps its slots full with whatever task's dependencies are already folded in, and folds whatever has landed whenever a slot frees. It exists because the barrier-slack reading on runs 91 to 115 found a finished task waits a quarter of an hour, on the median, for its wave to close. After this run a plan's clock is its longest dependency chain, not its widest wave, and a worker that finds its proof needs a sibling still in flight waits for that sibling instead of failing the run.

**Goal:** Blackboard Phase C (#979; map #810 re-charter 2026-09-13, "the width bet"), on the operator's three decisions of 2026-09-14: the driver computes readiness from its own record (the compiled edges plus what it has adopted), the hub stays the workers' channel and the mirror, never a dispatch dependency; an epoch is everything captured since the last fold, folded whenever a slot frees; `driver:wave-adopted` keeps its name with `wave` meaning the epoch, so the status page, the viewer, `evals/barrier_slack.py` and the contract's cells read unchanged. The gate is met: #832's sequential-adoption sim read green on the real-join fixtures (2026-09-13) and the barrier-slack reading was 1.14 task-minutes waiting per wall-minute against a pre-registered 0.20. Readings after this run, on #979: launch→approved on the run-67 replay against run-129's 15.3 min; `evals/barrier_slack.py` against 1.14; parks that became delays, counted. Not here: dispatch from the hub's `ready` set (a dark hub must not stall a run — #955's 25-minute 502 window), a task authored mid-run, a PR per task.
**Closes:** #979

**Tech Stack:** Node 20+ (`fleet/run-engine.mjs`, sims under `fleet/tests/` on the `_engine_helpers.mjs` rig), markdown role files. Test command: `python3 -m pytest -n auto` from the repo root (the bridge runs the sims).

**Spec:** #979's body; the 2026-09-13 re-charter on #810 (moves 3, 5, and Phase C); #832's desired state (the fold shape readiness produces); the kata REST facts measured 2026-09-14 (`ready?unowned=true` exists, `next` is CLI-only, a contended `claim` is 409 `already_claimed`, a blocked-by is filed from the blocker as a `blocks` link, a `GET` of an issue answers its `links`).

**Parallelization rationale:** one chain of two, width 1 then 1. Task 2 (the worker's re-edge) is dispatched after Task 1 (the ready-set scheduler) because its exam drives a worker that returns stuck with a new edge and asserts the task is re-dispatched *after its blocker is adopted* — that re-dispatch is Task 1's runtime behaviour, which no shared literal can promise. M3. A task lands in exactly one epoch, a red epoch marks exactly its own tasks `blocked` (`driver:wave-blocked` with that epoch's ids) and makes their consumers unready, and a task that never became ready is recorded `unfinished` with the reason (`blocked — depends on a failed task`). M4.
