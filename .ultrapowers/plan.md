# The Stale-if evaluator — the compiler reads the five predicates at BASE and refuses a task whose predicate holds

**Grammar:** claims-v1

**Claim:** A stale task should be refused or skipped with a judgment call, not built. (quoted from #538)
**Summary:** This makes the compiler read each task's Stale-if lines against the base a run launches on, so a task the world has already moved past is refused on the laptop before any sandbox is paid for. It exists because the five predicates every plan carries have been parsed and then ignored by everything since the grammar landed. After this run, launching a plan whose task is stale prints the predicate that holds and stops, and an issue predicate the laptop cannot read is printed as a note on the launch line rather than blocking the launch.

**Goal:** #538 item 2 only (the fold-log half rides #728). The five predicates are evaluated where the plan is compiled at a base — `compile_plan.py --check --base <sha|dir>` — and nowhere else: a bare `--check` and a plain compile evaluate nothing, and the engine is untouched. Choices made while the operator slept, on the quality-then-tokens-then-clock rule: (1) an issue predicate that cannot be read — no `gh` on PATH, a non-zero exit, an answer that is neither `OPEN` nor `CLOSED`, a malformed argument — is an advisory `STALE fact: … unreadable at BASE — …` line after the verdict and never a refusal, because the sandbox has no `gh` and a laptop offline should still compile; (2) the exam extends `tests/test_compile_plan_edges.py`, the one compile_plan exam under `tests/`, under a comment naming the task, rather than opening a task-named file; (3) the launcher forwards the advisory lines the same way it forwards `BASE fact:` lines — a one-line filter change and its own sim — so the note reaches the launch line; (4) `sha-matches` is read as a prefix match on the blob id so a 7-hex pin and a 40-hex pin both decide. Measured at BASE `a94143bb`: no test under `tests/` compiles with `--base` (`grep -rn -- '--base' tests/*.py` hits one docstring), so no existing pin changes; the probe fixture `evals/fixtures/claims/plan.md` carries `issue-closed: #489` and #489 is CLOSED, so `--check --base .` on it will refuse after this run — its one test (`test_probe_fixture_plan_still_checks_clean`) runs a bare `--check` and is unaffected.
**Closes:** #538

**Tech Stack:** Python 3 under `skills/ultrapowers/scripts/` (pytest under `tests/`, `pytest.ini` scopes it there); Node 22 ESM under `fleet/` (sims `fleet/tests/test_*.mjs`, each printing `ALL TESTS PASSED`, bridged by `tests/test_fleet_suite.py`, which globs the directory so a new sim rides the suite with no registration and runs under `simEnv` with `gh`/`ssh`/`curl` stubbed off PATH). Suite: `python3 -m pytest`.

**Spec:** #538 (body item 2; the 2026-09-11 re-scope comment: "Closes when the launcher's `compile_plan.py --check --base` seam … evaluates `path-exists/path-absent/sha-matches/issue-open/issue-closed` and refuses or skips a stale task").

**Parallelization rationale:** one wave, width 2. Task 1 (the evaluator in the compiler, its exam, and the authoring skill's sentence) and Task 2 (the launcher forwarding the advisory lines, its sim, and the two operator docs that describe the launch line) share no file and no symbol: Task 2 filters the compiler's stdout by a prefix string that both Contexts carry as one literal (`STALE fact:`), so it needs Task 1's shape, not its runtime, and its sim answers the compiler through the exec seam. No chain.

## Global Constraints

- The engine, the roles, the kernel and the worker are untouched: nothing at runtime re-evaluates a Stale-if predicate.
- Check: git diff --quiet $ULTRA_BASE -- fleet/run-engine.mjs fleet/run-main.mjs fleet/run-worker.mjs fleet/run-waves.mjs fleet/publish-fold.mjs fleet/sandbox-boot.sh fleet/roles skills/ultrapowers/kernel
- No test and no sim touches the network: every `gh` an exam sees is a fake on a PATH the exam built, and every compiler a sim sees is answered through the exec seam.
- The `BASE fact:` lines keep their text and their place after the verdict; a `STALE fact:` line is a new line beside them, never a rewording of one.
- Every sim keeps printing `ALL TESTS PASSED` on its last line and names no sibling sim.

### Task 1: The compiler evaluates the five predicates at BASE and refuses a task whose predicate holds

**Type:** implementation
**Review:** peer

**Files:**
- Modify: `skills/ultrapowers/scripts/compile_plan.py`
- Modify: `skills/ultrawrite/SKILL.md`
- Test: `tests/test_compile_plan_edges.py`

**Claim:** When I compile a plan at a base with `--check --base`, a task whose Stale-if predicate is already true at that base is refused, and the line I read names the task and the predicate that holds; an issue predicate the machine cannot read is a note after the verdict, not a refusal. (derived)
Machine: M1. Under `compile_plan.py --check --base <base> <plan>`, a task's `path-exists: <path>` entry holds when `<path>` is an entry of the tree at BASE — for a 40-hex `--base`, `git ls-tree <sha> -- <path>` lists it; for a directory `--base`, the path exists under that directory — and does not hold otherwise. M2. A `path-absent: <path>` entry holds exactly when the same read finds no entry. M3. A `sha-matches: <path>@<sha>` entry holds when `<path>` is a blob at BASE whose object id (the `git ls-tree` id for a sha base, `git hash-object` of the file for a directory base) begins with `<sha>`; a `<path>` absent at BASE, or an id that does not begin with `<sha>`, does not hold. M4. An `issue-open: #N` entry holds when `gh issue view N --json state -q .state`, run with the base repository as its working directory, prints `OPEN`, and an `issue-closed: #N` entry holds when it prints `CLOSED`; `gh` is run once per distinct issue number per compile, however many tasks name it. M5. Every entry that holds is one violation whose line is `STALE fact: task <id>: <entry> holds at BASE`, with `<entry>` the Stale-if line as written after its bullet, so the compile exits 2, prints those lines and prints no `PLAN OK`. M6. An issue entry `gh` cannot decide — `gh` absent from PATH, a non-zero exit, or output that is neither `OPEN` nor `CLOSED` — and a `sha-matches` or issue entry whose argument is malformed (no `@`, no digits after `#`) is not a violation: the compile prints its verdict as before and, after it, one line `STALE fact: task <id>: <entry> unreadable at BASE — <reason>` on stdout per such entry, so a plan with nothing else wrong prints `PLAN OK` and exits 0. M7. A bare `--check` without `--base`, and a plain compile with or without `--base`, evaluate no predicate: the same plan whose entry holds prints `PLAN OK` under bare `--check`, and its plain compile exits 0 with no `STALE fact:` line on either channel. M8. The `## The proof gate` section of `skills/ultrawrite/SKILL.md` says that a Stale-if predicate that holds at the base is a `STALE fact:` refusal and that an issue predicate the laptop cannot read is an advisory line.

The reader every BASE question goes through is `BaseTree` (from line 2326): `_blob_mode(path)` runs `git ls-tree <rev> -- <path>` and returns the mode of a blob entry (None for absent or a tree); `read_text` and `is_binary` read the disk for a directory base and `git show` for a sha base; `_git(repo, *args)` returns stdout or `''` on any failure and never raises; `_git_run` is the one subprocess call. `WORKTREE_REV` is the sentinel `HEAD` a directory base carries, and `_blob_mode` passes it to `ls-tree`, so for a directory base the path predicates read the disk (`(repo / path).exists()`, the way `read_text` does) and `sha-matches` hashes the file on disk with `git hash-object`; for a sha base, `git ls-tree <sha> -- <path>` gives both existence and the blob id in one read. The argument of an entry is the text after `<predicate>:`, whitespace and backticks stripped; `sha-matches` splits at the last `@`; an issue entry takes the digits after `#`.
