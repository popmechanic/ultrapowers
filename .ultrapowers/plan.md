# One fold per landing, not four

**Grammar:** claims-v1

**Claim:** When the factory lands one task, the merge step walks that task's change twice instead of four times, and the merged code it produces is exactly what it produced before. (elicited)
**Summary:** This trims the merge step the factory runs every time it lands a task, which today re-merges the same single change four times over. Two of those four passes check things that cannot go wrong when only one task is being merged, and their time sits on the clock of every landing in every run. Landings finish sooner with the same merged code; it is an experiment under the five-run floor, and turning one setting off in the factory's policy file (the single-task fast fold) brings back the old four-pass merge.

**Goal:** In `skills/ultrapowers/kernel/fold_wave.py`, when `fold` (and `resolve`'s completing call) is handed exactly one `--patch`, skip `_pre_scan` and the raw-shuffle self-check and keep the rehydrate self-check; `ULTRA_FOLD_FULL_CHECKS=1` in the kernel's environment restores the four-pass path. In `factory/policy.json` add the cell `fold.single_task_fast` (an `experiment`, rollback `enabled = false`), and have `factory/engine.mjs` run the kernel under `ULTRA_FOLD_FULL_CHECKS=1` whenever that cell is off.
**Closes:** #1278

**Tech Stack:** Python 3 (the fold kernel), Node 24 ES modules (`factory/`). The suite: `python3 -m pytest -q` from the repository root.

Spec: popmechanic/ultrapowers#1278 (kernel proposal 2 of the 2026-09-24 whole-codebase review).

## Global Constraints

- Check: git diff --quiet $ULTRA_BASE -- skills/ultrapowers/kernel/vendor/manyana.py
- A wave of two or more tasks folds exactly as it does at BASE: the pre-scan and both self-checks still run on it.
- A one-task fold that completes clean, or completes after its conflicts are resolved, ends in the same reply and the same `materialize` candidate whichever path ran.

The change: when the task list has length 1 and `ULTRA_FOLD_FULL_CHECKS` is not `1`, `cmd_fold` skips `_pre_scan`, and `_self_checks` (both in `cmd_fold` and in `cmd_resolve`'s completing call) skips the raw-shuffle leg and keeps the rehydrate leg — rehydrate is what catches a patch edited after it folded. The pre-scan's only job is to park a wave before a resolver is dispatched; with one task the incremental pass meets the same conflicts on its first and only fold, and a stop whose entries include an undispatchable one must still answer with no dispatchable `open` entry, so the engine parks the fold without paying a resolver for a fold that cannot complete — the same outcome the pre-scan's park reply gave it. Update the module docstring's "`fold` runs twice over the wave" paragraph to say the pre-scan and the shuffle leg run only for a wave of two or more tasks, or under `ULTRA_FOLD_FULL_CHECKS=1`. Never edit `skills/ultrapowers/kernel/vendor/manyana.py`. `tests/test_fold_wave_anchor.py` drives this CLI over two-task and one-task waves and must stay green. The engine side (a `factory/policy.json` cell that sets this variable when switched off) is a sibling task; this task only reads the variable.
