# The board reader starts at the run issue: a run in flight prints its rows, and `cursor` is the feed's true last id

**Grammar:** claims-v1

**Claim:** A run in flight prints its rows; `cursor` is the feed's true last id. (quoted from #1227)
**Summary:** The board reader is the laptop's window onto a run while it is in flight, and today it stops thousands of events short of any live run and prints nothing. This plan makes it start from the run's own creation event so it reads only that run. You will be able to watch a run's tasks and timeline from the laptop again instead of reading the hub feed by hand.

**Goal:** #1227 (map #876, on #1174): `readBoard` in `fleet/board-read.mjs` locates the asked run's own `issue.created` event on the hub's feed and pages `after_id` from there to the feed's end, so a live run's rows are printed and `cursor` is the feed's last `event_id`; the reader's own exam pins it over a hub-shaped fixture feed.
**Closes:** #1227

**Tech Stack:** Node 24 ESM; no new npm dependency.
**Exam command:** node {paths}
**Spec:** none on disk — issue #1227 is the brief (map #876, on #1174), and everything a worker needs is in its own Context. The sandbox holds no spec.
