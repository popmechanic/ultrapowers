# A relaunch reuses the tasks a parked run already finished — stamped on the hub at close, folded in from the evidence tag at setup

**Grammar:** claims-v1

**Claim:** When I relaunch a parked plan, the tasks that already finished are folded in from the parked run's record and only the unfinished ones are worked, and the run's gate still runs on the whole tree. (elicited)
**Summary:** This teaches the engine to start a relaunch from what a parked run already got right, instead of doing every task again. It exists because the record of this month prices a park at the whole plan, and the reading on the run-98 to run-99 pair shows a re-drive pays a finished task's full cost a second time. After this run, relaunching a parked plan works only the tasks that did not finish, and the suite and gate still judge the whole tree before anything merges.

**Goal:** #383 in its 2026-09-11 narrowing — "done on a prior run" is a hub read — built the way the operator chose on 2026-09-14: the engine stamps each issue it closes `done` with its run number and adopted sha (Task 1), and at setup a run whose issues are already closed `done` fetches that run's evidence tag and folds its `publish-fold/run.patch` onto BASE through the kernel as a reuse wave, dispatching no workers for those tasks (Task 2). No launcher, boot or lobby change: Phase B (#978, run-131) already makes a relaunch of the same plan resume the same issues. The pre-registered reading (#383): the run-98 task-2 slice was 3 workers and $6.96; its re-drive as run-99 was 3 workers, $6.71 and 21.5 min of wall against 37.1 — a re-drive repays a task in full, and a whole-plan relaunch repays the finished one ($4.50 for run-98's task 1) as well.
**Closes:** #383

**Tech Stack:** Node 20+ (`fleet/run-engine.mjs`, sims under `fleet/tests/` on the `_engine_helpers.mjs` rig), the Python kernel `skills/ultrapowers/kernel/fold_wave.py` (unchanged, driven by the engine). Test command: `python3 -m pytest -n auto` from the repo root (the bridge runs the sims).

**Spec:** #383 (body and the 2026-09-11 comment); the 2026-09-14 comment on #978 for the hub facts; `fleet/CONTRACT.md` §Kata record (engine) for what the engine writes today.

**Parallelization rationale:** one wave, width 2. Task 1 is the close-time stamp; Task 2 is the setup-time reuse. Task 2's exam seeds the stamp on its fake hub itself, so it needs Task 1's shape (a shared literal, in both Contexts) and never its runtime. Both edit `fleet/run-engine.mjs` in different regions and both add the same one-line `kata` passthrough to the rig, which folds as one edit; both edit `fleet/CONTRACT.md`'s kata bullet in different sentences.

### Task 1: The engine stamps an issue with the run and sha that adopted it, before it closes it

**Type:** implementation

**Files:**

**Claim:** After this run, every task the engine closes as done carries on its issue which run adopted it and at which commit, so a later run can read that without opening the run's record. (derived)
Machine: M1. For each task a wave adopts, before that task's `close`, the engine patches the issue's metadata with exactly the two flat keys `work.adopted_run` (the run's number as an integer, parsed from the run stamp `run-<N>`) and `work.adopted_sha` (the wave's adopted head, 40 hex), under the revision the engine last held for that issue, and the `close` that follows carries the same sha in its `commit` evidence. M2. A task the engine does not close — one marked `needs-review` — gets no `work.adopted_run` and no `work.adopted_sha`. M3. A run with no hub record makes no metadata call at all: with `kata` absent the engine's hub calls are exactly what they were at BASE, none. M4. `fleet/CONTRACT.md`'s Kata record (engine) bullet says, in its Closes sentence, that the close is preceded by a metadata patch of `work.adopted_run` and `work.adopted_sha`.

**Authorized-by:** #383 (2026-09-11: "'done on a prior run' becomes a fact-sheet read (`closed: merged, sha`)"); operator decision 2026-09-14 (the hub, automatically); measured 2026-09-14 on kata v0.17.2: a closed issue keeps `evidence: null` on itself (evidence lives only in its close event), so the sha a later run needs must be on the issue's metadata.

### Task 2: A run whose issues are already closed done folds that run's work in at setup and works only the rest

**Type:** implementation
**Review:** peer

**Files:**

- Modify: `fleet/CONTRACT.md`

**Claim:** When I relaunch a parked plan, the tasks that already finished are folded in from the parked run's record and only the unfinished ones are worked, and the run's gate still runs on the whole tree. (derived)
Machine: M1. At setup, with a hub record, the engine reads every task's issue once (the same read that checks its revision and takes its fact sheet, moved ahead of wave 1) and takes as *reused* the set of tasks whose issue's `status` is `closed` and whose metadata carries both `work.adopted_run` and `work.adopted_sha` (the two keys only a `done` close writes); when that set is empty the run proceeds exactly as at BASE and fetches nothing. M2. When the set is non-empty and every member names one run M, the engine fetches the tag `ultra/evidence/run-<M>` from `origin` into the integration clone, reads `.ultrapowers/runs/<M>/report.json` and `.ultrapowers/runs/<M>/publish-fold/run.patch` off that tag, and folds through the kernel — the publish fold's shape: `--base <report.baseSha>` with `main=` the diff from that base to this run's BASE and `reuse=` that `run.patch`, then `materialize` — so that the integration head before wave 1 is BASE plus the parked run's adopted work; that head is the base every wave-1 task clone starts from; and one event `driver:reuse` `{run: M, tasks: [<reused ids>], headSha}` is appended. M3. A reused task dispatches no worker (no `exam:<id>`, `impl:<id>`, `review:<id>:*` or `fix:<id>:*` label appears), is not claimed, is not closed and is not marked `needs-review`, is excluded from its wave's fold, and appears in the report's `tasks` as `status: 'done'`, `reviewVerdict: 'reused'`, `headSha` the reuse head; a wave whose tasks are all reused adopts nothing and the next wave starts from the reuse head. M4. Reuse is refused, with one `driver:reuse` event carrying `reason` and an empty `tasks`, and the full plan then runs as at BASE, when any of these holds: the reused tasks name two different runs; the tag cannot be fetched; the tag's `report.json` does not list every reused task with `status` `done`; `report.baseSha` is not an ancestor of BASE. M5. When BASE has moved past the parked run's base — a commit on main touching another file — the reuse head carries both that commit's change and the parked run's work, and the suite and gate run on that whole tree exactly as they do on any wave's. M6. `fleet/CONTRACT.md`'s Kata record (engine) bullet carries, in this order, the words `once, at setup`, `closed`, `work.adopted_run`, `ultra/evidence/run-<M>`, `run.patch`, `driver:reuse` and `refus`.

**Authorized-by:** #383 (the prototype's three steps: verify, seed, run the rest with the gate as normal; 2026-09-11: the input is the tag `ultra/evidence/run-<N>`); the #810 comment of 2026-09-14 ("#383 (re-drive reuse) is the half-step"); operator decisions 2026-09-14 (the hub automatically; the Claim above).
