# The factory uses the full width of its fold: Jev reads every pair, every task starts at once, and every fold is checked by the exams it touched

**Grammar:** claims-v1

**Claim:** do: hand the factory a plan whose tasks share files and build on each other; see: every task starts at once, nobody has written an ordering, Jev says for each pair whether it folds or has to wait and says it again as the real code appears, two edits that only add beside each other are kept without a resolver, and after every fold the exams of the tasks it touched are run on the folded tree — so a wrong call shows as a red exam and one more attempt, never as a silent break. (elicited)
**Summary:** This makes the factory use the full width of its own fold: ordering stops being something an author guesses and becomes something Jev reads and the exams check. It exists because run-193 lost about nine minutes to an ordering its author added out of caution, because every examiner waits today on work it never needed, and because no fold has ever been checked after the fact (run-193, n=1 run, 7 tasks). You get runs as long as their longest task instead of their longest chain, plans with no ordering to write or review, and folds that are verified for the first time — as five experiments, each with a one-switch rollback, measured on their first run.

**Goal:** The operator's call of 2026-09-18 (Draft A, "everything starts at once", over a draft in which ambiguous pairs wait): one build-out, no probe, rollback by switch. Five switches in `factory/policy.json`, each an `experiment` under the n = 5 floor with its rollback named — `pairs.mode` (`live` → `off`), `speculate.exam_at_zero`, `speculate.on_candidate`, `resolve.union.mode` (`live` → `record-only`) and `fold.reverify.enabled` — and all five off is the engine exactly as run-193 left it. The parser keeps printing every edge with its `why`; with `pairs.mode` live the engine keeps only the `write-after-create` edges, which are facts, and takes every other ordering from Jev's reading of the pair (`fold`, `look`, `chain`), read again when the producer's candidate exists. What makes that safe is the one thing the factory has never done: after each fold, the exams of the tasks that fold touched are run on the folded tree, so a wrong reading is a red exam, a `[fold-red]` fact and one more attempt. Every pair leaves a row with Jev's verdict beside two mechanical labels, so the thresholds are re-read from the record (the floor for that reading is 20 pairs). Readings cited: run-193 (n=1 run, 7 tasks, 2026-09-18: 54 min 31 s wall, task 7 dispatched 17 min late behind an author-made edge); the 8-wide drain of 2026-09-08 (n=4 same-file pairs, 8 runs: all folded with zero conflicts); the resolver's whole record (n=10 dispatches, runs 36, 44 and 183). This plan carries no author-made ordering of its own beyond one write-after-create fact: three of its tasks edit `factory/engine.mjs` at once and fold. Nothing under the old engine moves, and the sha-pinned kernel is not touched.

**Tech Stack:** Node 24 ESM for the pair builder, the schedule, the fold check, the union and the engine, with no new npm dependency; Python 3 standard library for the parser; `fleet/jev-client.mjs` consumed as-is through `factory/judge.mjs` (Jev 1.13: 64k tokens per request, 32k for state plus the longest question; the client refuses a state over 120,000 bytes before any call).
Spec: `docs/superpowers/specs/2026-09-17-jev-factory.md` §The loop, and map #1131 on the target — laptop only; what a worker needs is in its Context.

**Parallelization rationale:** wave 1 is seven wide — the parser, the pair builder, the pair readers, the schedule with its engine wiring, the fold check, the union and the authoring text. Three of them edit `factory/engine.mjs` concurrently, each in its own region behind its own new module, and fold; the shapes they share are literals in every Context that needs them, and the engine reaches each new module through `deps` or a guarded dynamic import, so no task's exam needs a sibling's file. Wave 2 is one task, starting from a producer's candidate, and it waits on a fact, not on a judgment: it modifies `factory/dispatch.mjs`, which the schedule task creates.

## Global Constraints

- A pair reading is never the run's failure: a Jev that does not answer reads as `look`, a pair builder that throws is one log line and a run with the edges the parser printed, and a fold check that cannot run a test is one row.
- Nothing runs the whole test collection: the fold check runs the exam commands of the adopted tasks a fold touched, at most `policy.fold.reverify.max_run` of them, each under `timeout`.
- Models never run git and never decide an ordering: candidates and hit lists come from code, the verdict from Jev, and the engine's own `child_process` applies it.
- A judgment is a question in `factory/questions.json` read through `factory/judge.mjs` with its threshold in `factory/policy.json`, carrying `n`, `window`, `experiment` and `rollback`; no threshold is a literal in code.
- Check: git diff --quiet $ULTRA_BASE -- ':(glob)fleet/run-*.mjs' fleet/sandbox-boot.sh fleet/fleet-bootstrap.sh fleet/roles fleet/kata-client.mjs fleet/launch.mjs skills/ultrapowers/kernel skills/ultrapowers/scripts/compile_plan.py

### Task 2: The pair builder — code assembles what Jev is shown about a pair, and decides alone when it can

**Type:** implementation
**Review:** peer

**Claim:** For each pair of tasks that could meet, code builds the small picture a judge needs — the two tasks, the outline of each file they share, and which parts of it each task names — decides by itself when the two plainly edit different parts, and afterwards labels the pair with what actually happened. (derived)
Machine: M1. `outlineOf(text, path)` answers the file's top-level constructs in order as `[{ name, kind }]`: for a path ending `.mjs`, `.js` or `.ts`, one entry per line matching `export function|const|class <name>`, `function <name>` or `const <name> =` at column 0 or indented exactly two spaces (`kind` `code`); for `.py`, per `def <name>` or `class <name>` at column 0 (`code`); for `.md`, per heading line, `name` the heading text without its `#` marks (`heading`); for `.json`, per top-level key (`key`); anything else `[]`; at most 200 entries. M2. `pairState({ pair, tasks, read })` resolves `{ producer, consumer, shared, shape }`: `producer` and `consumer` are `{ id, title, claim, machine, interfaces, files, context, legs }` read from the two tasks' bodies (`legs` only on the consumer; for a files-only pair the producer is `pair.a`), `shared` is one `{ path, exists_at_base, outline, producer_hits, consumer_hits }` per `pair.paths` entry where a task's hits are the outline names that occur as whole words inside any backticked span of that task's body, and `shape` is `{ symbol, stated_in_consumer }`, true when the consumer's body contains the producer's full `Produces:` bullet text for `pair.symbol`; the serialized state is at most 60,000 bytes, outlines cut from the end first. M3. `decideByCode(state)` answers `'fold'` when the pair has at least one shared path, no `symbol`, and for every shared path both hit lists are non-empty and disjoint; otherwise `null`. - Produces: `labelPair({ pair, tasks, read, folds }) -> { a, b, calls, fold }`

### Task 4: Every task starts at once — the engine takes its ordering from the pair readings, and every examiner goes at minute zero

**Type:** implementation
**Review:** peer

**Files:**
- Create: `factory/dispatch.mjs`
- Modify: `factory/engine.mjs`
- Test: `fleet/tests/test_factory_dispatch.mjs`

**Claim:** With the switch on, no task waits on an ordering someone wrote: every examiner starts when the run starts, an implementer waits only on a fact or on a pair Jev read as a chain, each reading is on the record with what later happened to the pair, and with the switch off the engine orders its work as it did before. (derived)
Machine: M1. `waitsFor({ taskId, hardPreds, chainPreds, policy })`, exported by `factory/dispatch.mjs`, answers `{ adoption, candidate }`: `adoption` is `hardPreds` followed by `chainPreds`, deduplicated, and `candidate` is `[]`. M2. With `policy.pairs.mode` `live`, the engine builds each task's hard predecessors from its `depends_on` and the parser's `write-after-create` edges only; for every entry of the parser's `pairs` it builds the pair's state with `pairState`, takes `decideByCode`'s answer when there is one and `readPair`'s otherwise, appends `{ kind: 'pair', a, b, why, verdict, by, score }` to `events.jsonl` with `by` `code` or `jev`, and treats only a `chain` verdict as an ordering — from `pair.producer` to `pair.consumer`, or from `a` to `b` for a files-only pair; an ordering that would close a cycle is dropped with a `{ kind: 'pair:cycle', a, b }` row. M3. With `policy.speculate.exam_at_zero` true, every task's exam worker is dispatched before any implementer and without waiting on any predecessor, in a clone of the run's base; a task's implementers start when every id in its `waitsFor(...).adoption` is adopted, in a clone of the head at that moment, with the exam files copied in. M4. When a producer's best candidate is first measured and a consumer of a pair with it has already been dispatched, the engine asks `readPairCandidate` once with `hunks` `hunksCarrying(<the producer's patch>, [pair.symbol], 8000)` and the consumer's state, appends `{ kind: 'pair:candidate', a, b, changes, score }`, and when `changes` is true posts `board.post(<consumer>, 'pair', <text naming the producer and the symbol>)`. M5. When the run ends the engine appends one `{ kind: 'pair:label', a, b, calls, fold }` row per pair from `labelPair`, `fold` being what the later task's fold did: `clean`, `resolved`, `union` or `parked`. M6. With `pairs.mode` not `live` the engine honours every edge the parser printed, appends no row whose kind begins `pair`, and asks neither pair reader; with `speculate.exam_at_zero` false a task's exam worker is dispatched only when its implementers may start.

**Authorized-by:** the operator's signed Claim of 2026-09-18 (Draft A: "every task starts at once"); map #1131; spec §The loop ("fold on every adoption; no epoch, no barrier")

**Interfaces:**
- Consumes: none
- Produces: `waitsFor({ taskId, hardPreds, chainPreds, policy }) -> { adoption, candidate }`
- Produces: `runEngine(args, deps) -> Promise<{ done, adopted, head, wall_ms, cost_usd }>`

**Context:** `factory/engine.mjs` today: `runEngine` parses the plan with `plan_parse.py` (its answer now carries `pairs`: `[{ a, b, why, paths, symbol, producer, consumer }]`, and `dag_edges` with `why` one of `write-after-create`, `interface`, `proof-run`), builds `edgePreds` from `depends_on` and every edge, and runs a pool: `settleReadiness` launches `land(task, anchor)` for each task whose predecessors are all done, and the `while` loop folds each landing as it settles. `land` is one function that does everything in order — the task reading, the covering selection, the exam worker, `k` implementers, measurement, selection, the landing run set, the one re-dispatch, the referee, the fix. This task splits the front of `land` off: an `examine(task)` that runs at minute zero at the run's base and resolves the exam files and the covering list, and the rest, which starts when `waitsFor` says so and awaits that task's `examine` promise. Keep `land`'s later steps and the loop's adoption bookkeeping where they are: two sibling tasks add one call each near them — one directly after a task is adopted, one at the top of `resolve` — and edits kept narrow fold cleanly. The pure ordering rule lives in the new `factory/dispatch.mjs` so a sibling can extend it; `candidate` is always `[]` here and is that sibling's to fill.
