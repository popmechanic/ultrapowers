# A fold red names the fold that caused it, an exam broken by a sibling's added field goes back to its examiner, and the repair goes to the exam's owner

**Grammar:** claims-v1

**Claim:** A `fold:red` row names the fold that turned the exam red — the exam was green at the head before it — and whose subject the exam is. When the red exam belongs to a task OTHER than the one that folded, and its failure is an equality over a structure the folding task legitimately extended, the engine asks Jev one question over the two facts (the failing assertion's text, the folding patch's hunks): is this exam asserting an exact shape that a sibling's added field breaks? Above the threshold the row is `fold:exam-defect`, the exam's owner is re-dispatched as an EXAMINER with that fact in the hand-off, and the run is not failed by it. Otherwise the re-attempt goes to whichever task owns the code the assertion names. (quoted from #1164)
**Summary:** This changes what a run does when a fold inside it turns an already-passing exam red: the record now names the fold that did it and whose exam it is, and the repair goes to the owner of that exam instead of to whoever folded last. It exists because the one true red of this kind went to a worker who owned neither the exam nor the code it measures and was repaired by hand (n=1 run, run-196, 2026-09-18), and because two over-strict exams on sound work would have ended a run as failed (n=2 exams on 1 run, run-195, 2026-09-18). It lets a run finish green when the only thing wrong is an exam pinning an exact shape a sibling lawfully extended, and plans stop writing such exams in the first place; it ships as an experiment, and its rollback is one switch in the policy file that sends the repair back to the task that folded, as today.

**Goal:** #1164: the fold check's reds go through one pure round in `factory/reverify.mjs` — attribution (which fold, whose exam, green before or not), one Jev question `fold_red.exact_shape_broken` behind `readFoldRed`, a `fold:exam-defect` row and an examiner re-dispatch above `policy.fold.attribution.t_exam_defect`, otherwise an implementer re-attempt for the exam's own task — and ultrawrite's gate question refuses a leg pinning exactly these keys on a shared record. "The code the assertion names" is read as the red exam's own subject, its task (the issue's run-196 comment: "whoever owns the subject of the red exam"). The pre-registered readings — `fold:red` rows by `cause`, and how many re-attempts changed the exam's result — are read off the rows this plan writes (`cause`, and `fold:verify` attempt 1 against attempt 2); no census script is added.
**Closes:** #1164

**Tech Stack:** Node 24 ESM for the factory and its exams, no new npm dependency; markdown for the authoring half.
Spec: none on disk — issue #1164 and its comment of 2026-09-18 are the brief, and everything a worker needs is in its Context. The sandbox holds no spec.
