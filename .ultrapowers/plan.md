# The Jev factory's boot: a sandbox runs the factory engine when the launch names it, and the engine writes its own record

**Grammar:** claims-v1

**Claim:** do: launch a plan with an engine sha that carries the factory; see: the sandbox boots the factory engine instead of the old one, the run's record lands on its evidence branch as the engine goes, and the pull request opens from the sandbox, while a launch naming any older sha boots exactly as it did yesterday. (elicited)
**Summary:** This is the boot for the Jev factory: the three hundred lines that let a sandbox run the new engine when a launch names it, and nothing when it does not. It exists because the engine merged inert, and a one-year inference token that serves every model call still parks every run at the old boot's credential check. You get a way to drive a real plan on the new loop by sha alone, with the old boot untouched as the rollback and the run's record written by the engine itself.

**Goal:** Map #1131's boot step (spec §Components: boot ≤ 300 lines — install, auth probe, start the unit; the engine commits its own evidence). Four files: `factory/boot.sh` (new, ≤ 300 lines), a dispatch line in `fleet/fleet-bootstrap.sh` (the one `fleet/` file that moves: it execs `factory/boot.sh` when the engine sha carries one, else `fleet/sandbox-boot.sh` exactly as today), a publish stage in `factory/engine.mjs` (evidence commits on every landing, the integration branch, the pull request over REST, the two record tags — all opt-in by `--run`, so the fixture drive is unchanged), and one sentence in `factory/roles/exam.md` so the next examiner's node exam passes the hermetic sweep. The factory path stays opt-in by `--engine <sha>` until five green runs (CLAUDE.md doctrine); this plan flips no default. Readings cited: run-185 (n=1 run, 2026-09-18) merged the engine with every fixture task adopted through the fold and one suite red from an unguarded exam; the three sandbox probes of 2026-09-17 are dated rows on `fleet/CONTRACT.md`.

**Tech Stack:** bash for the two boot scripts (the sandbox is exe.dev's Ubuntu image with `systemd --user`, `curl`, `git`, `npm`, `node` 24, `claude`); Node 24 ESM for `factory/engine.mjs` with no new dependency; the engine's `git` and `sh` seams (`deps.git`, `deps.sh`) plus one new `deps.fetch` for REST, so every exam drives fakes and no exam touches the network.
Spec: `docs/superpowers/specs/2026-09-17-jev-factory.md` (laptop only; nothing below asks a worker to open it — what a worker needs is in its Context).

**Exam command:** node {paths}

**Parallelization rationale:** one wave, four wide. The four tasks share no file: the boot script, the bootstrap, the engine and the role file each carry their own contract, and the one shape two of them share — the engine's command line as the boot assembles it — is stated as a single literal in both Contexts, so neither waits on the other. No chain: nothing here needs a sibling's runtime behaviour, and the first end-to-end drive of boot → engine → pull request is the next live launch with `--engine` at this merge, which no sandbox exam can stand in for.

## Global Constraints

- No direct Anthropic API call and no `anthropic` SDK anywhere under `factory/`: every model call is one `query()` of `@anthropic-ai/claude-agent-sdk`, which rides the edge-injected bearer. A file under `factory/` that imports `@anthropic-ai/sdk` or sets `x-api-key` is a blocking finding.
- Models never run git. Every `git`, every `curl` and every kernel invocation is the boot's or the engine's own process; no worker prompt asks for one.
- No credential is written to any file or any argv: the sandbox's bearer is injected at the edge, `CLAUDE_CODE_OAUTH_TOKEN` is the literal `placeholder`, and the boot passes no token to the engine.

- Check: git diff --quiet $ULTRA_BASE -- factory/worker.mjs factory/judge.mjs factory/tools.mjs factory/questions.json factory/policy.json factory/proto factory/replay skills/ultrapowers/kernel
- The `fleet/` freeze above names the old engine's own shapes — its modules, its boot and helper scripts, unit, documents and role files — and deliberately not `fleet/fleet-bootstrap.sh` (Task 2's dispatch line) nor `fleet/tests/exams/` (the driver's exam handoff stages it in every clone). The old boot path is the rollback and stays byte-identical.
- A role file states what to produce and what to look for, never how a finding is graded: the words `blocking`, `minor`, `severity` and `verdict` do not appear in `factory/roles/exam.md` (minor).

### Task 1: The factory boot — three hundred lines that read the assignment, prove the credential and start the engine

**Type:** implementation
**Review:** peer

**Files:**
- Create: `factory/boot.sh`
- Test: `fleet/tests/test_factory_boot.mjs`

**Claim:** A sandbox handed a run reads what it was assigned, refuses a credential that is really dead without refusing one that is merely scoped for inference, and starts the factory engine with everything it needs on its command line. (derived)
Machine: M1. `factory/boot.sh boot` reads the assignment from `$FLEET_ASSIGNMENT` when set, else from the `comment` field of `GET $REFLECTION_URL/comment`, and accepts exactly the keys `run`, `plan`, `target`, `base`, `engine`, `tier`, `effort`, `hold`: any other key exits 1 with a line naming it, and a `plan`, `base` or `engine` that is not 40 lowercase hex, or a `target` that is not `owner/repo`, exits 1. M2. It clones `https://github.int.exe.xyz/<target>.git` into `$FLEET_HOME/target` and checks out `base`; it fetches `refs/heads/ultra/plan-run-<N>` and exits 1 when `FETCH_HEAD` is not `plan`; it writes the blob `<plan>:.ultrapowers/plan.md` to `$FLEET_HOME/plans/run-<N>.md`. M3. When `$FLEET_HOME/engines/<engine>/fleet/node_modules` is absent it runs `npm ci --no-audit --no-fund` in `$FLEET_HOME/engines/<engine>/fleet` when `package-lock.json` is present there, else `npm install --no-audit --no-fund`; when the directory is present it runs neither. M4. Before the engine starts, `claude auth status` (run with `ANTHROPIC_BASE_URL=$ANTHROPIC_PROXY_URL CLAUDE_CODE_OAUTH_TOKEN=placeholder`) must print `oauth_token` and must not print `api_key`, else exit 1; then exactly one `GET $ANTHROPIC_PROXY_URL/api/oauth/usage` with header `authorization: Bearer placeholder` is classified by status and body: `200` proceeds, logging `bearer probe: alive`; `401` or `403` whose body contains `oauth_scope_insufficient` proceeds, logging `bearer probe: inconclusive (scope)`; `401` or `403` whose body contains `"type":"error"` and not that token exits 1 with a line carrying the body's `message`; `403` whose body begins `integration not found` exits 1 with a line carrying the whole body; any other status or no answer proceeds, logging `bearer probe: inconclusive`. M5. It starts the engine as one `systemd-run --user --unit=fleet-engine-<N> --pipe --wait --collect -p MemoryMax=40G -p MemorySwapMax=0 -p LimitNOFILE=524288 -p WorkingDirectory=$FLEET_HOME/target -- env -u CLAUDE_CONFIG_DIR ANTHROPIC_BASE_URL=$ANTHROPIC_PROXY_URL TYPESAFE_BASE_URL=$TYPESAFE_PROXY_URL CLAUDE_CODE_OAUTH_TOKEN=placeholder ULTRAPOWERS_FLEET_RUN=run-<N> node $FLEET_HOME/engines/<engine>/factory/engine.mjs --plan $FLEET_HOME/plans/run-<N>.md --target $FLEET_HOME/target --base <base> --run-dir $FLEET_HOME/run --run <N> --repo <target> --plan-sha <plan> --evidence-dir $FLEET_HOME/evidence --vm <name>` where `<name>` is the `name` field of `GET $REFLECTION_URL/` or empty; it writes the engine's exit code to `$FLEET_HOME/.fleet-engine-done` and exits with that code; the engine's combined output is appended to `$FLEET_HOME/engine.log`. M6. `factory/boot.sh` is 300 lines or fewer, and no line of it contains the string `/usr/bin/` or the string `/usr/local/bin/`, so every `curl`, `git`, `npm`, `claude` and `systemd-run` it runs is resolved through `PATH`.

### Task 3: The engine publishes — evidence on every landing, the branch, the pull request, the two tags

**Type:** implementation
**Review:** peer

**Files:**
- Modify: `factory/engine.mjs`
- Test: `fleet/tests/test_factory_engine.mjs`

**Claim:** A run's record is written by the engine as it goes — every landing a commit on the evidence branch — and when the last task lands the engine pushes the branch, opens the pull request from the sandbox and leaves the two tags that are the run's record; a drive without a run number does none of it. (derived)
Machine: M1. When `--run <N>` is given (with `--repo <owner/repo>`, `--plan-sha <sha>`, `--evidence-dir <dir>`, `--vm <name>`), before the first dispatch the engine runs `git -C <target> fetch origin refs/heads/ultra/evidence-run-<N>` and adds a detached worktree at `<evidence-dir>` at `FETCH_HEAD` when that fetch succeeded, else at `<plan-sha>`; it writes `<evidence-dir>/.ultrapowers/runs/<N>/status.json` with `state` `running`, commits with subject `run-<N>: running` and pushes `HEAD:refs/heads/ultra/evidence-run-<N>`. When `--run` is absent, no `git` argv the engine issues contains `worktree`, `push`, `fetch` or `tag`, `deps.fetch` is never called, and `runEngine` resolves exactly `{ done, adopted, head, wall_ms, cost_usd }` as at BASE. M2. `status.json` is a JSON object whose top-level keys are exactly `run`, `state`, `phase`, `pr`, `prAuthor`, `merged`, `disclosures`, `branch`, `vm`, `startedAt`, `updatedAt`, `error`, `tasks`, with `run` the string `<N>`, `state` one of `running`, `publishing`, `done`, `parked`, `failed`, `branch` `ultra/integration-run-<N>`, `vm` the `--vm` value, `merged` and `disclosures` `null`, and `tasks.<id>` an object with keys exactly `wave`, `state`, `role`, `lastProof`, `park`, `attention`, `blockedBy`, where `state` is `queued` before dispatch, `implementing` while in flight, `folded` after adoption and `failed` after a park. M3. After every `landing` row and every `parked` row is appended, the engine copies `<run-dir>/events.jsonl` to `<evidence-dir>/.ultrapowers/runs/<N>/events.jsonl` (written to a temporary name in that directory and renamed), rewrites `status.json`, stages exactly those two paths, commits with subject `run-<N>: task <id> landed` or `run-<N>: task <id> parked`, and pushes `HEAD:refs/heads/ultra/evidence-run-<N>`; a push that fails is retried after `git pull --rebase origin ultra/evidence-run-<N>` up to five times, and after the fifth the engine logs `evidence: push rejected 5 times` and the loop continues. M4. When the loop ends with every task adopted, the engine pushes `<head>:refs/heads/ultra/integration-run-<N>` from `<target>`, sets `state` `publishing`, and calls `deps.fetch('https://github.int.exe.xyz/api/v3/repos/<repo>/pulls', { method: 'POST', headers: { 'content-type': 'application/json' }, body })` where `body` parses to `{ title, head, base, body, draft }` with `title` `fleet run-<N>: <the plan's first "# " heading>`, `head` `ultra/integration-run-<N>`, `base` the name after `refs/remotes/origin/` in `git -C <target> symbolic-ref refs/remotes/origin/HEAD`, `draft` `false`, and a `body` string that begins with the plan's `**Summary:**` paragraph verbatim (the text after `**Summary:** `, to its blank line), then one markdown table row per task `| <id> | <k> | <exam exit> | <candidate sha> |`, then one `Closes #<n>` line per number on the plan's `**Closes:**` line in order; on a 2xx reply it appends `{ kind: 'publish:pr', url: <html_url>, number: <number>, draft: false }` to `events.jsonl`, sets `pr` to `html_url`, `prAuthor` to `user.login` and `state` `done`; when one or more tasks parked it does the same with `draft` `true` and `state` `parked`; a non-2xx reply sets `state` `failed`, `error` to the first 2000 characters of the reply body, and `main` exits 1. M5. After the final `status.json` commit and push of a `done` or `parked` run, the engine pushes `<plan-sha>:refs/tags/ultra/plan/run-<N>` from `<target>` and `HEAD:refs/tags/ultra/evidence/run-<N>` from `<evidence-dir>`, reads `git -C <target> ls-remote --tags origin refs/tags/ultra/plan/run-<N> refs/tags/ultra/evidence/run-<N>`, and only when that listing shows both refs at those two shas runs `git -C <target> push origin --delete refs/heads/ultra/plan-run-<N> refs/heads/ultra/evidence-run-<N>`; otherwise it logs `record:` with the listing and issues no delete; a `failed` run pushes no tag. M6. `factory/engine.mjs` is at most 1,500 lines, and `main` exits 0 when `done` is true and, with `--run`, the pull request was opened.

**Authorized-by:** #1131 (map, the boot step: "the engine commits its own evidence"); spec `docs/superpowers/specs/2026-09-17-jev-factory.md` §Components (engine: the loop, dispatch, capture, fold calls, publish); `fleet/CONTRACT.md` §Literals (`ultra/evidence-run-<N>`, `status.json`, the two tags)

**Interfaces:**
