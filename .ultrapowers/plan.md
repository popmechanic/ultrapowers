# Hermetic sims — every fleet sim sees only what its test hands it

**Grammar:** claims-v1

**Claim:** Nothing in the engine's own pre-flight reads the machine it runs on; what it sees is what it was handed, and one probe fails the moment any of it does. (elicited)

**Goal:** Close #868 and #856 as one seam — the fleet test rig. One shared `simEnv()` hands every process a `fleet/tests` sim spawns a scrubbed environment and a home of its own; the pytest bridge hands every sim the same; the six sibling-sim spawns and the one pytest shell-out are deleted, each sibling list kept only as a glob the sim reads; and one driver-run probe, `fleet/tests/test_sims_are_hermetic.mjs`, sweeps the tree and fails on the first spawn that inherits, the first literal read of a path the box owns, or the first sim that runs another. Class behind #833 (runs 73/74/75 reddened by a host `/etc/fleet/render.env`) and the nested-sim residuals #827 #846 #850 (#809 removed this shape once).
**Closes:** #868 #856

**Tech Stack:** Node 24 (`node:child_process`, `node:fs`, `node:os`), Python 3 (`subprocess`, `shutil.which`) for the bridge; no new dependencies.

**Spec:** #868 and #856 are the specification; there is no separate spec document.

**Parallelization rationale:** One wave of width 1 — a single `implementation` task. Two shapes were weighed and rejected. (i) Rig + probe in one task, the seven nested-spawn deletions in another, same wave: the probe is red in any clone where a nested spawn survives, so the rig task would have to hand those seven sites a `simEnv()` of their own to make its own `Run:` green, and the deletion task would delete the very same lines — modify-versus-delete of one hunk is a resolver job (run-36's two misses), not the line-disjoint fold the doctrine measured. (ii) Deletions first, rig second, as a chain: no `Consumes:` symbol joins them, so the compiler would put both in one wave anyway and the collision of (i) returns. The seven sites are the lines the rig would otherwise rewrite; one writer of one hunk is the seam, and that is why this is one task. The compiler's `wide-files` advisory (50 entries) is read and accepted: a split along the `simEnv` symbol puts every consumer sim in a later wave, and the probe — which sweeps the whole tree — is red at the wave-1 fold until they land, so a narrower task cannot leave its own wave green; the edits are mechanical (one `env:` per spawn site) and the width is in files, not in judgment.

A missing interpreter is left out silently, never thrown on: the sim that needs it fails where it spawns it. The parent's `PATH` is read for locations only; no other key of the parent reaches a child except through the caller's `env`. Node's own rule (the `node:child_process` documentation, read 2026-09-09): with an `env` option the child gets exactly that object and nothing of `process.env`, the command is looked up on `env.PATH` — on Unix a missing `env.PATH` falls back to `/usr/bin:/bin` — and a `bash -c` child resolves its own sub-commands on the same `PATH`, which is why the interpreters ride it; Python's `subprocess.run(env=...)` is the same: the dict replaces the environment and `PATH` is taken from it. Git identity: `_engine_helpers.mjs` and `_lobby_helpers.mjs` already `git config user.name/user.email` in every repository they create, and the publish-fold sims set `GIT_CONFIG_NOSYSTEM`; with `HOME` under `home` there is no `~/.gitconfig`, so a sim that commits without configuring identity fails — none does at BASE, and `simEnv` sets no `GIT_*` of its own.
