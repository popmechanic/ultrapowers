# celld on the sandbox — the digest-pinned runtime, memory sized by browsers, and the module-object shape in the greenfield rule

**Grammar:** claims-v1

**Claim:** do: launch a TinyApp plan on the fleet; see: the sandbox already carries celld at the pinned release, the box is sized for the browsers the run will hold open at once, and the plan's author was told the app shape, one root and one module object per store, and what an exam must do to start and stop the runtime cleanly. (elicited)
**Summary:** This plan puts a self-hosted Workers runtime, celld, on every fleet sandbox so a TinyApp's exams can run against a real Durable Object with no network and no credential. It exists because the convergence exam and the forked-state probes need that runtime in the sandbox before any fixture plan can use them, and because a two-task TinyApp run today gets a box too small for two browsers. After it, a TinyApp run has its runtime and its memory, and the next plan's author starts from the module-object shape that proved green on the laptop.

**Goal:** Step 3 of #1094's sequence (spec `docs/superpowers/specs/2026-09-16-root-and-facets-on-celld.md` §3.6, operator decisions 7, 9, 10 and 11 of 2026-09-16/17, Shelley's measurements on fleet-counsel of 2026-09-17), as three plugin-side changes: `fleet/setup-script.mjs` installs celld 0.5.0 at `/usr/local/bin/celld` from the release's Linux x86-64 asset only after `sha256sum -c` agrees with the digest recorded beside `BUN_VERSION`, and the run unit and the engine's transient service raise `LimitNOFILE`; `fleet/launch.mjs` sizes a run's memory by the browsers it may hold open at once (#1087) while a run with no state exam keeps today's `2 + W`; and `skills/ultrawrite/references/greenfield-stack.md` tells a TinyApp plan's author the root-plus-module-object shape and the runtime contract an exam honours on celld.

**Claim:** Memory is sized by browser concurrency, not task count: floor 6 GB, `2 GB + 1.25 GB × C` where C is the number of browsers a run may hold open at once (the plan's width for a TinyApp target, 0 otherwise), capped at 12 GB; CPU keeps the width formula. (quoted from #1087)
Machine: M1. `fleet/launch.mjs` exports `browsersFor(compiled)`, which reads `compiled.waves` — the launcher's compiled object, whose `waves` is the compiler's `launch_waves`, an array of arrays of task objects — and returns the largest count, over those arrays, of tasks in one wave whose `proofTests` carries a path under `tests/state-exams/`; an entry that is not an object with a `proofTests` array counts as no exam, and a compiled object with no `waves` array gives `0`. M2. `vmSizeFor(widestWave, cap, browsers)` keeps `cpu` equal to `min(cap.cpu, 2 + ceil(W / 3))` for every `browsers`, returns `memory` equal to `min(cap, 2 + W) GB` when `browsers` is `0` or omitted, and returns `memory` equal to `min(cap, max(6, ceil(2 + 1.25 × browsers))) GB` when `browsers` is at least `1` — so under the cap `12GB` a run of width 2 with 2 browsers asks `6GB`, width 4 with 4 browsers `7GB`, width 8 with 8 browsers `12GB`, and width 10 with 10 browsers `12GB`, and under the cap `8GB` width 8 with 8 browsers asks `8GB`. M3. `fleet/launch.mjs` exports `sizeFromCompile(compiled, { cpuCap, memoryCap, cpu, memory })`, pure, returning `{ width, browsers, cpu, memory }` where `width` is the length of the longest array in `compiled.waves` (at least `1`), `browsers` is `browsersFor(compiled)` of the same object, and `cpu`/`memory` are `vmSizeFor(width, { cpu: cpuCap, memory: memoryCap }, browsers)` unless the matching `cpu` or `memory` override is given, in which case that cap value is returned outright; and `launch()` sizes every run by calling this export on the object `compileFor` returns — the source of `fleet/launch.mjs` has exactly one definition of `sizeFromCompile`, the exported one at top level, and the call inside `launch()` passes the compiled object and the four options.
