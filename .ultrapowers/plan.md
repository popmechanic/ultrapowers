# The exam seam — a red exam the repair round declares unsatisfiable reaches the referee instead of parking

**Grammar:** claims-v1

**Claim:** If the implementer's repair-round output carries a finding that names an exam case and says it cannot pass for any output (the shape run-99's implementer wrote: "cannot pass for any report output. Its `_section` helper reads … the case then asserts the line before the note equals that same last entry"), the task goes to the referee with that finding attached, exactly as a blocking review finding would; the referee, which already owns the PROPOSED PATCH mechanism for exam edits (run-96 used it), can propose the exam fix, the implementer applies it as an `examEdited` edit (recorded, named to the referee, reviewed — the 2026-09-02 rule), and the task proceeds. A repair round that is red with no such finding parks as today. (quoted from #908)
**Summary:** Today a peer-written exam case that no implementation can satisfy is a guaranteed park: the fix round may not edit the exam, and the reviewer — the one reader allowed to propose an exam patch — never sees a task whose pre-review pass stays red. This plan opens exactly one door: when the repair round's own reply says an exam case cannot pass (the `exam:` concern `fleet/roles/fix.md` already asks for), the task goes to review round 1 with that concern on the prompt, and the loop that already exists does the rest — the reviewer proposes the exam patch, the fix round applies it, the edit is recorded as `examEdited`, round 2 re-grades a green exam. A red exam still outranks every reviewer verdict, so a lazy implementer's concern buys a second independent reader, never a merge.

**Goal:** #908 — runs 98 (task 2) and 99 each parked `proof-red` on one unsatisfiable exam case with the implementer's written finding in hand, and each implementation was lost with the VM (#907 rebuilt run-99's inline). The engine's pre-review pass gains one route: an `exam:` concern from `fix:<id>:0`, beside a still-red exam, falls through into the review loop instead of returning `proof-red`; `fleet/roles/reviewer.md` learns what that concern is and that its answer is a `proposedPatch` on the exam; `report-format.md`'s two rows that promise "no reviewer was dispatched" say when one now is.
**Closes:** #908

**Tech Stack:** Node 24 ESM (`fleet/run-engine.mjs`, sims under `fleet/tests/` bridged by `tests/test_fleet_suite.py`); role prompts as plain markdown under `fleet/roles/`.

**Spec:** none — authored from #908 alone; every fact a worker needs is in the task's Context.

**Parallelization rationale:** one task, width 1. The engine clause, the reviewer's paragraph and the report-format rows are one behaviour with one exam; a second task would only wait on the first's literal.

**Launch base:** main after the referee-deletion plan lands (operator decision 2026-09-11); the launcher re-compiles at `--base`.

## Global Constraints

- The driver never refuses an exam edit and never edits an exam itself: an exam changes only through a fix round's applied patch, recorded as `examEdited` and read by a reviewer (CLAUDE.md §Wayfinding, Peer Review, 2026-09-02).
- A task whose exam is red never merges: the existing rule that a red exam in a review round is a blocking issue whatever the reviewer returned stays in force, so the second reader of an `exam:` concern is a reviewer dispatch, never the implementer's own word.
- The route is one added branch at the existing `proof-red` return; no new `reviewVerdict` value, no new schema field, no new role file.
- Check: git diff --quiet $ULTRA_BASE -- fleet/roles/fix.md fleet/roles/implementer.md fleet/roles/examiner.md

**Acceptance:** suite — the committed suite plus per-task review is the verification; the new sim joins it through `tests/test_fleet_suite.py`'s glob.

**Claim:** After the repair round, a task whose exam is still red and whose repair round wrote down that an exam case cannot pass goes to the reviewer with that finding on the prompt; the reviewer's proposed exam patch is applied by the fix round, recorded as `examEdited`, and the task merges — while the same red with no such finding parks `proof-red` exactly as today, and a reviewer that waves the red through still cannot merge it. (derived)
Machine: M1. When the pre-review pass after `fix:<id>:0` still has the exam red (its `reds` carry the `the Proof's exam failed:` line) and that fix round's reply is `DONE_WITH_CONCERNS` with at least one `concerns` entry whose text begins `exam:`, the driver does not return `reviewVerdict: 'proof-red'`; it pushes one `judgmentCalls` entry containing `exam concern` and the task id, then enters review round 1 (`review:<id>:1` is dispatched) reading that second pass's own evidence. M2. M3. When round 1's reviewer returns `FIX_REQUIRED` with one blocking issue of actor `implementer` carrying a `proposedPatch`, and `fix:<id>:1` rewrites the exam at its Proof `Test:` path so the round-2 exam exits 0, the task's report row reads `status: 'done'`, `reviewVerdict: 'fixed'`, `proofFixes: 1`, `fixIterations: 1`, `examEdited` equal to the list of exactly that path, `coverage.tasks_merged` is 1, the `review:<id>:2` prompt carries the line `EXAM EDITED: <path>` and a line `EXAM EDITED DIFF <path>:`, and the run's integration branch holds the rewritten exam bytes. M4. M5. **Context:** Where the route goes. In `fleet/run-engine.mjs`'s `runTaskInner`, the driver's pre-review pass is `prePass(0)`; when it is red the driver dispatches `fix:<id>:0`, reassigns `impl` to that round's reply, calls `noteConcerns(impl)` and `noteDrift('the fix round')`, then runs `prePass(1)`; when `reds.length` is still non-zero it returns `{ status: 'failed', reviewVerdict: 'proof-red', … }` (a command, exam or check still red). Vocabulary: since #853 "reviewer" names the model that reads the patch under `fleet/roles/reviewer.md` and returns `REVIEWER_SCHEMA`, and #908's "referee" is that reviewer in today's words; the driver's own arithmetic that used to share the name is deleted by the plan this one launches after, so nothing here reads any record of it. The route is one condition in front of that return: the exam's red line is `EXAM_FAIL(preExam)` (`'the Proof\'s exam failed: ' + cmd + ' — exit ' + exit`) and is in `reds` exactly as the `#722` branch above already tests it (`examIsRed`); the concern is `impl.status === 'DONE_WITH_CONCERNS' && impl.concerns.some(c => /^exam:/.test(String(c)))`. When both hold, push the judgment call, log, and fall through to the `for (let iter = 1; …)` loop instead of returning; nothing else in the loop needs to change, because round 1 already reads `preRuns`/`preExam`/`preChecks` — which `prePass(1)` just wrote — and `proofFixes` is already `1`. Every other red (no `exam:` concern; a red with `impl.status` of `DONE`) returns as today.

Why the loop as it stands finishes the job. In round 1 the driver already appends a blocking issue `EXAM_FAIL(examEvidence)` "whatever the reviewer returned", so the fix round `fix:<id>:1` is always dispatched; a reviewer's blocking issue with a `proposedPatch` is rendered under `PROPOSED_PATCH_HEADER` in that fix prompt, `fleet/roles/fix.md` already says to apply it, and `noteDrift('the fix round')` after that round records the moved exam path as `examEdited` and pushes the `edited the exam` judgment call. Round 2 then re-runs the exam (`runExam(2)`) and builds the review prompt with `EXAM EDITED: <path>` and `examEditedDiffBlock` — a PASS ends the task `done`/`fixed`. If round 1's reviewer returns PASS and the fix round leaves the exam red, round 2's red exam is again a blocking issue and `iter === 2` returns `fix-loop-exhausted` — that is M5, and it is what keeps the implementer's word from merging anything.

The concern prefix already exists. `fleet/roles/fix.md` at BASE already tells the fix round that a Proof `Test:` file red for a reason other than the missing implementation is reported as a `concerns` entry prefixed `exam:` rather than edited around. That is the finding this route reads; no role file other than `reviewer.md` changes and the Check above pins that. The implementer role (`implementer.md`) never holds the exam (#653), so the first pass cannot write this concern and the route reads only the fix round's reply.

The prompt line. Add the `EXAM CONCERN: ` lines to the review prompt beside the other evidence blocks (a small exported builder in the style of `examEvidenceBlock` is fine; export nothing the exam must import). Place them after the `EXAM EVIDENCE:` block so the reviewer reads the red output first and the implementer's claim about it second. `reviewer.md` currently opens with "Do not run git, read any implementer report, or modify anything" — the new passage is the one stated exception: an `EXAM CONCERN:` line is the fix round's claim that a named exam case cannot pass for any output, to be checked against the exam file in PATCH, and rule 8's clause "unless the exam itself was wrong — a pin that no correct implementation could satisfy" is the standard; agree → blocking issue, actor `implementer`, `proposedPatch` = the unified diff on the exam path that changes only that case; disagree → blocking issue, actor `implementer`, naming what the diff gets wrong. The exam path in the graded tree is the landing path the reviewer sees in PATCH (an unguarded exam lands under `tests/exams/<run>/` or `fleet/tests/exams/<run>/`, #777), so the patch names that path.

The docs. `skills/ultrapowers/references/report-format.md` row `tasks[].reviewVerdict` says of `proof-red` "no reviewer was ever dispatched, because a patch whose own proof fails is not a patch a reviewer can grade", and row `tasks[].proofFixes` says a second red pass ends the task at `proof-red` (as the deletion plan will have left those rows). Amend both in place to say the one case that now proceeds: a still-red exam beside a fix-round `exam:` concern goes to review round 1 with an `EXAM CONCERN:` line, and its row then reads like any reviewed task (`proofFixes: 1` and `fixIterations` counting the rounds that followed). Nothing reads these rows mechanically.
