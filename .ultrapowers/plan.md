# Failure receipts — every red exam, fold conflict, resolver miss, blocking finding and refuted finding leaves a receipt on the run's record, and a judge whose brief covers those files reads it before judging

**Grammar:** claims-v1

**Claim:** Every failed verification and every refuted judgment in a run leaves a receipt naming what failed, what it rested on and which files it was about, and any judge whose brief covers those files reads it before judging. (elicited)
**Summary:** This makes a run remember its own failures: when an exam goes red, a merge collides, a resolver gives up, or a finding is blocked or later shown wrong, the run writes down what failed, what that reading rested on and which files it was about, and any judge about to read those same files is shown that note before it judges. It exists because today those facts are scattered across report rows and prompts nobody re-reads, so a second judge on the same file repeats a block a first one already made, or never learns that a block on that file was already shown wrong — and #1037's replayed verdict was the same mistake in the other direction, a fact from another run shown as this run's, which is why a receipt here never leaves the run that wrote it. Over the next five runs (n=5 runs, the five that follow this merge) the record says how often a brief carried such a note, how often a finding cited one, and whether a judge that saw a prior failure on a file caught more or repeated less than one that did not; a note kind no finding ever cites is deleted, and a run with no failure produces exactly the briefs it produces today.

**Goal:** give the engine of popmechanic/ultrapowers, read at `4a63b4ef097ac1a81e539a3f3c79771ebc9a04be`, a per-run failure record its own judges read: two fields, `paths` and `evidence`, on the failure events the driver already appends (`driver:exam-run` red, `resolver:reply`, `driver:wave-blocked`, `driver:publish-fold`), two event kinds for what is not an event today — a blocking finding and a refuted one, which live only in `report.json` rows and prompt lines — and one bounded `FACTS:` block the driver renders into the examiner's, the reviewer's and the resolver's brief from this run's rows matched by kind and path. The carrier is `events.jsonl` with no hub, on purpose beside run-155's handshake, which posts through kata metadata (map #810 rule 4: every accepted fact is also an event; the split between the two carriers is chosen, not accidental). Nothing here blocks, no schedule changes, no worker writes an event, and a run whose log holds no receipt dispatches briefs byte-identical to today's (#810 rule 1: facts, never commands — the driver alone decides what fires; #1037: a fact from another run is history, never this run's state).

**Tech Stack:** Node ≥ 20 (`fleet/`), the engine sims under `fleet/tests/test_*.mjs` (sentinel `ALL TESTS PASSED`, bridged by `tests/test_fleet_suite.py`), the fold kernel `skills/ultrapowers/kernel/` called by the engine as `python3`, the hub's REST API through `fleet/kata-client.mjs` (stubbed in every sim).

**Spec:** the operator's brief of 2026-09-16 (the Claim above is its first sentence verbatim); map #810 (rules 1 and 4, and its `makeEventLog` reading: the log is a one-writer tuple space whose consumers are all whole-file readers — a matcher over rows is the missing template read); #1037 (run-16's replayed attention: a fact from a different run rendered as this run's state, the failure mode a receipt must never repeat); #1035 (the resolver brief moved off argv because it grew with siblings — every worker prompt rides stdin since `e245b71c`, so the bound here is a reader's, not argv's); #964 (one reviewer, one round, no fix worker from a referee's finding); #908 (the fix round's `exam:` concern); #944 (the flaky re-run); #836 (the hollow exam the reviewer caught); #998 ticket 5 / run-155 (`handshake:finding`, the one driver-minted finding on the record today).

**Parallelization rationale:** two waves. Wave 1 is width 5 and wave 2 is width 2: Tasks 1, 2 and 3 put the receipt fields on the record (each in its own region of `fleet/run-engine.mjs` — the exam pass and the resolver work list; the two fold-blocked sites and `fleet/publish-fold.mjs`; the review round), Task 4 is the pure matcher-and-renderer module `fleet/facts-block.mjs` with its own sim, and Task 6 is the contract text; all five agree on the shared literal in every Context (RECEIPT SHAPE, RECEIPT KINDS, FACTS BLOCK) and consume nothing a sibling runs. Wave 2 is Tasks 5 and 7, two chains: Task 5 consumes `factsBlock` from Task 4 and `examReceiptOf` from Task 1 and needs both their runtime behaviour — its own exam drives the engine end to end and reads the rendered block's bytes, carrying the receipt the engine wrote on a red exam, out of the captured prompts, which no stub of either shape could produce; Task 7 consumes `publishFoldEvent` from Task 2 and `factsBlock`/`receiptRows` from Task 4 for the same reason — it drives a real publish fold and reads what the fold's row and the resolver's brief carry. The two are independent of each other (Task 5 edits the engine, Task 7 the publish fold) and run side by side. Tasks 1 and 3 both extend `fleet/tests/test_run_engine_proof_runs.mjs`, and Tasks 1 and 2 both extend `fleet/tests/test_run_engine_stale_patch.mjs`, each under a comment naming its task: same-wave text edits that fold, and where both append at the file's end an adjacent insert the resolver orders (run-115's shape: one Sonnet resolver, 60 s, $0.34, n=1 fold, 2026-09-13) — cheaper than the wait a chain would buy.

## Global Constraints

- A run whose record holds no receipt row dispatches every judge with the brief this engine's base produces: no captured prompt of any role contains the token `FACTS:`, and the schedule — waves, edges, fold epochs, dispatch order, the one review round — is what it is at BASE.
- Check: git diff --quiet $ULTRA_BASE -- fleet/roles/
- No worker writes an event: every receipt row is appended by the driver — `appendEvent` in `fleet/run-engine.mjs` or `eventLog.onEvent` in `fleet/publish-fold.mjs` — and no role file asks a worker to post, edit or read one.
- A receipt states what was observed and never what to do: `evidence.read` and `evidence.against` are readings, and no rendered `FACTS:` line carries an instruction to a judge beyond the block's own header sentence.
- A receipt is scoped to the run that wrote it: the matcher reads only rows this run's own process appended — the engine's in-memory receipts, or the publish fold's own `<runDir>/events.jsonl` — and never a tag, a hub issue or another run's directory; a relaunch renders nothing of the run before it.
- The `FACTS:` block is bounded: at most 20 rows, each row's `read` and `against` at most 500 characters, so a block is under 24 KB however many failures the run recorded.
- Every new event kind and every new event field is named in `fleet/CONTRACT.md`, which wins over `fleet/RUNBOOK.md` on any literal.
- Check: node fleet/tests/test_sims_are_hermetic.mjs | grep -q 'ALL TESTS PASSED'
