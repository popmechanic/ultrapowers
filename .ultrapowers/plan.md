# Viz's sensor — the fleet turns where I can see it

**Grammar:** claims-v1

**Claim:** do: open a run's page while a wave is running. see: what each task is doing right now, the last proof that ran and how it went, and the live event log; and the evidence branch is never more than two minutes or a handful of events behind the machine. (elicited)

**Summary:** This makes a running fleet visible while it runs. Today the run's page shows one word for a whole wave and the record on GitHub falls a wave behind, so a slow run and a stuck run look the same and the only way to tell them apart is to ask Shelley. After this run the page shows each task's current step and its last proof, serves the live event log, and the record catches up within two minutes or ten events, so silence means nothing is happening rather than that nothing can be seen.

**Goal:** #877 (map #876 Viz, ticket 1, with Shelley's two readings of 2026-09-10 on fleet-r84 and fleet-r87): the sandbox serves `events.jsonl` beside `status.json`; `status.json` gains per-task cells and a sub-phase, both projections of the event log; evidence commits are gated on new events or elapsed time, not on the phase string. The engine records wave adoption and wave blocking as events so the projection needs no second bookkeeping.

**Tech Stack:** bash (`fleet/sandbox-boot.sh` with an embedded python projector), Node 24 ESM (`fleet/run-engine.mjs`, sims), Markdown (`fleet/CONTRACT.md`)

**Spec:** issue #877 and its two Shelley comments; every fact a worker needs is in its task's Context.

**Parallelization rationale:** one wave, two wide. Task 1 has the engine append two event kinds at the wave barrier; task 2 has the boot script project the log onto the page, serve the log, and re-gate its commits. Task 2 reads the two event kinds task 1 emits, but its sims seed their own event lines (the stub engine writes `events.jsonl`), and the line shapes are one literal carried in both Contexts — so no edge. No chain.

**Launch base:** any main at or after run-88's merge; folds with the engine plan and the card plan if they are in flight, since every shared file is text.

Machine: M1. `https://<vm>.exe.xyz/events.jsonl` serves the run's `events.jsonl`: on every refresher tick the boot script copies `<run dir>/events.jsonl` to `WWW_DIR/events.jsonl` (temp file then rename), so the served copy grows across two appends within two ticks. M2. `status.json` carries a `tasks` object: one key per task id seen in the plan's compiled waves (read from `args.json`'s `waves`, or from events when absent), each `{"wave":<n>,"state":<s>,"role":<label or null>,"lastProof":{"cmd","exit","ts"} or null,"park":<detail or null>}`, with `state` derived from the log in `id` order — `queued` with no event for the task; `examining` after `worker:start` `exam:<id>`; `implementing` after `worker:start` `impl:<id>`; `proving` after a `driver:proof-run`, `driver:check-run` or `driver:exam-run` for the task with no worker open; `reviewing` after `worker:start` `review:<id>:…`; `fixing` after `worker:start` `fix:<id>:…`; `folded` after a `driver:wave-adopted` listing the id; `failed` after a `driver:wave-blocked` listing the id or a `worker:end` for `impl:<id>` whose `status` is `BLOCKED` — `role` the label of the task's last `worker:start` with no later matching `worker:end`, else null; `lastProof` the task's last `driver:proof-run`/`driver:check-run`/`driver:exam-run` event's `cmd`, `exit` and `ts`; `park` the `driver:wave-blocked` `detail` when failed by one. M3. `status.json`'s `phase` while the engine runs is `<last engine:phase> · <sub>` where `<sub>` is the label of the most recent `worker:start` with no matching `worker:end`, else the `kind` of the last event; with no event past `engine:phase` it is the phase alone. M4. The refresher commits evidence when at least 10 new event lines have been appended since the last commit or at least 120 seconds have elapsed since it, whichever first (both bounds `FLEET_COMMIT_EVENTS` / `FLEET_COMMIT_SECONDS`), and never on the phase string alone; a wave that emits 25 events in 30 seconds yields at most three commits, and a wave that emits one event then goes quiet for five minutes yields one commit within the first 150 seconds. M5. `fleet/CONTRACT.md` spells the served files (`status.json`, `engine.log`, `events.jsonl`), the `tasks` cell schema with its eight states, the `phase` sub-phase form, and the commit rule; `fleet/RUNBOOK.md`'s "walk away" guidance says the page's `phase` names the sub-step and the branch is at most two minutes behind.
