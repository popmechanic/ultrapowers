# A factory worker cannot run git inside a compound command: the block reads the whole Bash line, and an attempt is a row

**Grammar:** claims-v1

**Claim:** The factory worker's `PreToolUse` boundary reads the whole Bash command line: a `git` word at the start of any segment of a compound command (after `&&`, `||`, `;`, `|`, a newline, `$(`, a backtick or a subshell paren), or behind `env`/`command`/`xargs`/`sh -c`, is denied with a message that says the engine runs git itself. Every denial appends `{ kind: 'worker:denied', task, label, tool: 'Bash', why: 'git', command: <first 200 chars> }` to `events.jsonl`, so an attempt is a reading and not a silence. (quoted from #1156)
**Summary:** This closes a gap in the rule that the models doing the work never run git themselves, which is one of the two rules a run's safety rests on. It exists because on run-193 a worker ran git tucked behind another command on the same line and the block, which only looked at the first word, let it through; that one was harmless, but the same shape would have let a commit or a reset through (n=1 occurrence seen in 57 test-run rows of one run, 2026-09-18). After this run the whole line is read, the worker is told the engine runs git itself, and every attempt shows up in the run's record instead of passing in silence; the old first-word block stays in place underneath as the rollback.

**Goal:** #1156: a pure command reader in `factory/gitblock.mjs`, a second `PreToolUse` hook in `factory/worker.mjs` that denies on it and reports the denial through a callback, and the two dispatch sites of `factory/engine.mjs` handing that callback their own `appendEvent`.
**Closes:** #1156

**Tech Stack:** Node 24 ESM, no new npm dependency.
Spec: none on disk — issue #1156 is the brief, and everything a worker needs is in the Context. The sandbox holds no spec.

**Context:** You see this task body and nothing else. **The gap.** `factory/worker.mjs` (139 lines) enforces "models never run git" with `export const DISALLOWED_TOOLS = ['Bash(git *)', 'WebFetch', 'WebSearch', 'Agent']`, which matches only a Bash command that BEGINS with `git`. Leave `DISALLOWED_TOOLS` exactly as it is: the prefix rule is the rollback and stays under the hook.
**The reader — `factory/gitblock.mjs`, new.** Export `findGit(command)`: a pure function from one Bash command line (coerce with `String`) to the first offending segment as a trimmed non-empty string, or `null` when no segment runs git. It imports nothing — no `fs`, no `child_process`. A *segment* starts at the start of the line and after each of `&&`, `||`, `;`, `|`, `&`, a newline, `$(`, a backtick, `(` and `{`. A segment's *command word* is its first word after skipping leading whitespace, leading `NAME=value` assignments, the shell keywords `then`, `do`, `else`, `time`, `!` and `exec`, and these wrappers with their own flags and assignments: `env` (flags and `NAME=value` words), `command`, `nohup`, `nice`, `timeout <duration>`, `sudo`, and `xargs` (its flags). The segment runs git when that command word, with surrounding quotes stripped, is exactly `git` or ends in `/git` (`/usr/bin/git`). `sh -c`, `bash -c`, `zsh -c` and `eval` run their string argument: read that string as a command line of its own, quotes stripped, by the same rule. The precedent is the old fleet's `fleet/confine-hook.mjs`, gone from the tree since cut two and not readable from a sandbox; what it taught, in its own words, is that such a reader is "naive on purpose" and "incomplete by nature", that an unbalanced parse is "not evidence about data", and that it must mask and never delete, so a quoted target is still found. For this reader the rule of thumb is simpler, because a git that runs is the one failure that matters: **a miss is worse than a false deny.** You need not tell quoted data from code — `echo "a; git b"` may be denied — but a git word that is only an argument (`grep -rn git factory/`), only part of another word (`cat .gitignore`, `ls .git`, `npm run git-hooks`, `git-lfs`), or a later word of a segment (`echo git`) is never a command word and answers `null`.
**The hook — `factory/worker.mjs`.** Add and export `makeGitHook({ task, label, onDenied })`, beside `makeConfineHook` and the same shape: an async `(input) => …` that answers `{}` unless `input.tool_name === 'Bash'` and `findGit(input.tool_input.command)` is not `null`. On a hit it first builds the row `{ kind: 'worker:denied', task, label, tool: 'Bash', why: 'git', command: String(command).slice(0, 200) }` and calls `onDenied(row)` inside a `try`/`catch` when `onDenied` is a function — a row that cannot be written never turns a deny into an allow, and neither does a missing callback — and then answers `{ hookSpecificOutput: { hookEventName: 'PreToolUse', permissionDecision: 'deny', permissionDecisionReason } }`, the envelope `makeConfineHook` already answers, where the reason contains the byte-exact words `the engine runs git itself` and tells the worker to leave git alone and keep working (for example `Bash denied: this line runs git, and the engine runs git itself — never a worker. Drop the git command and carry on; your edits are captured for you.`). Add it to the default export. In `workerOptions` the first argument gains `task`, `label` and `onDenied` (the engine already hands every dispatch `task` and `label`), and `hooks.PreToolUse` carries both hooks, with no `matcher` on any entry — each hook reads `tool_name` itself, as the confine hook does: `[{ hooks: [makeConfineHook({ cwd, files, denials }), makeGitHook({ task, label, onDenied })] }]`. `denials` stays the edit-confinement ledger; the git hook does not write to it.
