# Every worker prompt rides stdin, and the publish-fold brief names its files by path — a third plan landing on a busy main dispatches every resolver

**Grammar:** claims-v1

**Claim:** A resolver gets its brief however long it is, and a fold onto a main that two siblings already landed on dispatches every resolver instead of dying on the first. (elicited)
**Summary:** This fixes the fleet so a third plan landing on a busy main no longer dies at its publish fold. Today the resolver's brief is handed to the worker as one command-line argument, and Linux refuses any argument over 128 KB, so a fold that has to describe everything two siblings already landed cannot start. After this run every worker prompt travels on stdin and each resolver's brief carries only its own file's contending block, written to a file the brief names, so concurrent plans keep landing however many went first.

**Goal:** #1035: (1) `fleet/run-worker.mjs` writes every worker prompt to the child's stdin and puts nothing prompt-sized on its argv, pinned by a hermetic sim that sends a 200,000-byte prompt through the worker seam; (2) the publish fold's resolver brief names, by absolute path, a file holding that conflicted path's contending-task block and a copy of `main.patch`, instead of pasting every conflicted path's block into every resolver's brief, so the brief no longer grows with the siblings that landed first or with the paths that conflicted.
**Closes:** #1035

**Tech Stack:** Node ESM under `fleet/` (`node:child_process` spawn seam, injected as `spawnFn`); the resolver role file `fleet/roles/resolver.md` read at dispatch as a data file; sims under `fleet/tests/test_*.mjs` bridged by `tests/test_fleet_suite.py` (sentinel `ALL TESTS PASSED`, 300 s, no network, `simEnv()` on every spawn). Suite: `python3 -m pytest`.

**Spec:** #1035 (the measurement, the cause and the three desired-state items); #715 decision 11 (plans launch concurrently whatever files they share); #1019 (the stale-patch fold, run-12's publish fold); the resolver work list at `fleet/run-engine.mjs` `resolveConflicts` and the publish fold at `fleet/publish-fold.mjs` step 4.

**Parallelization rationale:** one wave, width 2. Task 1 owns the worker's spawn seam (`fleet/run-worker.mjs`, the one sim that stubs `spawnFn`, and its new sim); Task 2 owns the resolver brief (`resolveConflicts` in `fleet/run-engine.mjs`, the publish fold, the resolver role file, the contract's receipt list, and its new sim). Their Files are disjoint, neither consumes a symbol the other produces, and neither needs the other's runtime behaviour: Task 2's brief is short whether or not Task 1 has landed, and Task 1 carries any prompt whether or not Task 2 has shortened it. No chain.

### Task 1: The worker hands every prompt to the child on stdin, never on argv

**Type:** implementation
**Review:** peer

**Files:**
- Modify: `fleet/run-worker.mjs`
- Modify: `fleet/tests/test_worker_kata_env.mjs`
- Test: `fleet/tests/test_worker_prompt_stdin.mjs`

**Claim:** A worker gets its prompt whole however long it is, and nothing prompt-sized is on the command line the worker was started with. (derived)
Machine: M1. When `createRunWorker(...)`'s `agent(prompt, { label })` is called with a prompt of exactly 200,000 bytes (UTF-8, carrying multi-byte characters) and a `spawnFn` whose child records what is written to its `stdin`, the bytes the child's stdin received are byte-identical to the prompt and its stdin was ended (EOF) by the worker.
M2. On that same dispatch, no element of the argv `spawnFn` received is longer than 4,096 bytes, the argv contains the element `-p`, and no element of it contains the prompt's first 64 bytes.
M3. A child that closes with exit code `0` and a result envelope on stdout before consuming its stdin, and whose stdin then emits an `error` (`EPIPE`), still resolves `agent()` with that envelope's `structured_output` — the write failure is neither thrown out of `agent()` nor reported as a worker failure.

**Authorized-by:** #1035 desired state 1 and 2; #715 decision 11 (concurrent plans, whatever files they share).

**Interfaces:**
- Consumes: none
- Produces: `createRunWorker(cfg)` (unchanged signature; its `runProcess` now spawns `[cli, ['-p', ...argv]]` with `stdio: ['pipe', 'pipe', 'pipe']` and ends the child's stdin with the prompt)

**Context:** At BASE `runProcess` (`fleet/run-worker.mjs` line 1075–1079) does `spawnFn(cli, ['-p', prompt].concat(argv), { cwd, env, stdio: ['ignore', 'pipe', 'pipe'] })`: the whole prompt is one argv element, and Linux caps one element at `MAX_ARG_STRLEN` = 131,072 bytes whatever `ARG_MAX` says — run-14 on tinyapp-fixture (2026-09-15) died `spawn E2BIG` on a 193,611-byte resolver brief. `-p`/`--print` is a boolean flag, and with no positional prompt the CLI reads the prompt from stdin under its default `--input-format text`; verified on the laptop 2026-09-15 against `claude 2.1.273 (Claude Code)`: `printf '…' | claude -p --output-format json --max-turns 1 --setting-sources user --disable-slash-commands --exclude-dynamic-system-prompt-sections --permission-mode default` returned a `stop_reason: end_turn` envelope. So the shape is `spawnFn(cli, ['-p'].concat(argv), { cwd, env, stdio: ['pipe', 'pipe', 'pipe'] })`, then `child.stdin.on('error', () => {})` before `child.stdin.end(prompt)` — the error listener is what M3 pins: a child that exits early makes the pipe raise `EPIPE`, and an unlistened `error` event on a stream is an uncaught exception that would crash the engine, not one worker. The comment block above `buildArgs` (lines 224–255) explains why the prompt was never a trailing positional — `--allowedTools`, `--disallowedTools` and `--add-dir` are variadic and would swallow it — and that reasoning survives: with the prompt on stdin there is no positional at all. Rewrite that comment and the one above `runProcess` (lines 1069–1074, "stdin is CLOSED, not inherited … The prompt goes on argv") to say what is now true; the three-second `Warning: no stdin data received in 3s` they cite was the cost of a pipe with no writer, and a pipe ended with the prompt is read at once (the laptop probe above returned in under two seconds). The evidence `cmd` file (line 972) writes `[cli, '-p', '<prompt>'].concat(argv)` then `--- prompt ---` and the prompt; keep the prompt in that file and let the first line read `claude -p …` with a `(prompt on stdin)` note rather than a `<prompt>` placeholder. `childEnvFor` (line 851) and everything below the spawn are untouched. The last `Run:` pins the code and not the prose: the pattern `'-p', prompt]` matches the spawn at line 1077 and nothing else at BASE (the `buildArgs` comment at line 255 writes `'-p', prompt, ...flags]`), so a rewritten comment cannot fail it and a surviving argv prompt cannot pass it. The largest argv element at BASE is a `--json-schema` value of 460 bytes (`IMPLEMENTER_SCHEMA`; the others are 120–357), so the 4,096-byte pin holds today and is there for whoever next reaches for argv. One existing sim stubs `spawnFn` with a child that has `stdout` and `stderr` emitters and `kill` but **no `stdin`** — `fleet/tests/test_worker_kata_env.mjs` lines 325–333 — so after this change `child.stdin.end(prompt)` would throw there; give that stub a `stdin` with `on` and `end` (a `Writable`, or an object with those two methods) and change nothing else in that file. No other `test_*.mjs` stubs `spawnFn`; the engine sims fake `agent` above the seam, and the boot sims' fake `claude` never receives a prompt. `fleet/tests/README.md` names a `test_run_worker.mjs` that does not exist at BASE; the worker's only sim is the kata-env one, which owns the env surface, so the prompt transport is a new surface and gets its own file, `test_worker_prompt_stdin.mjs`, named for it. The new sim needs only `createRunWorker` from `../run-worker.mjs` with `cwdFor: () => <tmp dir>`, `cli: 'claude'`, `env` from `simEnv()` of `./_helpers.mjs`, `workersDir` under its own `mkdtemp`, and a `spawnFn` returning an `EventEmitter` child with `stdout`/`stderr` emitters (`setEncoding` as a no-op), `kill`, and a `stdin` that collects chunks; it emits on stdout the one-line envelope `{"type":"result","subtype":"success","is_error":false,"session_id":"s","structured_output":{"ok":true},"usage":{},"total_cost_usd":0}` and `close` with `0`. `agent()` returns the envelope's `structured_output` on success. The sim's own `spawnFn` is not a `node:child_process` call, so the hermetic probe's `inherit` rule does not read it; any real spawn in the sim passes `simEnv()`.

**Proof:**
- Test: `fleet/tests/test_worker_prompt_stdin.mjs`
- Legs: (a) dispatch a 200,000-byte prompt built from a repeated line that carries an em-dash, through `agent(prompt, { label: 'impl:1' })` with the recording stub; assert `Buffer.concat(chunks).equals(Buffer.from(prompt, 'utf8'))` and that the stub's `stdin.end` was called — a worker that still passes the prompt as argv writes nothing to stdin and fails the byte comparison, and one that writes without ending fails the EOF assertion [M1]; (b) on the same dispatch, for every element of the recorded argv assert `Buffer.byteLength(el, 'utf8') <= 4096`, assert `argv.includes('-p')`, and assert no element `includes(prompt.slice(0, 64))` — the BASE shape fails the first and third [M2]; (c) a second dispatch whose stub child emits the envelope and `close(0)` on `setImmediate` and whose `stdin.end` schedules an `error` event with `code: 'EPIPE'` on the stdin after the close; assert `await agent(...)` resolves to `{ ok: true }` and that no `uncaughtException`/`unhandledRejection` fired during it (install listeners that record, and assert the record is empty) — a worker without a stdin error listener fails this leg by crashing the process [M3]; (d) the kata-env sim, whose stub now carries a stdin, still prints its sentinel — the first `Run:` [M1].

### Task 2: The publish-fold brief names its contending block and main's patch by path, one conflicted path per brief

**Type:** implementation
**Review:** peer

**Files:**
- Modify: `fleet/run-engine.mjs`
- Modify: `fleet/publish-fold.mjs`
- Modify: `fleet/roles/resolver.md`
- Modify: `fleet/CONTRACT.md`
- Test: `fleet/tests/test_resolver_brief.mjs`

**Claim:** A publish-fold resolver is briefed on the one path it is resolving and told where to read the rest, so its brief stays short however many siblings landed first and however many paths conflicted. (derived)
Machine: M1. `resolveConflicts` accepts `contendingBlock` as a function of the conflict entry as well as a string: with a function and two open conflicts, the brief the injected `agent` receives for conflict `2` is `roles.resolver` + its own `HUNKS FILE:` line + the function's return for conflict `2`, and it does not contain the function's return for conflict `1`.
M2. With `contendingBlock` a string (the wave loop's shape at BASE), the brief the `agent` receives is `roles.resolver` + the `HUNKS FILE:` line + that string, unchanged.
M3. `writeResolverBriefs({ briefsDir, attemptKey, open, blockFor, mainPatch })`, exported from `fleet/publish-fold.mjs`, writes for each open conflict `i` the file `<briefsDir>/contending-<i>-<attemptKey>.txt` holding exactly `blockFor(conflict.path)`, copies `mainPatch` to `<briefsDir>/main.patch` byte for byte, and returns a function whose string for conflict `i` names both absolute paths on lines beginning `CONTENDING TASKS FILE:` and `MAIN PATCH FILE:`, carries no line beginning `- run `, and is shorter than 1,024 bytes when the block is 200,000 bytes long.
M4. `fleet/roles/resolver.md` tells the resolver what a `CONTENDING TASKS FILE:` line and a `MAIN PATCH FILE:` line name, and `fleet/CONTRACT.md`'s `publish-fold/` receipts list names `contending-<i>-<attempt>.txt`.

**Authorized-by:** #1035 desired state 3; #715 decision 11; `fleet/CONTRACT.md` (the `publish-fold/` receipts list, the authority for every literal).

**Interfaces:**
- Consumes: none
- Produces: `resolveConflicts({ …, contendingBlock: string | ((conflict) => string) })`
- Produces: `writeResolverBriefs({ briefsDir, attemptKey, open, blockFor, mainPatch }) -> Promise<(conflict) => string>`

**Context:** What the brief actually carries at BASE, measured on run-14's `publish-fold/resolver-brief-1-1.txt` (tag `ultra/evidence/run-14` on popmechanic/tinyapp-fixture, 2026-09-15): 193,611 bytes, of which the first 1,606 are the role file plus the `HUNKS FILE:` line, and the rest is **seven** `CONTENDING TASKS:` blocks — one per conflicted path, each 18–31 KB because `fleet/publish-fold-block.mjs`'s `taskEntry` inlines every contending task's whole body — concatenated by `fleet/publish-fold.mjs` step 4 (lines 807–818: `blocks.push(await buildContendingBlock(…))` for every open conflict, then `block = blocks.join('')`) and handed whole to every resolver of the stop. The brief holds zero `diff --git` lines: `main.patch` (122,139 bytes on run-14) is not pasted into it at BASE, so the ceiling #1035 names is the block-per-path times the bodies of every sibling that touched that path, and the shape that removes it is the wave loop's own precedent at `fleet/run-engine.mjs` lines 3307–3311, where the block carries one title line per task and says `Their full verbatim task text lives in the JSON file at <wavesPath>`. `resolveConflicts` (`fleet/run-engine.mjs` line 895) takes `contendingBlock = ''` and appends it at line 916 inside the `agent(...)` call; the change is one expression — `typeof contendingBlock === 'function' ? contendingBlock(conflict) : contendingBlock` — and the wave loop at line 3313 keeps passing its string. The conflict entry handed to the function is the kernel's own `open` row, `{ i, path, hunksFile, epoch }`. In `fleet/publish-fold.mjs` the resolver runs with `--add-dir <runDir>` (`makeAddDirsFor` in `fleet/run-main.mjs`: `reviewer` and `resolver` get `[runDir]`) and the hunks file it already reads lives under `<runDir>/publish-fold/frontier/wave-<attempt>/`, while `foldEvidence` (`<evidenceDir>/publish-fold/`, where `main.patch` and the `resolver-brief-<i>-<attempt>.txt` records are written) is under `$FLEET_HOME/evidence`, outside every add-dir — so the files a brief names must be written under the run directory: `briefsDir = path.join(foldRunDir, 'briefs')` (`foldRunDir` is `path.join(runDir, 'publish-fold')`, line 312), a directory of the driver's own beside the kernel's `frontier/`, never inside a `frontier/wave-<a>/` directory the kernel owns. Step 4 then becomes: `const blockFor = (p) => buildContendingBlock({ repo, base, tip, run, path: p, tasks })`, `const block = await writeResolverBriefs({ briefsDir, attemptKey, open, blockFor, mainPatch })`, and `resolveConflicts({ …, contendingBlock: block, … })`; and for the record, copy each `contending-<i>-<attemptKey>.txt` into `foldEvidence` under the same name, beside the `resolver-brief-<i>-<attempt>.txt` the fold already saves (the brief record now holds the two path lines, the contending file holds what they pointed at). The string the function returns is, per conflict: a newline, `CONTENDING TASKS FILE: <abs path> (the tasks that wrote <conflict.path> on both sides — read it before resolving)`, a newline, `MAIN PATCH FILE: <abs path> (everything main gained since this run's base)`.
