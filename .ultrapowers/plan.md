### Task 1: A merged engine change carries a reading of which changed lines a sim reached

**Type:** implementation
**Review:** peer

**Files:**

- Modify: `fleet/run-engine.mjs`

**Claim:** When a run that changed the engine merges, its record says which of the changed lines a sim actually ran and which none did — a reading beside the receipt, never a gate. (derived)
Machine: M1. `fleet/engine-coverage.mjs` exports `engineCoverage({ tree, base, head, file, sims, width })` which resolves to `null` when `git diff -U0 <base> <head> -- <file>` in `tree` adds or modifies no line, and otherwise to `{ file, base, head, changed, reached, unreached, sims }`: `changed` the ascending new-side line numbers of every added or modified line of that diff; `sims` one `{ sim, exit, ms, reached }` per entry of the `sims` argument in the order given, each run as `node <tree>/<sim>` with cwd `tree` and the inherited environment plus `NODE_V8_COVERAGE` set to a fresh directory of its own under the OS temp dir, at most `width` at once; `reached` the ascending subset of `changed` whose count is greater than zero in at least one sim; `unreached` the rest of `changed`, ascending. M2. A line's count in one sim is the count of the innermost range containing the line's first character — ranges of one function are listed outermost first, and offsets index the file's text as a JavaScript string, not its bytes — read only from coverage script entries whose `url` is exactly the `file://` URL of `<tree>/<file>`; an entry for a copy of the same file at another path contributes nothing. A sim that exits non-zero has its exit recorded and its coverage read all the same. M3. In `runEngine`, after the last fold and before the report object is assembled, when the integration clone's `git diff --name-only <baseSha> HEAD -- fleet/run-engine.mjs` names the file and the integration tree holds at least one `fleet/tests/test_run_engine_*.mjs`, the engine calls `engineCoverage` with those sims sorted by path and `width` the run's width, and the returned report carries the reading as `engineCoverage`; on any other run the report carries `engineCoverage: null`. The reading changes no other report field: a run whose changed engine lines no sim reaches still ends with the `tests.passed` and `coverage.complete` it would have had without the reading. M4. `fleet/CONTRACT.md`'s evidence sub-bullet (the `ultra/evidence-run-<N>` item of "The three branches on the target") names `report.json`'s `engineCoverage` as a reading that gates nothing, and `skills/ultrapowers/references/report-format.md`'s field table carries an `engineCoverage` row, between the `coverage` and `missingDeliverables` rows, stating the M1 shape and that it is never gated.

**Authorized-by:** #992 desired state 1; `fleet/CONTRACT.md` evidence bullet; `skills/ultrapowers/references/report-format.md` field table.

**Context:** Measured at BASE: `NODE_V8_COVERAGE=<dir> node fleet/tests/test_run_engine_review_economy.mjs` takes 5.8 s and writes one `coverage-<pid>-<ts>-0.json` whose `result[]` holds TWO script entries ending `fleet/run-engine.mjs` — `file:///…/ultrapowers/fleet/run-engine.mjs` (300 functions, 760 ranges) and `file:///…/T/engine-review-economy-…/base-tree/fleet/run-engine.mjs` (124 functions), the second being the copy the sim lays into its scratch base tree — which is why M2 matches the URL exactly rather than by suffix. The JSON shape is V8's: `result[].functions[].ranges[]` of `{ startOffset, endOffset, count }`, the first range of a function being its whole span, inner ranges after it; the count at an offset is the innermost containing range's — the rule c8 applies — and offsets are JavaScript string indices, which matters because `run-engine.mjs` carries em dashes and box-drawing characters. The engine sims import the engine in-process (`fleet/tests/_engine_helpers.mjs:14` `import { runEngine } from '../run-engine.mjs'`), so the sim process's own coverage is the engine's; the children a sim starts (git, the kernel, `bash check.sh`) run under `simEnv()` and carry no `NODE_V8_COVERAGE`, which is correct. There are 13 `fleet/tests/test_run_engine_*.mjs` at BASE (`ls fleet/tests/test_run_engine_*.mjs | wc -l`), the longest `test_run_engine_proof_runs.mjs` at ~41 s on a laptop, so `width` 4 bounds the reading to about one suite's length; `fleet/package.json` has no dependencies and the module adds none (V8's own writer, a reader of ~40 lines, no `c8`). In `fleet/run-engine.mjs` at BASE: the exec seam is `exec(cmd, argv, { cwd, env, timeoutMs })` resolving `{ code, stdout, stderr }` (never rejecting; `sh` at ~726 wraps it as `bash -lc`), `execSeam` in `fleet/run-main.mjs:221` is the production one and the rig's default; `baseSha` is read at ~1756 (`git rev-parse HEAD` in `integ`); the report object is returned at ~4385 with `coverage` (the structural completeness signal — a different thing, keep both names) at ~4410 and `judgmentCalls` at ~4415 — put `engineCoverage` beside `coverage`; `lastSuite` at ~4312 is the last fold's suite result, and the reading runs after it. The engine's width is `args.width` (`run-main.mjs` passes `widthOf(launchArgs)`; the rig passes none, so default 4). `ultra_gate.py:98–100` writes `report.json` as the unwrapped engine result verbatim, so the new key reaches the evidence tag with no change to `run-main.mjs` or the boot.
