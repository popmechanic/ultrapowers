# A task starts early on a sibling's candidate only while the head has not moved

**Grammar:** claims-v1
**Claim:** do: launch this plan; see: a task that would start early on a sibling's unadopted candidate does so only while nothing else has landed since that candidate was cut; if the run's head has moved, it waits for the sibling's adoption and starts on the real head, and the record says which way it went and why. (elicited)
**Summary:** On fixture run-45, the page task started early on the store task's candidate, a tree cut before the rule task had landed, so all three of its builders worked without the file they needed and every build was red until the fold rescued it. This makes the early start conditional: it happens only when the head has not moved since that candidate was cut, and otherwise the task waits the few seconds for the sibling to land and starts on a tree that has everything. Runs with a task that depends on two siblings stop paying for builds that cannot pass, and the record shows each early start or wait with its reason.
**Goal:** `factory/dispatch.mjs` gains one pure export, `speculationFor`, that answers `launch`, `on-candidate` or `wait` with a reason from three facts (is the producer adopted, what is the run's head, where was the producer's candidate anchored); `factory/engine.mjs`'s readiness read asks it instead of branching on `done.has(producerId)` alone, remembers every dispatch's anchor, and writes a `speculate:wait` row the first time a task is held back at a given head; the `dispatch:on-candidate` row and `launchOnCandidate` itself are unchanged, so `speculate.on_candidate` keeps its rollback.
