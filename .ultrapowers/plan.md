# The sequential-adoption fold sim: every adoption order yields the simultaneous fold's tree (#832, the gate before Phase C of #810)

**Grammar:** claims-v1

**Claim:** do: run the fold-order sim on the merged engine. see: for every patch set it names, every order of adopting the tasks one at a time lands on exactly the tree the one-shot wave fold lands on, the sim shows it can catch a divergence, and the run's record says what sequential adoption costs in kernel calls. (elicited)
**Summary:** This is the measurement that decides whether tasks can be folded into the branch one at a time, as each finishes, instead of waiting for their whole wave to close. It exists because the barrier-slack reading on runs 91–115 found a finished task waits a median quarter of an hour for its wave, and per-task adoption is only safe if arrival order cannot change the result. After this run you know, from a model-free sim over real same-file joins, whether the pool of Phase C is safe to build or whether the wave barrier was load-bearing.

**Goal:** #832 — `fleet/tests/test_readiness_fold_order.mjs`, a model-free sim: for every patch set (the synthetic fold corpus waves 1–5 built by `evals/frontier/corpuslib.make_fixture_corpus`, plus the real-join fixtures committed under `fleet/tests/fixtures/readiness/<fixture>/`), the simultaneous fold's tree equals the tree of every sequential adoption order (each step the publish-fold's two-patches-against-recorded-base shape), the narrated conflict keys agree, a negative control is caught, and the cost per order is recorded. The real-join patches for `contend`, `contend-wide` and `degrade` are produced once by a scripted split of each fixture's `reference/` against its `project/` and committed. `contend-big` and `bun-greenfield` have no `reference/` tree at BASE and are out of this plan; a later task adds them the same way. Never a change to the kernel: a red equality is a finding on #360, and the run parks on it.
**Closes:** #832

**Tech Stack:** Node 24 ESM sims under `fleet/tests/` (`node:test` is not used there — the sims are plain `assert` scripts ending in `ALL TESTS PASSED`), Python 3 (`skills/ultrapowers/kernel/fold_wave.py` driven as a CLI, `evals/frontier/corpuslib.py`, `evals/frontier/split_fixture.py`), git.

**Exam command:** node {paths}

**Spec:** #832 (its body is the spec; the research appendix it came from is on the laptop only — every fact a worker needs is in Context).

**Parallelization rationale:** one wave, two wide — task 1 (the sim) and task 2 (the real-join fixture patches). Task 1's sim reads `fleet/tests/fixtures/readiness/*/manifest.json` by glob and runs on the corpus and its negative control alone when the directory is empty; task 2 writes that directory and never touches the sim. The manifest shape is a shared literal in both Contexts, so no edge is needed: the sim needs task 2's *shape*, not its runtime behaviour, and the integrated run on the adopted tree is where the sim first meets the fixtures. Neither task edits a file the other names.

**Claim:** A model-free sim `fleet/tests/test_readiness_fold_order.mjs` proves: for every fixture patch set, every sequential adoption order yields the same tree as the simultaneous fold. (quoted from #832)
Machine: M1. For each of the corpus waves 1, 2, 4 and 5 built by `make_fixture_corpus`: every order the kernel's `sampled_orders(n)` returns yields, by sequential adoption, a candidate whose `^{tree}` sha equals the simultaneous fold's candidate `^{tree}` sha. M2. Corpus wave 3 (the rewrite over an inner edit, one `lines` conflict on `d.txt`) is folded in both modes with the same committed reply text for its hunk, and every order's tree equals the simultaneous tree. M3. For every set, the set of `(path, kind)` pairs narrated across all of an order's sequential steps equals the simultaneous fold's set, for every order. M4. A negative-control set, whose committed reply for one hunk is chosen by the step index the conflict arose at, is reported by the sim as `caught` — its trees differ between at least two orders — and the sim still ends `ALL TESTS PASSED`. M5. The sim prints one line per set of the form `<set> n=<tasks> orders=<k> tree=<sha> sim=<sha> ok` (`caught` in place of `ok` for the negative control), each carrying `steps=<n> kernelCalls=<n>` for the cost of one order, and ends with `ALL TESTS PASSED`. M6. Every directory under `fleet/tests/fixtures/readiness/` that holds a `manifest.json` is a set the sim runs the same way as a corpus wave, and with that directory absent or empty the sim runs the corpus sets and the negative control alone. M7. A soft-edges pair — corpus wave 2's `2b` re-captured against the head that adopted `2a`, folded with that head as its recorded base — yields the simultaneous wave-2 tree.

**Authorized-by:** #832; #810 (Phase C gate, re-charter of 2026-09-13); #360 (never patch `vendor/manyana.py`)

**Interfaces:**
- Consumes: none
- Produces: `runSet(spec) -> {simTree, simConflictKeys, repliesUsed, orders: [{order, tree, conflictKeys, repliesUsed, steps, kernelCalls}], verdict}` (in `fleet/tests/_readiness_helpers.mjs`)

**Context:** Every kernel call is `python3 skills/ultrapowers/kernel/fold_wave.py <verb> --repo <repo> --run-dir <dir> --wave <int> …`; `--wave` is `type=int`, and `fold` exits 2 when `<run-dir>/frontier/wave-<n>/fold_log.jsonl` already exists, so give every step its own `--run-dir` (a fresh temp dir per order and step is the simplest key). The verbs used: `fold --base <sha> --patch <id>=<file> [--commutes <id>=<path,…>]` (prints a JSON summary; `"complete": true` with `"autoResolved"` counts a commutes-licensed union), `resolve --conflict <i> --reply-dir <dir> --base … --patch …` (the reply dir holds `h<N>.txt` per hunk id in the conflict's hunks file, newline-terminated, plus `notes.txt`; `hunks.read_reply_dir` refuses an unknown or missing hunk file), `materialize --prev-head <sha> --patch <id>=<file>` (prints `{"candidateSha": …}` on success and `{"fallback": "…"}` when a narrated path is unresolved; it takes no `--commutes`). A patch is `git diff --binary --full-index --no-renames <BASE>` taken in a clone, which is exactly what `corpuslib._capture_patch` writes. **The sequential step, measured by hand on 2026-09-13:** head ← BASE; for each task t in the order, `adopted.patch` = `git diff --binary --full-index --no-renames BASE head` (empty on the first step — pass no `adopted` patch then), then `fold --base BASE --patch adopted=<adopted.patch> --patch t=<t.patch>` and `materialize --prev-head head` with the same `--patch` list, head ← the candidate. Waves 1, 4 and 5 folded to the simultaneous tree in both orders on the first try. Wave 2 did NOT until the set's `commutes` declaration was carried onto the adopted pseudo-task as well — `--commutes adopted=c.txt --commutes 2b=c.txt` on the `fold` call — after which both orders matched (`effc72ef…`); without it the second step narrates one `lines` conflict on `c.txt` and materialize falls back. So a set's commutes map applies to `adopted` at every step where any already-adopted task declared that path. Wave 3 was not probed by hand: its one conflict (`d.txt`, `lines`, hunk `h1`: `frontier` side `d alpha rewritten / d beta rewritten`, `3b` side `d alpha tuned`) needs a `resolve` in both modes; the committed reply for it is the resolved text of that region and is the same file whichever side is labelled `frontier`, so key replies by `(set, path, hunk id)` and never by side label or step. Build the corpus once per sim run with `python3 -c 'import sys; sys.path.insert(0, "evals/frontier"); import corpuslib; corpuslib.make_fixture_corpus(sys.argv[1])' <dir>` (2 s; `<dir>/repo` is the scratch repo at BASE, `<dir>/work/patches/wave-<n>/task-<id>.patch` the per-task patches, `corpuslib.SCENARIOS` and `FIXTURE_COMMUTES` name the waves, their tasks and the commutes). Take the orders from the kernel itself: `python3 -c 'import sys, json; sys.path.insert(0, "skills/ultrapowers/kernel"); from frontier_fold import sampled_orders; print(json.dumps(sampled_orders(int(sys.argv[1]))))' <n>` — all n! for n ≤ 4, the identity plus 19 seeded shuffles above. One fold plus materialize costs about 0.75 s on a laptop; the suite bridge (`tests/test_fleet_suite.py`) caps a sim file at 300 s, and a real-join set of eight tasks at 20 orders is ~120 s of that budget, so print each set's line as it finishes and keep the corpus work first. The real-join sets arrive from a sibling task as directories `fleet/tests/fixtures/readiness/<fixture>/` holding `manifest.json` — exactly `{"fixture": "<name>", "project": "evals/fixtures/<name>/project", "tasks": [{"id": "<task id>", "patch": "task-<id>.patch"}, …], "commutes": {"<task id>": ["<path>", …]}, "replies": "replies"}` — the patches beside it, and `replies/<path with / as __>/h<N>.txt` for any hunk the simultaneous fold narrates; the sim builds that set's BASE by copying `project/` into a scratch repo and committing it, then runs it exactly like a corpus wave. Assertion 3's cost line counts kernel CLI calls (fold, resolve, materialize) per order; the sim runs no suite. The negative control is built inline from corpus wave 3's patches with a reply directory that answers `h1` with one text at step 1 and another at step 2, so the two orders materialize different trees; the sim must report it `caught` and count it as a pass of assertion 4. The exam `fleet/tests/test_readiness_fold_order_exam.mjs` is the peer examiner's file at a stable path (guarded): it runs the sim once as a child process with `READINESS_FIXTURES_DIR` pointed at an empty temp directory (so the exam's own wall is the corpus and the control, ~15 s, and never the real-join sets) and reads that stdout for every leg that needs a sim line, and it imports `runSet` from `_readiness_helpers.mjs` to drive one hand-built two-task set whose expected trees it computes itself. Existing helper conventions to copy: `fleet/tests/_helpers.mjs` (`sh`, temp dirs, the `ok (…) — name` line and the sentinel).

**Proof:**
- Test: `fleet/tests/test_readiness_fold_order_exam.mjs`
- Guard: `fleet/tests/test_readiness_fold_order_exam.mjs`
- Legs: (a) for each of corpus waves 1, 2, 4 and 5, the sim's stdout line for that wave carries `ok` and a `tree=` sha equal to its `sim=` sha, and `runSet` over that wave returns every order with `tree` equal to `simTree` [M1]; **Context:** The fixtures live under `evals/fixtures/<name>/` with `plan.md` (legacy grammar: `### Task N:` headings, a `**Files:**` block of `Modify:`/`Create:`/`Test:` bullets, checkbox steps naming the symbol each task adds), `project/` (BASE) and `reference/` (the whole plan applied). `contend` has 5 tasks: tasks 1–3 each `Modify: clitool/cli.py` (the `--verbose`, `--format`, `--limit` flags), task 4 `Create: clitool/textutil.py`, task 5 is a run-the-tests gate with `**Files:** none` and gets no patch; `reference/` differs from `project/` in `clitool/cli.py` and adds `clitool/textutil.py`, and `project/tests/` has no counterpart in `reference/` (leave tests out of every patch — the fixture's `Test:` paths are not in `reference/`). `contend-wide` has 8 tasks all on `clitool/cli.py`; `degrade` has 3 on `confkit/config.py`. A patch is `git diff --binary --full-index --no-renames <BASE>` taken in a clone of the scratch repo whose BASE commit is `project/` committed with a fixed author, email and date (`GIT_AUTHOR_DATE=GIT_COMMITTER_DATE=2026-08-31T00:00:00+00:00`) so the BASE sha, and therefore M3's byte-identity, is reproducible. The manifest is exactly `{"fixture": "<name>", "project": "evals/fixtures/<name>/project", "tasks": [{"id": "<task id>", "patch": "task-<id>.patch"}, …], "commutes": {"<task id>": ["<path>", …]}, "replies": "replies"}` — `commutes` names, per task, the paths whose same-anchor additions the fixture's plan calls independent (all three of `contend`'s flag tasks on `clitool/cli.py`, all eight of `contend-wide`'s, `degrade`'s tasks on `confkit/config.py`); leave `replies/` absent unless the simultaneous fold of the set narrates a hunk that commutes does not license, in which case commit `replies/<path with / as __>/h<N>.txt` with the region's text as `reference/` has it.
