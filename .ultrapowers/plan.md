# The worker's `settled` tool reads its candidates off the worker's own patch, a new file's exports included, and a refusal names what it found

**Grammar:** claims-v1

**Claim:** `settled` offered a symbol that the worker's patch exports (a new file included) accepts it; the candidate list is exam-driven off a patch that adds a file with one `export function`. (quoted from #1229)
**Summary:** A worker declares which symbol it settled through a tool, and on run-215 that tool refused every symbol offered because a brand-new file's exports were never counted. This plan makes a new file's exports valid candidates and makes a refusal name what it did find. Workers stop wasting turns arguing with a tool that cannot see their own work.

**Goal:** #1229 (map #1131): the `settled` tool's candidate list is read off the worker's own working tree at the moment it is called, through the engine's own `candidatesOf` over the same capture the landing uses, instead of the empty list the tool server is built with at dispatch; a refusal names the candidates found and, for a shell file, says why a shell function is never one.
**Closes:** #1229

**Tech Stack:** Node 24 ESM; no new npm dependency.
**Exam command:** node {paths}
**Spec:** none on disk — issue #1229 and the two run-215 worker notes it quotes are the brief, and everything a worker needs is in its own Context. The sandbox holds no spec.

- Check: git diff --quiet $ULTRA_BASE -- factory/roles factory/union.mjs factory/worker.mjs factory/reverify.mjs factory/judge.mjs factory/questions.json factory/boot.sh fleet/fleet-bootstrap.sh skills/ultrapowers/kernel
