# A finished task lands however far the head has moved — its patch is folded as a three-way over the head it was captured against, resolved by the resolver when the edits overlap, and never refused

**Grammar:** claims-v1

**Claim:** When a task finishes after a sibling's work has already been folded, I see it fold onto the moved head anyway — cleanly when the edits sit apart, through the resolver when they overlap — and the run's record says which of the two it was; a clean task is no longer parked for a hand merge and a re-drive. (elicited)
**Summary:** This closes the one hole in the doctrine that same-file work folds at merge: today that holds only when two tasks land in the same fold, and a task whose patch was captured before a sibling's fold landed is refused outright, with a park, a hand merge and a re-drive as the price. After this run the kernel knows which head each patch was captured against and folds it as a three-way over that head, so a moved context merges by construction and a real overlap becomes a narrated conflict the resolver already knows how to answer. It exists so that the run finishes what its reviewers passed, and so that the record names how each task landed — on its own head, rebased, or resolved.

**Goal:** #1019 (map #810, filed 2026-09-15 on runs 136 and 146): a task patch captured against an older head that no longer applies on the epoch head at fold time is folded rather than refused — a three-way over the head it was captured against, clean when the edits sit apart and a resolver-narrated conflict when they overlap — and `driver:wave-adopted` says per task whether it applied on its own head (`base`), was rebased clean (`rebased`) or went through a resolution (`resolved`); `fold printed no verdict (exit 2)` remains only for a fold whose resolver misses. Two contracts on BASE `cef3aef8`: (1) the kernel takes a per-patch anchor and folds over it; (2) the engine passes each result's capture anchor, records `applied` per task on the adoption event, and emits `driver:wave-blocked` for a `CONFLICT` epoch too. The reading to keep is refusals per run before and after; #1019 carries the two.

**Claim:** When a task's patch was captured against an older head than the one the fold is onto, the kernel folds it anyway — the same result as if the task had been written on the new head, or a narrated conflict where the two edits meet — instead of refusing the whole fold. (derived)
Machine: M1. A `--patch` spec is `<taskId>=<patchFile>` or `<taskId>=<patchFile>@<anchorSha>` on `fold`, `resolve` and `materialize` alike; a spec without `@` has the wave's `--base` (for `materialize`, the log's base) as its anchor, and the patch is applied over its anchor — never over `--base` — to derive the task's tree, so a patch that applies over its anchor is never `does not apply`. M2. A patch whose anchor is the wave's `--base` folds exactly as at BASE: for a two-task wave both anchored at `--base`, the fold log's events carry the same `type`, `task` and `headSha` values and no `anchor` key, `conflicts.json` is byte-identical, and the `materialize` candidate's `a.txt` is the same text, all against the reading the BASE kernel produces for the same inputs. M3. A patch anchored at an older head H, folded onto a `--base` that descends from H, is merged as a three-way over H: for each path the task touched, the frontier's current lines are re-rooted as an edit over H's file and merged with the task's edit over H's file, so a task that changed line 2 of a file whose line 8 the head has since changed folds clean and the candidate carries both changes, while the same task folded onto a head that changed line 2 differently narrates one conflict on that path whose marker sides read `frontier` and the task's id — the shape `hunks.derive` accepts, so `resolve --conflict 1 --reply-dir D` with one `h1.txt` completes the wave and `materialize` yields a candidate carrying the reply's lines. M4. The fold log's `fold` event gains `anchor` (the anchor sha) whenever the anchor differs from the log's base, and `rehydrate` re-derives such a task over its recorded anchor, so the post-fold self-checks read `ok` and a second `resolve` or `materialize` on the same wave rebuilds the same engine; a `fold` event without `anchor` reads as anchored at the base, so every log written before this task rehydrates unchanged. M5. `materialize` applies the touched set derived per task against that task's anchor: a path the head added after the task's anchor, which the task never touched, is present in the candidate with the head's content, and a path the task deleted relative to its anchor is absent. M6. The two refusals stay for what they name: a patch that does not apply over its own anchor is still `refusing wave N: patch for task <id> (<file>) does not apply against base <anchor>` on stderr with exit 2, and a task head not descended from `--base` is still refused. M7. `skills/ultrapowers/kernel/FOLD_LOG.md` documents the `anchor` field on the `fold` event and the `@<anchorSha>` form of `--patch`, and `git diff --quiet $ULTRA_BASE -- skills/ultrapowers/kernel/vendor` holds.
